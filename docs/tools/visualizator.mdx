The EEZ Visualizator is a web dashboard for inspecting cross-chain execution flows step by step. Rather than reading raw execution tables in your terminal, the Visualizator presents the evolution of L1 and L2 execution queues side by side, highlights cross-chain call correlations as they are consumed, and lets you step through the entire execution plan at your own pace. Use it to build intuition for how EEZ batches work, or to verify that a given transaction bundle matches your expectations.

## Accessing the Visualizator

The hosted version is always available at:

**[https://visualizator-woad.vercel.app](https://visualizator-woad.vercel.app)**

No installation is required. Open the URL in any modern browser to start exploring the built-in example scenarios.

## Two Visualizator Tools: Scenario Demo and Live Dashboard

The `visualizator/` directory ships two distinct tools:

- **Scenario demo (`visualizator/index.html`)** — the static, single-file HTML page described below. This is what's hosted at [https://visualizator-woad.vercel.app](https://visualizator-woad.vercel.app). It works entirely from the built-in scenario data and has no network connectivity of its own.
- **Live dashboard (`visualizator/dashboard/`)** — a separate Vite + React + viem application that connects directly to real L1 and L2 RPC endpoints for live block inspection. Its Connection Bar lets you enter L1/L2 RPC URLs and contract addresses; the `useChainWatcher` and `useAutoDiscovery` hooks then watch both chains and stream real cross-chain execution events into the same execution-table / flow-diagram / state-panel UI as the scenario demo.

For live network inspection without running the dashboard yourself, you can also use the EEZ trace decoder CLI (see [Trace Decoder](/tools/trace-decoder)) to produce a unified execution diagram from real transaction traces.

## What the Visualizator Shows

The dashboard is organized around **scenarios** — pre-loaded examples of cross-chain execution patterns. Each scenario contains:

### Execution Tables

The main panel shows the L1 and L2 execution tables side by side. Each entry in the table displays:

- **Entry index** — position in the queue.
- **Action hash** — the `keccak256` identity of the cross-chain call (`actionHash`).
- **State delta** — the `currentState → newState` transition and `etherDelta` for this entry's rollup.
- **Call count** — number of top-level cross-chain calls in the entry.
- **Rolling hash** — the expected hash of the executed call sequence.
- **Nested actions** — any [`ExpectedL1ToL2Call`](/contracts/data-types#expectedl1tol2call) / [`ExpectedOutgoingCrossChainCall`](/contracts/data-types#expectedoutgoingcrosschaincall) frames.

Entries are color-coded: blue for L1, purple for L2. The currently active step is highlighted in teal, and consumed entries appear with a strikethrough.

### Transaction Bundles (Step-by-Step View)

The **Steps** panel lists the ordered sequence of cross-chain events across both chains. Each step has:

- A chain badge (`L1` or `L2`) identifying where the event occurs.
- A human-readable title describing the call (`bridgeTokens`, `receiveTokens`, `claimAndBridgeBack`, etc.).
- A detail line showing which entries are added to or removed from the queue.
- The state delta applied at this step.

Click any step to jump to that point in the execution. The execution tables and state panels update to reflect the queue state at that exact moment.

### Cross-Chain Call Correlations

The **Flow Diagram** at the top of each scenario renders a node-and-arrow diagram of the cross-chain call graph. Each node represents a contract:

- Solid blue border — L1 contract.
- Solid purple border — L2 contract.
- Dashed border — `CrossChainProxy` (gateway between chains).
- Highlighted border — the contract involved in the current step.

Arrows between nodes are labeled with the function name and carry a direction indicator. The diagram makes the proxy-to-original and original-to-proxy relationships immediately visible.

### Contract States

Below the execution tables, the **L1 Contracts** and **L2 Contracts** panels list each contract involved in the scenario alongside its current value — a scenario-defined abstract state label (for example, a counter or a short descriptive tag), not a rollup-level state root or ETH balance. A contract's value is highlighted when it changes at the current step, so you can see which contracts were affected by the step you're on.

The rollup-level [`StateDelta`](/reference/glossary#statedelta) fields (`rollupId`, `newState`, `etherDelta`) aren't shown at this panel — they appear inside an individual execution-table entry's own expanded detail view, alongside that entry's `calls[]` and `nestedActions[]`.

## Built-In Scenarios

The Visualizator ships with several built-in scenarios corresponding to the EEZ e2e test cases:

| Scenario | Description |
|---|---|
| L1 → L2 | A single L1 entry calls an L2 contract via proxy; one entry per chain, consumed sequentially by execution index |
| L2 → L1 | A single L2 entry calls an L1 contract via proxy; one entry per chain, consumed sequentially by execution index |
| L2 → L1 → L2 | Starts on L2, crosses to L1, and the L1 contract dispatches a reentrant nested call back to L2 via `_consumeNestedAction` |
| L1 → L2 → L1 | Starts on L1, crosses to L2, and the L2 contract dispatches a reentrant nested call back to L1 via `_consumeNestedAction` |
| Cross-Chain Flash Loan | A flash loan on L1 bridges tokens to L2, claims a token-gated NFT, bridges the tokens back, and repays the loan — spans three entries per chain plus a nested action for the bridge return |

Select a scenario using the tabs at the top of the page.

## Self-Hosting the Scenario Demo

`visualizator/index.html` is a self-contained static file with no build step — open it directly in a browser, or serve it from any static host (Vercel, Netlify, GitHub Pages, or a plain CDN).

## Self-Hosting the Live Dashboard

The live dashboard is a Vite project with its own `package.json`, located at `visualizator/dashboard/`.

### Step 1 — Navigate to the dashboard directory

```bash
cd visualizator/dashboard
```

### Step 2 — Install dependencies

```bash
npm install
```

### Step 3 — Start the development server

```bash
npm run dev
```

Vite starts a local server (typically at `http://localhost:5173`). Open it, click **Connect**, and enter your L1/L2 RPC URLs and contract addresses in the Connection Bar. The dashboard hot-reloads on any change to the source files.

### Step 4 — Build for production

```bash
npm run build
```

The built files land in `dist/`. Deploy them to any static hosting provider: Vercel, Netlify, GitHub Pages, or a plain CDN.

## Interpreting the Execution Table Colors

| Color / State | Meaning |
|---|---|
| Teal highlight | Entry just added to the queue at the current step |
| Red strikethrough | Entry consumed (executed) at the current step |
| Dim + strikethrough | Entry was consumed in a previous step |
| Normal | Entry queued but not yet consumed |

When an entry is consumed, its state delta is applied: the rollup's `stateRoot` advances from `currentState` to `newState`, and `etherBalance` is adjusted by `etherDelta`. You can confirm this by watching the state panels update in sync.
