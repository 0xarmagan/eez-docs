EEZ's execution model inverts the normal on-chain programming model: rather than executing calls and discovering results, you pre-compute every result off-chain, commit to those results with a proof, and then replay the pre-approved execution deterministically on-chain — from building an `ExecutionEntry` off-chain, through submitting it in a batch, to consuming it in the same block.

## Off-Chain Simulation by the Rollup Node

Before any transaction reaches L1, the rollup node runs a complete simulation of the cross-chain interaction. It steps through every contract call across every involved chain, records the exact return data from each call, tracks every reentrant callback, and computes the `rollingHash` that will be verified on-chain. The simulation runs against specific state roots — the committed state of each rollup at a particular point in time.

This simulation produces two kinds of outputs:

- **`ExecutionEntry` structs**: the pre-computed call plan for each cross-chain interaction.
- **ZK proofs** (or multi-prover attestations): cryptographic evidence that each `ExecutionEntry` correctly describes the state transition for its target rollup, given those specific pre-state roots.

## The `ExecutionEntry`

The [`ExecutionEntry`](/reference/glossary#executionentry) is the central pre-computed record for a single cross-chain interaction. Conceptually it holds four kinds of information:

- **What state changes** — a list of pre-state → post-state transitions, one per rollup the entry touches, plus a signed ETH change for each.
- **What calls run** — the entry's own top-level calls, in its own array; every reentrant frame (a plain callback, a static read, or a try/catch'd revert) carries its **own** sub-array instead of sharing one flat array with the top level.
- **What the calls return** — pre-computed return data for the top-level call, plus a `success` flag; the same call plus flag pattern repeats on every row of the unified reentrant table, and on the top-level static-entry pool for read-only queries.
- **How to check integrity** — an expected [`rollingHash`](/reference/glossary#rollinghash) that must match after every call and nesting has been replayed, plus a `proxyEntryHash` that routes the entry (immediate vs. proxy-triggered — see [transient vs. deferred](/reference/glossary#transient-vs-deferred)).

If the live state root doesn't match the entry's expected pre-state, EEZ reverts. This is the protocol's safety backstop: even if a stale entry somehow makes it into the queue, it cannot corrupt state.

<details>
<summary>For builders: exact struct layout</summary>

Full struct field listings, including every field's role and packing, live in [Data Types](/contracts/data-types). The core structs:

```solidity
// From src/interfaces/IEEZ.sol
struct ExecutionEntry {
    StateUpdate[]         stateUpdates;         // per-rollup pre-state → post-state transitions (≥1, enforced on-chain)
    bytes32               proxyEntryHash;       // bytes32(0) = immediate (L2 tx), else action hash
    L2ToL1Call[]          l2ToL1Calls;          // the entry's TOP-LEVEL calls only — reentrant frames carry their own
    ExpectedL1ToL2Call[]  expectedL1ToL2Calls;  // unified reentrant table: SUCCESS / STATIC / REVERTED rows
    bytes32               rollingHash;          // expected final hash after all calls + nestings replay
    uint64                destinationRollupId;  // routes this entry into the correct per-rollup queue; must be ∈ stateUpdates
    bool                  success;              // false ⇒ the entry runs, is verified, then reverts with returnData
    bytes                 returnData;           // pre-computed top-level return value (revert payload when !success)
}

struct L2ToL1Call {
    uint16  revertNextNCalls; // 0 = normal; N>0 = force-revert state effects of the next N calls (this one included)
    bool    isStatic;         // dispatch via STATICCALL (read-only; value must be 0)
    uint64  gas;              // gas limit for the target call; 0 = forward all remaining gas
    address sourceAddress;
    uint64  sourceRollupId;
    address targetAddress;
    uint256 value;
    bytes   data;
}

struct StateUpdate {
    uint64  rollupId;
    bytes32 currentState;   // checked against rollups[rollupId].stateRoot — mismatch is a non-match at the queue, or StateRootMismatch for immediate entries
    bytes32 newState;
    int256  etherDelta;
}
```

`l2ToL1Calls[]` holds only the entry's own **top-level** calls. Every reentrant frame — a plain successful callback, a read-only static row, or a try/catch'd reverting call — is a row of the unified `expectedL1ToL2Calls[]` table, and each row carries its **own** sub-call array (also typed `L2ToL1Call[]`) that its resolver runs to completion independently. There's no shared flat array and no `callCount` bookkeeping left anywhere in the struct: a frame's completeness is structural (its resolver processes the whole array it was handed), not counted. See [Build Entries](/guides/build-execution-entries) for a step-by-step builder walkthrough and [Static Entries](/guides/lookup-calls) for the unified reentrant table's STATIC/REVERTED rows.

</details>

## Per-Frame Sub-Arrays: No Shared Partition

Earlier versions of the protocol partitioned one flat call array between the top-level frame and its reentrant callbacks, tracked by a `callCount` invariant and a single monotonically-increasing cursor. That model is gone. Every reentrant-table row and every static entry now carries its **own** sub-call array, run to completion by its own resolver:

- A plain **SUCCESS** row folds its sub-array into the host's continuous rolling hash between `NESTED_BEGIN`/`NESTED_END`.
- A **STATIC** row (or a top-level `StaticExecutionEntry`) runs its sub-array flatly via `_processNStaticCalls`, using an untagged hash.
- A **REVERTED** row runs its sub-array as its own mini-entry via `_processNCalls` under the tagged schema — it may itself contain further reentrant calls, resolved from the same host table — then terminal-reverts.

Suppose your entry has a top-level call that triggers a reentrant callback. The top-level frame's `l2ToL1Calls[]` holds only the top-level call; the reentrant callback is a separate row in `expectedL1ToL2Calls[]` with its own `l2ToL1Calls[]` sub-array, matched not by position but by a content-addressed key (below). There is no shared cursor across frames and no `callCount` to keep in sync: each frame's array is processed in order, in full, by whichever function owns that frame — the entry's top-level array by `_processNCalls`, a reentrant row by its resolver. Completeness for a SUCCESS row rests entirely on the rolling hash (a skipped frame omits its `NESTED_BEGIN`/`NESTED_END` folds and diverges the hash); an unconsumed STATIC or REVERTED row is simply inert — the table may legitimately contain rows a given run never touches.

<details>
<summary>For builders: the position key that replaced call counts</summary>

Every reentrant-table row is content-addressed by one value instead of a slice offset:

```text
expectedL1toL2Hash = keccak256(abi.encodePacked(crossChainCallHash, expectedRollingHash))
```

`expectedRollingHash` is the live `_rollingHash` at the instant the reentrant call or read fires — it uniquely pins the execution point because the hash chain folds every prior call result and nesting boundary. Matching walks strictly forward from the reentrant cursor (`_lastL1ToL2CallConsumed` on L1); the first key match is the row. A resolved CALL advances the cursor past its row; a static read (a `view` frame) cannot advance it, so the same STATIC row can satisfy repeated identical reads fired at the same hash point.

See [Static Entries](/guides/lookup-calls) for the full key derivation and [Build Entries](/guides/build-execution-entries) for the constructor walkthrough.

</details>

## Immediate vs. Deferred Entries

An entry's `proxyEntryHash` field determines how it is consumed:

- **Immediate** (`proxyEntryHash == bytes32(0)`): The entry represents a pure L2 transaction or a batch's built-in L1 work. `postAndVerifyBatch` executes these inline, before the [meta hook](/reference/glossary#meta-hook) (the callback that lets the batch submitter consume transient entries in the same transaction) fires. If an immediate entry reverts, EEZ emits `L2TxSkipped` and continues — it is not a hard error.
- **Deferred** (`proxyEntryHash != bytes32(0)`): The entry is triggered by a proxy call. It sits in the per-rollup queue (or the transient stream) waiting for `executeCrossChainCall` to consume it — `executeL2Txs(rollupId)` only ever consumes immediate entries. The caller's proxy recomputes `crossChainCallHash` from the live call context; if it matches the entry's `proxyEntryHash`, the entry is consumed and executed.

## What Happens at `postAndVerifyBatch`

`postAndVerifyBatch` is the single entry point that loads a full batch onto L1. In order: it validates the batch's structure, fetches per-rollup verification keys, verifies all proofs atomically, marks each touched rollup verified-this-block, drains the leading run of immediate L2Tx entries straight from calldata, fires the meta hook (if transient-prefix entries remain and `msg.sender` has code) so the caller can consume them via proxy calls, saves the remainder unconditionally into per-rollup persistent queues, and only then clears the transient tables (closing the re-entry window) and emits `BatchPosted`. See [Post Batch](/guides/post-verify-batch) for the complete step-by-step pipeline, struct fields, and error table.

:::note
The phrase "same block" is load-bearing. All entries posted in a `postAndVerifyBatch` call must be consumed before the block ends. Any unclaimed entry is overwritten when the next `postAndVerifyBatch` verifies the same rollup — or simply becomes unreachable because the `lastVerifiedBlock` guard will reject it in a future block.
:::

## Entry Consumption: `executeCrossChainCall` and `executeL2Txs`

Once entries are in the per-rollup queue, they're consumed by a single forward scan — there is no separate lookup pool for top-level reverting calls. When a user calls a cross-chain proxy on L1, the proxy routes to `executeCrossChainCall`. EEZ recomputes `crossChainCallHash` from the proxy's identity and the live call context, then scans the queue forward from the rollup's cursor (`_findMatchingEntry`) for the first entry whose identity, routing, and state preconditions all match (`_entryMatches`):

- **Identity**: `entry.proxyEntryHash == crossChainCallHash`.
- **Routing**: `entry.destinationRollupId == destRid`.
- **State preconditions**: every one of the entry's `StateUpdate.currentState` values equals the live `rollups[rollupId].stateRoot`.

On a match, EEZ executes all calls in `l2ToL1Calls[]`, verifies the rolling hash and ether invariant, and applies the state updates. The entry's `success` flag then decides the outcome: `true` returns `entry.returnData`; `false` rolls back everything just applied (state updates included) and reverts with `entry.returnData` as the payload. A top-level cross-chain call that's meant to revert is just an ordinary `ExecutionEntry` with `success == false` sitting in the same queue as every other entry — matched by the exact same forward scan, with no separate lookup pool or fallback check.

If the scan reaches the end of the queue with no match, EEZ reverts `ExecutionNotFound`. Skipping a non-matching entry costs nothing: a `success == false` entry that already reverted on an earlier attempt leaves the cursor where it was (the revert rolled back the cursor bump too), so a later call simply scans past it to reach whichever entry actually matches.

`executeL2Txs(rollupId)` is the permissionless entry point for immediate entries (`proxyEntryHash == 0`). It consumes the next matching entry in the rollup's queue that was posted as a pure L2 transaction, through this same matching machinery.

## L2-Side Execution

On L2, the execution model is leaner: there are no state updates, no per-rollup queue maps, and no transient/deferred split. The system address calls `loadExecutionTable` to atomically replace the execution table (or `executeIncomingCrossChainCall` for inbound calls from another rollup), and user transactions consume entries through `executeCrossChainCall` exactly as on L1. The same rolling hash mechanics apply — every call is hashed into `_rollingHash` and checked against `entry.rollingHash` at the end.
