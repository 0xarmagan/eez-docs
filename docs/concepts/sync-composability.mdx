Ethereum's rollup ecosystem fragments liquidity and composability: when your contract on one rollup calls a contract on another, you normally wait minutes or hours for a bridge message to settle, destroying the tight execution guarantees that make DeFi primitives possible. EEZ removes that wait entirely by committing to the full outcome of every cross-chain interaction before any on-chain state changes — letting you compose across rollups as freely as you compose within a single chain.

## Why Traditional Bridges Break Composability

Standard cross-rollup bridges work by locking assets on the source chain, posting a message to L1, and releasing assets on the destination chain once the message is confirmed. This multi-step dance introduces three fundamental problems:

- **Latency**: Finality on L1 takes about two epochs (~13 minutes), and withdrawal periods on optimistic rollups can reach 7 days. Your transaction cannot atomically depend on the result of a call on another chain.
- **No atomicity**: If the second leg of your transaction fails, you must manually unwind the first. Flash loans — borrow, use, repay in one transaction — are impossible across chains using async bridges.
- **Fragmented liquidity**: Protocols must maintain separate reserves on each rollup, duplicating capital and increasing slippage.

:::note
EEZ is purpose-built for **based rollups** — rollups that share the L1 block proposer as their sequencer. Because a single entity sequences both L1 and all participating rollups in the same L1 block, EEZ can guarantee that a cross-rollup interaction plays out atomically within that block's execution window.
:::

## The Based Rollup Assumption

EEZ's atomicity guarantee rests on one architectural premise: all participating rollups share the same L1 sequencer (they are "based" rollups). When a single sequencer proposes both the L1 block and the rollup blocks derived from it, you get a coherent ordering across chains — the sequencer can ensure that the L1 verification transaction (`postAndVerifyBatch`) and the corresponding rollup execution transactions land in the same L1 block. Without this shared sequencer, cross-rollup atomicity would require a separate coordination layer.

## The Pre-Compute-Then-Replay Model

EEZ's core insight is that you can move all the uncertainty off-chain. Before anything touches the blockchain, the rollup node simulates the entire cross-chain interaction — every contract call, every return value, every reentrant callback — against the current state of all involved chains. The results of that simulation are packaged into `ExecutionEntry` structs and submitted to L1 along with an attestation that the simulation was faithful to each chain's state transition rules. Today that attestation is an M-of-N multi-prover signature set (ECDSA-based); EEZ's target architecture replaces it with a zero-knowledge proof — see below.

On-chain, EEZ doesn't re-discover what happened; it replays a pre-approved script:

1. **Off-chain**: The rollup node simulates the full execution tree, records every call's return data, and computes a `rollingHash` that commits to the entire sequence of events.
2. **Proof generation**: An attestation is generated — the M-of-N multi-prover signature set described above — binding the execution entries to specific state roots on each rollup.
3. **`postAndVerifyBatch`**: The L1 EEZ contract verifies the proof, loads the entries, and executes any immediate work. Deferred entries are queued per-rollup, ready for consumption in the same block.
4. **Consumption**: When your contract calls a cross-chain proxy, the proxy forwards the call to EEZ, which replays the pre-approved entry — verifying the rolling hash at the end to confirm nothing diverged from the simulation.

The reason this can stay synchronous is real-time proving: EEZ's design targets verifying and aggregating per-rollup and blob proofs into a single on-chain PLONK proof, fast enough to land inside an L1 slot. This ZisK-based aggregation pipeline is the target architecture, not the proof system running today — see [Security](/reference/security) for the current, ECDSA-signature-based placeholder proof system and honest audit status.

If any call returns different data than the proof committed to, the rolling hash check fails and the entire entry reverts. You get the execution you proved, or you get nothing — no partial states, no stuck funds.

:::info
The rolling hash check (`require(_rollingHash == entry.rollingHash)`) is the on-chain attestation that every call happened exactly as simulated. A single byte of unexpected return data changes the hash and reverts the whole entry.
:::

## Flat Sequential Execution

Rather than discovering a tree of nested cross-chain calls at runtime, EEZ pre-records each level of the execution tree as its own flat array, run to completion by its own frame. The entry's own top-level calls live in one array (`l2ToL1Calls[]` on L1); reentrant callbacks — calls that a destination contract on one rollup makes back to a contract on another — are pre-recorded as rows in the unified `expectedL1ToL2Calls[]` table, and each row carries its **own** sub-call array rather than sharing the entry's. There is no global flat-call cursor or `callCount` partition tying these arrays together: a reentrant row is matched by content-addressing it against the live rolling hash at the moment it fires, and its resolver simply runs its own array start to finish. This design still eliminates runtime discovery of call structure — the protocol never has to figure out what comes next, it only has to verify that what came next matches what was promised — without requiring every frame to share one global array or cursor.

## Practical Use Cases

**Cross-rollup flash loans**: Borrow on rollup A, use the funds on rollup B, repay on rollup A — all within a single L1 block. Because atomicity is guaranteed, the flash loan provider can trust that the repayment will occur; if it doesn't, the entire execution reverts.

**Atomic multi-chain DeFi**: Execute an arbitrage that spans a DEX on rollup A and a lending market on rollup B in one transaction. If the second leg fails, the first leg reverts automatically — no partial fills, no bad debt.

**Cross-rollup governance**: A DAO on L1 can atomically read the vote tally from a rollup and execute a proposal, with the guarantee that the tally reflects a specific committed rollup state.

**Synchronized liquidity**: A liquidity manager can atomically rebalance positions across multiple rollups in a single L1 block, treating the multi-chain liquidity pool as a single coherent system.

:::note
All cross-chain interactions must be consumed in the same L1 block they are posted. EEZ enforces this with a per-rollup `lastVerifiedBlock` guard: any attempt to replay an entry from a prior block reverts with `ExecutionNotInCurrentBlock`. This constraint is what makes the atomicity guarantee meaningful — there is no race condition across blocks.
:::
