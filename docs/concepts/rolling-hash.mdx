EEZ replays pre-computed execution off-chain — but how does the on-chain contract know the replay matches what the proof committed to? The answer is the rolling hash: a single `bytes32` accumulator that folds every call result and every reentrant frame boundary into one value. If anything diverges from the simulation — wrong return data, an extra call, a missing callback, even a single flipped bit — the final hash changes and the entry reverts.

## What the Rolling Hash Is

The rolling hash is a transient `bytes32` value that starts at zero at the beginning of each execution entry and gets updated at four points during execution. After all calls complete, EEZ checks that the accumulator matches the entry's committed hash and reverts the entire entry if it doesn't.

The committed hash was computed during off-chain simulation and covered by the proof. Any deviation between the simulation and the on-chain replay changes the final accumulator value, so the check fails.

Both the L1 and L2 managers share the same rolling-hash machinery — the tag constants and fold helpers live on the shared `EEZBase` contract, not on either chain's manager individually.

## The Four Tagged Events

Every accumulator update fires at one of four points, each carrying a distinct tag so that different kinds of events can never produce colliding hashes:

- **Call begin** — folded in _before_ each call is executed. Carries the 1-indexed global call number. Committing the call number up front is what prevents an attacker from reordering calls to produce a different outcome while preserving individual return values.
- **Call end** — folded in _after_ each call returns. Carries the call number, a `success` boolean, and the **full** return-or-revert data. This is where wrong return data, a mismatched success flag, or truncated/padded output are caught.
- **Nested begin** — folded in _before_ a reentrant callback frame starts. Carries the 1-indexed count of reentrant calls consumed so far.
- **Nested end** — folded in _after_ the reentrant frame finishes. The begin/end pair brackets every reentrant frame; any change to nesting depth (missing, extra, or mistimed callback) shifts the sequence and causes a mismatch.

<details>
<summary>For builders: exact tag constants, helpers, and error name</summary>

The tag constants are protocol constants defined in `EEZBase`:

```solidity
// From src/base/EEZBase.sol
uint8 internal constant CALL_BEGIN   = 1;
uint8 internal constant CALL_END     = 2;
uint8 internal constant NESTED_BEGIN = 3;
uint8 internal constant NESTED_END   = 4;
```

Each event is folded into `_rollingHash` via one of four helpers:

```solidity
function _rollingHashCallBegin(uint256 callNumber) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, CALL_BEGIN, callNumber));
}

function _rollingHashCallEnd(uint256 callNumber, bool success, bytes memory retData) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, CALL_END, callNumber, success, retData));
}

function _rollingHashNestedBegin(uint256 nestedNumber) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, NESTED_BEGIN, nestedNumber));
}

function _rollingHashNestedEnd(uint256 nestedNumber) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, NESTED_END, nestedNumber));
}
```

At the end of every entry, EEZ enforces:

```solidity
if (_rollingHash != entry.rollingHash) revert RollingHashMismatch();
```

The domain tag bytes prevent an event of one kind from hashing identically to an event of another (e.g., a `CALL_END` for call #2 vs. a `NESTED_BEGIN` for frame #2).

</details>

## The Call Number Is Live, Not Captured

Both `callNumber` arguments — the one folded at call-begin and the one folded at call-end — come from the **same** global cursor (`_currentL2ToL1Call` on L1, `_currentIncomingCall` on L2), read fresh each time. The call processor does not save the cursor's value at call-begin and reuse it at call-end.

This matters because the cursor keeps advancing while a call is in flight. If executing a call triggers a reentrant callback, that callback's own sub-calls consume further positions in the same flat array — advancing the cursor — *before* control returns to finish the outer call. The outer call's `CALL_END` then folds in whatever the cursor reads at that later point, which is higher than the number it started with.

This is a corollary of the flat-call model, not a special case: `entry.l2ToL1Calls[]` is a single array walked by one shared cursor, and reentrant frames borrow that same cursor rather than getting one of their own (see [Build ExecutionEntry Structs](/guides/build-execution-entries#computing-the-rollinghash) for the full walkthrough). Getting this wrong — assuming the outer call's `CALL_END` reuses its `CALL_BEGIN` number — is the single most common way to hand-build an incorrect `rollingHash`.

## A Worked Example

Consider an entry with three top-level calls, where the **first** call triggers a reentrant callback that processes two sub-calls:

- Top-level frame: c0, c3, c4 (three iterations, `entry.callCount = 3`).
- Reentrant frame (fires during c0): c1, c2 (two iterations, `expectedL1ToL2Calls[0].callCount = 2`).
- Flat call array totals five: c0, c1, c2, c3, c4.

The event sequence — and therefore the hash chain — looks like this: call-begin(c0) → nested-begin → call-begin(c1) → call-end(c1) → call-begin(c2) → call-end(c2) → nested-end → call-end(c0) → call-begin(c3) → call-end(c3) → call-begin(c4) → call-end(c4).

Because the shared cursor has already advanced to 3 by the time c0's callback returns, c0's own `call-end` folds in call number **3** — not the `1` it was tagged with at `call-begin`. The hash captures the full nesting structure, including exactly how far the cursor moved during the nested frame, not just the call order.

<details>
<summary>For builders: exact hash chain</summary>

```text
H0  = 0x0                                             (initial)
H1  = keccak256(H0,  CALL_BEGIN,   callNum=1)         (c0 starts, cursor 0→1)
H2  = keccak256(H1,  NESTED_BEGIN, nestedNum=1)       (reentrant fires during c0)
H3  = keccak256(H2,  CALL_BEGIN,   callNum=2)         (c1 starts, cursor 1→2)
H4  = keccak256(H3,  CALL_END,     callNum=2, true, retData_1)
H5  = keccak256(H4,  CALL_BEGIN,   callNum=3)         (c2 starts, cursor 2→3)
H6  = keccak256(H5,  CALL_END,     callNum=3, true, retData_2)
H7  = keccak256(H6,  NESTED_END,   nestedNum=1)       (reentrant frame closes)
H8  = keccak256(H7,  CALL_END,     callNum=3, true, retData_0)   (c0 returns — cursor is 3, not 1)
H9  = keccak256(H8,  CALL_BEGIN,   callNum=4)         (c3 starts, cursor 3→4)
H10 = keccak256(H9,  CALL_END,     callNum=4, true, retData_3)
H11 = keccak256(H10, CALL_BEGIN,   callNum=5)         (c4 starts, cursor 4→5)
H12 = keccak256(H11, CALL_END,     callNum=5, true, retData_4)

require(H12 == entry.rollingHash)                     // else RollingHashMismatch
```

Entry layout:

```text
entry.l2ToL1Calls         = [c0, c1, c2, c3, c4]
entry.callCount            = 3
entry.expectedL1ToL2Calls = [{ callCount: 2, returnData: retData_1_and_2_owner }]
```

This exact pattern — the outer call's `CALL_END` folding in the cursor value *after* the nested frame advanced it — is exercised by the protocol's own end-to-end fixtures (`script/e2e/deepNested/E2E.s.sol` builds its own hash chain with `RollingHashBuilder` around a different call structure — a single top-level call with two *nested* levels of depth, rather than this page's three top-level calls with one nested frame of two siblings — but it hits the same mechanism: the outer call's `CALL_END` tags with the post-nesting cursor value, not its own `CALL_BEGIN` number).

</details>

## How It Prevents Tampering

The rolling hash makes three guarantees simultaneously:

**Wrong return data**: If a call returns `0xdeadbeef` instead of the committed `0xabcdef`, `CALL_END` folds the actual `retData` into the accumulator. The hash diverges from `entry.rollingHash` immediately after that call and the entry reverts.

**Wrong success flag**: If a call that was simulated as reverting unexpectedly succeeds (or vice versa), the `success` bool in `CALL_END` changes. The hash diverges.

**Wrong nesting structure**: If a reentrant callback fires one step later than expected, the positions of `NESTED_BEGIN` and `CALL_END` swap in the sequence — and because `CALL_END`'s call number is read live, any change in how far the cursor moved during nesting changes that number too. Every subsequent hash step produces a different value.

A hash-check failure is the terminal signal for all of these cases. It reverts the entire entry — not just the diverging call — preserving the atomicity guarantee.

## Rolling Hash and `revertSpan`

When a call is wrapped in a `revertSpan`, EEZ executes the calls inside the span normally — hashing call-begin and call-end for each — then unconditionally reverts the span's state changes via a self-call to `executeInContextAndRevert`, which always reverts with `error ContextResult(bytes32 rollingHash, uint256 reentrantConsumed, uint256 callsProcessed, bool callNotFound)`. The rolling hash and cursors computed *inside* the span escape through that revert payload and are re-applied by the caller, so the outer execution's rolling hash reflects that the spanned calls happened, even though the EVM rolled back their state effects. See [Build ExecutionEntry Structs](/guides/build-execution-entries#revertspan-forced-revert-context) for the full mechanics of when to reach for `revertSpan`.

:::info
The lookup sub-hash on `ExpectedLookup` and `LookupCall` structs is dual-schema, verified against a separate `rollingHash` field on the lookup itself: it uses the untagged schema in static mode — a deliberately simpler formula of one keccak fold per static sub-call, with no tags and no call numbers — and the same tagged entry schema as regular execution in reverted mode. The untagged static formula is distinct from the entry-level rolling hash: it serves a narrower purpose and is safe because the lookup's match key already pins the call context that the tagged events disambiguate at the entry level.
:::

## Troubleshooting a Mismatch

If the on-chain execution diverges from what the proof committed to, the entry reverts with a rolling-hash mismatch. Common causes:

- A destination contract's state has changed between proof generation and execution, causing it to return different data.
- The batch was built against a different state root than what is currently committed on-chain.
- A builder assumed a reentrant-triggering call's `CALL_END` reuses its `CALL_BEGIN` call number, instead of the cursor value live at the moment the call returns (see above).
- A bug in the off-chain prover produced an incorrect committed hash.

In all cases, the correct response is to re-simulate the execution against the current state and generate a new batch.
