EEZ replays pre-computed execution off-chain — but how does the on-chain contract know the replay matches what the proof committed to? The answer is the rolling hash: a single `bytes32` accumulator that seeds from the entry's starting state and identity, then folds every call result and every reentrant frame boundary into one value. If anything diverges from the simulation — wrong return data, an extra call, a missing callback, even a single flipped bit — the final hash changes and the entry reverts.

## What the Rolling Hash Is

The rolling hash is a transient `bytes32` value. Between entries it sits at `bytes32(0)` — the EVM's default for transient storage — but the first thing that happens when an entry begins is `_rollingHashEntryBegin`, which **seeds** it to a non-zero value derived from the entry's per-rollup state deltas and its identity hash. Everything that follows folds on top of that seed, not on top of zero.

After all calls complete, EEZ checks that the accumulator matches the entry's committed `rollingHash` and reverts the entire entry if it doesn't:

```solidity
if (_rollingHash != entry.rollingHash) revert RollingHashMismatch();
```

The committed hash was computed during off-chain simulation and covered by the proof. Any deviation between the simulation and the on-chain replay changes the final accumulator value, so the check fails.

Both the L1 and L2 managers share the same rolling-hash machinery — the tag constants and fold helpers live on the shared `EEZBase` contract, not on either chain's manager individually.

## Seeding: Binding State and Identity Before Any Call Runs

```solidity
// From src/base/EEZBase.sol
function _rollingHashEntryBegin(StateUpdate[] memory deltas, bytes32 proxyEntryHash) internal {
    if (_rollingHash != bytes32(0)) revert RollingHashNotCleared();

    bytes32 rollupStatesHash;
    for (uint256 i = 0; i < deltas.length; i++) {
        rollupStatesHash = keccak256(abi.encodePacked(rollupStatesHash, deltas[i].rollupId, deltas[i].currentState));
    }
    _rollingHash = keccak256(abi.encodePacked(rollupStatesHash, proxyEntryHash));
}
```

Two things get folded in before a single call runs:

- **`rollupStatesHash`** — an ordered fold over the entry's `StateUpdate[]` deltas (`rollupId`, `currentState` pairs), one per rollup this entry touches. This ties the hash to the exact pre-state the entry was simulated against.
- **`proxyEntryHash`** — the entry's own identity: the `crossChainCallHash` of the inbound call that produced it (`bytes32(0)` for an L2 transaction with no inbound proxy call).

`_rollingHash != bytes32(0)` at this point means a prior entry left the accumulator un-reset, and the call reverts with `RollingHashNotCleared` rather than silently seeding on top of stale state. (The accumulator is cleared back to zero at the end of every entry, success or revert, so this should never fire in correct execution.)

The upshot: two entries with identical calls but different starting state, or different inbound identities, produce different rolling hashes from the very first fold — the hash isn't just "what happened," it's "what happened, starting from this exact state, in response to this exact call."

## The Five Tagged Events

Every subsequent accumulator update fires at one of five points, each carrying a distinct tag so that different kinds of events can never produce colliding hashes:

- **Call begin** — folded in _before_ each call is dispatched. Carries the call's **identity hash** (`crossChainCallHash`), not a position or counter.
- **Call end** — folded in _after_ each call returns. Carries a `success` boolean and the **full** return-or-revert data. This is where wrong return data, a mismatched success flag, or truncated/padded output are caught.
- **Nested begin** — folded in _before_ a reentrant callback frame starts. Carries the reentrant call's identity hash, same as call-begin.
- **Nested end** — folded in _after_ a successfully-committing reentrant frame finishes. No arguments — the frame's content was already bound going in (identity) and throughout (its own calls' begin/end folds).
- **Call not found** — folded in when a reentrant call has no matching row in the expected-calls table. Carries the identity hash of the call that couldn't be matched.

```solidity
// From src/base/EEZBase.sol
uint8 internal constant CALL_BEGIN = 1;
uint8 internal constant CALL_END = 2;
uint8 internal constant NESTED_BEGIN = 3;
uint8 internal constant NESTED_END = 4;
uint8 internal constant CALL_NOT_FOUND = 5;
```

Each event is folded into `_rollingHash` via one of five helpers:

```solidity
function _rollingHashCallBegin(bytes32 crossChainCallHash) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, CALL_BEGIN, crossChainCallHash));
}

function _rollingHashCallEnd(bool success, bytes memory retData) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, CALL_END, success, retData));
}

function _rollingHashNestedBegin(bytes32 crossChainCallHash) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, NESTED_BEGIN, crossChainCallHash));
}

function _rollingHashNestedEnd() internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, NESTED_END));
}

function _rollingHashCallNotFound(bytes32 crossChainCallHash) internal {
    _rollingHash = keccak256(abi.encodePacked(_rollingHash, CALL_NOT_FOUND, crossChainCallHash));
}
```

<details>
<summary>For builders: why `CALL_NOT_FOUND` exists</summary>

If a reentrant call fires and the unified expected-calls table has no row matching its position key (see below), the protocol does **not** revert immediately. Instead it folds `CALL_NOT_FOUND(crossChainCallHash)` into the accumulator and returns empty bytes to the caller — the divergence is caught later, at the entry's final `RollingHashMismatch` check. This matters because the no-match can occur deep inside a `try/catch` or a `revertSpan`, and the tag needs to survive that unwind. `CALL_NOT_FOUND` is a distinct tag from `CALL_END(true, "")` (what a normal empty-return call folds), so a prover can't disguise a not-found as an ordinary empty return.

</details>

The domain tag bytes prevent an event of one kind from hashing identically to an event of another (e.g., a `CALL_END` for one call vs. a `NESTED_BEGIN` for a reentrant frame that happens to share an identity hash by coincidence — which itself can't happen, since identity hashes already differ by `isStatic`/source/target/value/data).

## Calls Are Bound By Identity, Not Position

There is no call counter and no shared cursor folded into the hash at all. `CALL_BEGIN` and `NESTED_BEGIN` both carry `crossChainCallHash` — the call's full identity, computed the same way everywhere in the protocol:

```solidity
function computeCrossChainCallHash(
    bool isStatic,
    address sourceAddress,
    uint64 sourceRollupId,
    address targetAddress,
    uint64 targetRollupId,
    uint256 value,
    uint64 callGas,
    bytes memory data
) public pure returns (bytes32);
```

No index is folded in anywhere because the accumulator is already a **chain** — each fold depends on the prior value, so order, count, and nesting depth are already bound by the sequence itself. An explicit `1, 2, 3, …` counter would add no information, and it would actively break `revertSpan`, which needs to process a force-reverted slice of calls as a self-contained 0-based run without diverging the hash from what a continuous execution would have produced.

This identity-based design also replaces how reentrant callbacks get matched. Instead of a shared position cursor, every row in the unified expected-calls table (`ExpectedL1ToL2Call` on L1, `ExpectedOutgoingCrossChainCall` on L2) is content-addressed by:

```
expectedL1toL2Hash = keccak256(abi.encodePacked(crossChainCallHash, expectedRollingHash))
```

`expectedRollingHash` is simply `_rollingHash` at the instant the reentrant call fires — because the chain already folds every prior call and nesting boundary, that single value uniquely pins the execution point. No cursor coordinates, no context index, no call-number bookkeeping: two textually identical calls fired at two different points in execution key differently, because `_rollingHash` differs between them. See [Static Entries](/guides/lookup-calls) for the full mechanics of this position key, including how a static (read-only) call keys distinctly from an otherwise-identical state-changing one via `isStatic`.

Each row in that table also carries its **own** `l2ToL1Calls[]` sub-array, run to completion by its own frame — there's no longer a single flat array shared between the top-level entry and its nested frames. A reentrant frame's calls are folded between that frame's `NESTED_BEGIN`/`NESTED_END`, entirely separate from the entry's own top-level call array.

## A Worked Example

Consider an entry with three top-level calls — call **A**, call **B**, call **C** — where **A** triggers a reentrant callback with its own two-call sub-array — call **X**, call **Y**:

- `entry.l2ToL1Calls = [A, B, C]` — the entry's own top-level calls.
- The reentrant row matched during A's dispatch carries `l2ToL1Calls = [X, Y]` as **its own** sub-array (not shared with the entry's array).

Let `hA`, `hB`, `hC`, `hX`, `hY` denote each call's `crossChainCallHash`. The event sequence — and therefore the hash chain — looks like this:

```text
H0  = 0x0                                                (transient default, pre-seed)
H1  = keccak256(rollupStatesHash, proxyEntryHash)         (_rollingHashEntryBegin — the seed)
H2  = keccak256(H1, CALL_BEGIN,   hA)                     (A dispatched)
H3  = keccak256(H2, NESTED_BEGIN, hX)                     (reentrant callback fires during A; matched row's identity is hX)
H4  = keccak256(H3, CALL_BEGIN,   hX)                     (X starts, inside the reentrant frame)
H5  = keccak256(H4, CALL_END,     true, retX)
H6  = keccak256(H5, CALL_BEGIN,   hY)                     (Y starts)
H7  = keccak256(H6, CALL_END,     true, retY)
H8  = keccak256(H7, NESTED_END)                           (reentrant frame closes — success row)
H9  = keccak256(H8, CALL_END,     true, retA)             (A returns, now that its callback resolved)
H10 = keccak256(H9,  CALL_BEGIN,  hB)
H11 = keccak256(H10, CALL_END,    true, retB)
H12 = keccak256(H11, CALL_BEGIN,  hC)
H13 = keccak256(H12, CALL_END,    true, retC)

require(H13 == entry.rollingHash)                         // else RollingHashMismatch
```

The reentrant row that satisfies `NESTED_BEGIN(hX)` is matched by its position key `keccak256(hX, H2)` — `H2` is `_rollingHash` at the exact instant the callback fires (right after `A`'s `CALL_BEGIN`, before `A`'s own `CALL_END`). Nothing about the outer call's own identity or count needs to be captured or replayed later; the nested frame's identity and the live hash at fire-time are the entire match key.

<details>
<summary>For builders: nesting still shows up in structure, not in a number</summary>

Compare this to the removed call-number scheme: there, the outer call's `CALL_END` had to reuse a *cursor value* that had moved on during the nested frame, and getting that number right required tracking how far a shared cursor advanced. In the current model there's no cursor to track — `A`'s `CALL_END` at `H9` folds only `(true, retA)`, with no position argument at all. The nesting is captured entirely by *where* `NESTED_BEGIN`/`NESTED_END` sit in the sequence and by each nested call's own identity hash, not by a number computed from cursor arithmetic.

</details>

## How It Prevents Tampering

The rolling hash makes four guarantees simultaneously:

**Wrong return data**: If a call returns `0xdeadbeef` instead of the committed `0xabcdef`, `CALL_END` folds the actual `retData` into the accumulator. The hash diverges from `entry.rollingHash` immediately after that call and the entry reverts.

**Wrong success flag**: If a call that was simulated as reverting unexpectedly succeeds (or vice versa), the `success` bool in `CALL_END` changes. The hash diverges.

**Wrong call identity or nesting structure**: If a different call fires than the one that was proven — wrong target, wrong source, wrong calldata, a callback at the wrong moment — its `crossChainCallHash` differs, so `CALL_BEGIN`/`NESTED_BEGIN` fold a different value than expected. Every subsequent hash step produces a different value.

**A reentrant call the table didn't expect**: If a callback fires that has no matching row in the expected-calls table — because the prover never simulated it, or it fired at a different execution point than proven — the mismatch doesn't revert on the spot. `CALL_NOT_FOUND(crossChainCallHash)` folds into the accumulator instead, and the divergence is caught at the entry's final check, even if the no-match happened inside a `try/catch` or a `revertSpan`.

A hash-check failure is the terminal signal for all of these cases. It reverts the entire entry — not just the diverging call — preserving the atomicity guarantee.

## Rolling Hash and `revertSpan`

When a call is wrapped in a `revertSpan`, EEZ executes the calls inside the span normally — hashing call-begin and call-end for each — then unconditionally reverts the span's state changes via a self-call to `executeInContextAndRevert`, which always reverts with `error ContextResult(bytes32 rollingHash, uint256 reentrantConsumed, uint256 callsProcessed)`. The rolling hash and cursors computed *inside* the span escape through that revert payload and are re-applied by the caller, so the outer execution's rolling hash reflects that the spanned calls happened, even though the EVM rolled back their state effects. A `CALL_NOT_FOUND` fold that occurred inside the span rides out the same way — it's already baked into `rollingHash`, so no separate flag is needed on `ContextResult`. See [Build ExecutionEntry Structs](/guides/build-execution-entries) for more on when to reach for `revertSpan`.

:::info
There is no separate "lookup" struct anymore. A reentrant static read or a pre-verified reverting reentrant call is just another row of the same unified expected-calls table used for successful reentrant calls (`ExpectedL1ToL2Call` on L1) — distinguished by `isStatic` folded into its position key and by its own `success` flag, not by a dedicated struct. Only a **top-level** static read (outside any execution) gets its own struct, `StaticExecutionEntry`. Static rows and static entries are verified against a separate, **untagged** rolling-hash field (`revertedOrStaticRollingHash` on a row, `rollingHash` on a top-level entry) — a simpler `keccak256(prev, success, retData)` fold per sub-call, seeded at `bytes32(0)`, with no tags and no identity hashes. That untagged formula is distinct from the entry-level rolling hash described on this page: it's safe because the surrounding position key already pins the execution context that the tagged events disambiguate at the entry level. See [Static Entries](/guides/lookup-calls) for the full read-path mechanics.
:::

## Troubleshooting a Mismatch

If the on-chain execution diverges from what the proof committed to, the entry reverts with a rolling-hash mismatch. Common causes:

- A destination contract's state has changed between proof generation and execution, causing it to return different data.
- The batch was built against a different state root than what is currently committed on-chain.
- A builder computed a call's `crossChainCallHash` with the wrong field ordering or a mismatched `isStatic` flag, producing a hash that never matches the on-chain replay.
- A reentrant callback fired at a different point in execution than the prover simulated, so its position key (`crossChainCallHash` + live `_rollingHash` at fire-time) never matches any row — folding `CALL_NOT_FOUND` instead of the expected `NESTED_BEGIN`/`NESTED_END` pair.
- A bug in the off-chain prover produced an incorrect committed hash.

In all cases, the correct response is to re-simulate the execution against the current state and generate a new batch.
