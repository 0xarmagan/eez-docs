EEZ is built around a two-sided contract architecture: a central L1 registry and a lightweight per-rollup L2 manager, bridged by a deterministic `CrossChainProxy` that gives every cross-chain address a stable on-chain identity.

Every cross-rollup call goes through three stages: prove and queue off-chain, then execute on L1 and L2 in the same block, linked by synchronous composability. `EEZ.postAndVerifyBatch()` verifies the proof and queues the entry; `EEZ.executeCrossChainCall()` checks the hash and applies the state delta — see [Execution flow: a complete example](#execution-flow-a-complete-example) below for the step-by-step breakdown.

## Contract overview

The following table shows the main contracts, where they live, and their primary responsibility:

| Contract | Chain | Responsibility |
| --- | --- | --- |
| `EEZ.sol` | L1 | Central registry: rollup state roots, ether accounting, batch verification, per-rollup execution queues |
| `EEZL2.sol` | L2 | System-driven execution: receives tables from the sequencer, executes incoming cross-chain calls |
| `EEZBase.sol` | Both | Shared base: rolling-hash accumulator, proxy registry, CREATE2 proxy creation, revert-transport helpers |
| `Rollup.sol` | L1 | Per-rollup manager: proof systems, verification keys, M-of-N threshold, ownership, state-root escape hatch |
| `CrossChainProxy.sol` | Both | Deterministic proxy: routes inbound calls to the manager, forwards outbound calls on behalf of the original address |

## The L1 EEZ contract

`EEZ.sol` is the heart of the protocol. It maintains two mappings for each registered rollup: `rollups[rollupId]` (a `RollupConfig` with the manager address, current state root, and ETH balance) and `verificationByRollup[rollupId]` (a `RollupVerification` holding the per-rollup execution queue (`entryQueue`), static entry queue (`staticEntryQueue`), consumption cursor (`entryQueueIndex`), and the `lastVerifiedBlock` marker).

### Rollup registration

Anyone can register a rollup by calling `registerRollup(rollupContract, initialStateRoot)`. The caller pre-deploys a `Rollup.sol`-conforming manager, then passes its address to the registry. The registry assigns a fresh rollup ID (starting at 1; ID 0 is the reserved `MAINNET_ROLLUP_ID`) and calls `rollupContractRegistered(rollupId)` on the manager once as a one-shot initialisation callback. After registration the manager is immutable in the registry — you cannot swap it out.

### Batch posting and verification

`postAndVerifyBatch` is the primary entry point for the off-chain sequencer. It accepts a `ProofSystemBatchPerVerificationEntries` struct that packages together:

- The array of `ExecutionEntry` structs to verify (`entries`)
- The array of `StaticExecutionEntry` structs for top-level static reads and reverting top-level calls (`staticEntries`)
- `immediateEntryCount` and `immediateStaticEntryCount`, which control how many leading `entries` / `staticEntries` run immediately (straight from calldata, or via the meta hook) versus get published to the persistent per-rollup queues
- The ordered list of proof system addresses and one proof per proof system
- Per-rollup proof system assignments (which rollup accepts which subset of proof systems)
- An optional `blockNumber` that binds the batch to a specific L1 block's context
- `expectedStateRootPerRollup`, an optional composer-supplied list of state-root assertions checked against each pinned rollup's live root before anything else runs — any mismatch reverts the whole batch
- `bindMsgSenderInPublicInput`, a bool that folds `msg.sender` into the batch's public input when `true` (only the original submitter can land the batch — front-run protection) or `address(0)` when `false` (anyone may submit it)

Verification is atomic: all proofs must pass or the batch reverts. On success, EEZ marks each participating rollup as verified this block, dispatches the leading transient entries into an in-memory stream (drained inline and via the meta hook), and pushes the remainder into per-rollup persistent queues. See [Post Batch](/spec/core-protocol/b-protocol-functions) for the full 8-step pipeline, struct fields, and error table.

### Execution queues: transient and deferred

EEZ maintains two tiers of execution entries per batch:

**Transient entries** are loaded into `_transientEntries` (and `_transientStaticEntries` for static reads) during `postAndVerifyBatch` and are only consumable within that same call. They are the fast path for high-priority cross-chain calls — the meta hook fires in step 7 and the caller can consume all transient entries through proxy calls in the same transaction. At the end of `postAndVerifyBatch` the transient tables are deleted.

**Deferred (persistent) entries** are pushed into `verificationByRollup[rollupId].entryQueue` (and static reads into `staticEntryQueue`) in step 9. These are consumed in separate transactions later in the same L1 block via `executeCrossChainCall` (for proxy-triggered entries with a non-zero `proxyEntryHash`) or `executeL2Txs(rollupId)` (for system-driven entries with `proxyEntryHash == bytes32(0)`). The `lastVerifiedBlock` gate ensures no entry survives past the block it was posted in — if it isn't consumed before the block ends, it becomes unreachable.

### Per-rollup isolation

Each rollup's queue is fully independent — a `postAndVerifyBatch` for rollup A does not interfere with rollup B's queue. But queue isolation and the reentry lock are two different mechanisms:

- **Queues can interleave.** The meta hook may consume entries from multiple rollups in a single transaction by calling through their respective proxies. Each such consumption is a **fresh top-level call**: during the meta-hook window (between proxy calls), `_insideExecution()` is false, so `executeCrossChainCall` takes its top-level branch and routes to `_consumeAndExecuteEntry`.
- **Nested calls route separately.** Pre-computed reentrant/nested calls occur *within* a single entry's execution (when `_insideExecution()` is true) and route through `_consumeNestedCall` instead.
- **The reentry lock is global, not per-rollup.** `_insideExecution()` returns `_verifiedRollupInCurrentExecutingEntry.length != 0` — a plain **storage** array (not a transient variable), populated by `_executeEntry` with the current entry's touched rollup IDs and `delete`d when the entry finishes (a revert unwinds the pushes with it, restoring the array). While any entry (for any rollup) is mid-execution, `executeL2Txs` explicitly reverts (`L2TXNotAllowedDuringExecution`) on a fresh top-level call for *any* rollup; `executeCrossChainCall` instead reroutes such a call into the reentrant-table resolution path, where it fails to match unless it's a genuine pre-computed reentrant call belonging to the entry currently executing.

## The L2 EEZL2 contract

`EEZL2.sol` is deliberately simpler than its L1 counterpart. It has no rollup registry, no state delta accounting, and no proof verification — all of that responsibility sits on L1. The L2 contract's only job is to execute the execution tables that the system address loads into it.

The L2 contract is constructed with two immutables: `ROLLUP_ID` (the rollup's ID in the L1 registry) and [`SYSTEM_ADDRESS`](/spec/core-protocol/i-security-considerations). Only `SYSTEM_ADDRESS` can call `loadExecutionTable` or `executeIncomingCrossChainCall`.

**`loadExecutionTable(entries, staticEntries)`** wipes the existing table and loads fresh entries. Entries are only consumable in the same block they were loaded (`lastLoadBlock == block.number`). After that block, the table is unreachable until the next `loadExecutionTable` call.

**`executeIncomingCrossChainCall(destination, value, data, sourceAddress, sourceRollup, entries, staticEntries)`** is the atomic path: the system address replaces the entire execution table and drives the first entry's call in one transaction. `entries[0].incomingCalls[0]` is the inbound call itself. Any ETH attached as `msg.value` must strictly equal the `value` parameter (`ValueMismatch` reverts otherwise) — this is the **mint** path: the system mints `value` on L2 by attaching it, and that ETH lives in the manager balance until it is drawn down when the entry forwards it through the source proxy. The reverse **burn** path — forwarding `msg.value` back to `SYSTEM_ADDRESS` — lives in `executeCrossChainCall`, not here.

The L2 struct vocabulary is self-relative rather than absolute: `incomingCalls` (calls executed on this L2) and `expectedOutgoingCalls` (pre-computed results of reentrant calls leaving this L2). This naming is intentional — an L2's counterpart can be L1 or another L2, so absolute names like `l1Calls` would frequently be wrong.

## CrossChainProxy: deterministic cross-chain identity

A `CrossChainProxy` is a CREATE2 contract that represents exactly one `(originalAddress, rollupId)` pair. It is the only way to trigger an execution entry on L1 (other than `executeL2Txs` for system-driven entries). When the proxy receives a call, it forwards to `EEZ.executeCrossChainCall` for a normal (state-changing) call, or `EEZ.staticCrossChainCall` when it detects a `STATICCALL` context, and the EEZ contract routes to the matching execution entry using the computed `crossChainCallHash`.

You create a proxy by calling `createCrossChainProxy(originalAddress, rollupId)` on the EEZ contract. The address is a deterministic CREATE2 hash of `(originalRollupId, originalAddress, manager)` — see [Cross-Chain Proxy](/spec/core-protocol/b-protocol-functions) for the exact formula. Two key properties follow: the address is **fully deterministic** (computable offline via `computeCrossChainProxyAddress`) and **manager-scoped** (the same `(originalAddress, rollupId)` pair on two different EEZ deployments produces different proxy addresses).

The cross-chain call hash used to match entries in the execution queue (and static entries in the static-entry pool) is computed by `computeCrossChainCallHash`, available as a `pure` function on both the L1 `EEZ` and L2 `EEZL2` managers (inherited from the shared `EEZBase`):

```solidity
function computeCrossChainCallHash(
    bool isStatic,
    address sourceAddress,
    uint64 sourceRollupId,
    address targetAddress,
    uint64 targetRollupId,
    uint256 value,
    uint64 callGas,
    bytes memory data
) public pure returns (bytes32) {
    return keccak256(
        abi.encode(isStatic, sourceAddress, sourceRollupId, targetAddress, targetRollupId, value, callGas, data)
    );
}
```

`isStatic` keys a read-only call distinctly from a state-changing one with otherwise-identical parameters — a call and a read to the same target can never collide. `callGas` is folded as `0` on every path except calls leaving an L2 with `USE_GAS_LEFT`; a plain read always keys `callGas = 0` too.

:::warning
Off-chain tooling must use this exact encoding — all 8 fields, in this order, via `abi.encode` (not `abi.encodePacked`) — when pre-computing entry hashes to match against `entry.proxyEntryHash`.
:::

Static context detection (for read-only cross-chain calls) uses the EIP-1153 `tstore` / `tload` asymmetry: the proxy attempts a `tstore` in a self-call; if the self-call reverts, the proxy is inside a `STATICCALL` and routes to `staticCrossChainCall` instead of `executeCrossChainCall`. `staticCrossChainCall` is unified across both call sites it can resolve from: fired *inside* an executing entry, it matches against that entry's own reentrant table (content-addressed by `crossChainCallHash` + the live rolling hash); fired at the *top level*, it matches against a `StaticExecutionEntry` in the transient pool (mid-batch) or the calling rollup's persistent `staticEntryQueue` (matched by `proxyEntryHash`, destination rollup, and — on L1 only — a set of state-root pins that bound the read's freshness). There is no longer a separate "lookup" struct or code path — see `docs/STATIC_ENTRY.md` in `eez-core-protocol` for the full mechanism.

## Per-rollup Rollup.sol manager

`Rollup.sol` is the reference per-rollup management contract. Each rollup operator deploys one and registers it with EEZ. The manager holds:

- **Proof systems**: a mapping of `proofSystem => verificationKey`. Only non-zero vkeys are allowed. The owner adds proof systems with `addProofSystem` and removes them with `removeProofSystem`.
- **Threshold**: the M-of-N minimum number of proof systems that must attest to a batch for it to be accepted. A threshold above the current PS count locks the rollup until more proof systems are added.
- **Custom data**: `getCustomData(blockNumber)` returns an opaque blob that the EEZ registry folds into the batch's public inputs hash, binding the proof to a specific L1 block context. The returned blob depends on `blockNumber`:

  | `blockNumber` | Returned blob |
  | --- | --- |
  | `0` (no L1 context sentinel) | Empty blob |
  | `type(uint64).max` (latest-block sentinel) | ABI-encoded `(uint256 timestamp, bytes32 blockHash)` — current block's `block.timestamp` and previous block's `blockhash` |
  | A specific block within the most recent 256 blocks | `(0, blockHash)` from `blockhash(blockNumber)` |
  | A specific block outside that 256-block window (or the current/future block) | Reverts `BlockHashUnavailable` — never silently binds a zero hash |

- **State root escape**: `setStateRoot(newRoot)` lets the owner directly update the L1 state root outside of the proof system, subject to the registry's same-block lockout (`RollupBatchActiveThisBlock` reverts if a batch already touched the rollup this block).

The `checkProofSystemsAndGetVkeys(proofSystems[])` function is called by EEZ during `postAndVerifyBatch`. It enforces the threshold, rejects any unknown proof system, and returns the verification key for each proof system in the submitted subset. This is a `STATICCALL` from EEZ — the manager cannot mutate state during proof verification.

## Multi-prover model

EEZ supports multiple independent proof systems attesting to the same batch. A batch carries a globally sorted list of proof system addresses and one proof per proof system. Each participating rollup selects the subset of proof systems it accepts via strictly-increasing indices into the global list. This allows different rollups to use different proof systems (ZK-SNARKs, ZK-STARKs, optimistic fraud proofs, or even a trusted multi-sig) while sharing the same batch and the same overhead.

The public inputs hash that each proof system verifies is constructed in two stages. First, a shared component is computed covering all entry hashes, static entry hashes, [blob hashes](/spec/blobs/blob-format), call data, and per-rollup custom data — this part is identical across all proof systems. Second, a per-proof-system component is computed from the vkeys contributed by each rollup that uses that proof system. The final `publicInputsHash[k]` for proof system `k` is `keccak256(abi.encodePacked(sharedPublicInput, perPSAccumulator[k]))`. This structure means proof systems with disjoint rollup memberships produce different public inputs, so a proof stolen from one proof system cannot be replayed against another.

## Rolling hash integrity

Every execution entry carries a `rollingHash` — a single `bytes32` that is the cumulative Keccak of all call events in execution order, verified via five tagged event types (static entries use a separate, untagged accumulator instead — see `docs/STATIC_ENTRY.md`):

| Tag | Value | Formula |
| --- | --- | --- |
| `CALL_BEGIN` | 1 | `keccak256(abi.encodePacked(prev, uint8(1), crossChainCallHash))` — folds the call's full identity hash, not a numeric call index |
| `CALL_END` | 2 | `keccak256(abi.encodePacked(prev, uint8(2), success, retData))` |
| `NESTED_BEGIN` | 3 | `keccak256(abi.encodePacked(prev, uint8(3), crossChainCallHash))` — same identity binding as `CALL_BEGIN`, for a reentrant frame |
| `NESTED_END` | 4 | `keccak256(abi.encodePacked(prev, uint8(4)))` |
| `CALL_NOT_FOUND` | 5 | `keccak256(abi.encodePacked(prev, uint8(5), crossChainCallHash))` — folded when a reentrant call has no matching row in the expected-calls table; distinct from `CALL_END(true, "")` so a no-match can't be forged as an empty successful return |

Call numbers are not part of the mechanism at all: ordering and completeness are enforced purely by chaining each call's full `crossChainCallHash` (identity) and outcome into the accumulator, not by any numeric index.

At the end of every entry, EEZ checks two invariants:

1. `_rollingHash == entry.rollingHash` — every call result and nesting boundary matched exactly, in order
2. `totalEtherDelta == _entryEtherDelta` — the net ETH flow from the entry's state deltas matches the actual ETH moved in/out across the entry and every reentrant sub-frame

There is no cursor-vs-length check and no reentrant-table-length check: the unified reentrant table mixes plain-success rows with static/reverted ones (content-addressed, so unused rows are simply inert), and completeness of the success path rests entirely on the rolling hash — a skipped success row omits its `NESTED_BEGIN`/`NESTED_END` frame and diverges the final hash.

A single mismatch anywhere — wrong return data, an extra call, a missing nesting boundary, reordered operations — changes the final hash and reverts with `RollingHashMismatch`. There is no path through which execution can diverge from the pre-committed proof and still complete successfully.

## Revert span and forced-revert execution

The `revertNextNCalls` field on each call (`L2ToL1Call` on L1, `CrossChainCall` on L2; a `uint16`) is the protocol's mechanism for expressing calls whose EVM state effects must be rolled back, regardless of whether the call itself succeeds or fails. Setting `revertNextNCalls = N` on a call causes EEZ to execute the next N calls (including the call with the non-zero `revertNextNCalls`), capture their results (success or failure) in the rolling hash, and then roll back all their EVM state changes. This is distinct from a naturally-reverting call (where `revertNextNCalls = 0` and the proxy's `.call` captures `(false, returnData)` into `CALL_END`, with no forced rollback beyond the EVM's own revert) — a `revertNextNCalls > 0` span has its state effects forcibly undone regardless of whether the wrapped call succeeded or reverted on its own.

The typical use case is a call that ran successfully on the destination chain but whose effects need to be rolled back on the source chain's view (for example, a collateral check that passed on L2 but whose side effects should not persist on L1).

## Execution flow: a complete example

The `counter` scenario in `eez-core-protocol` is the simplest complete case:
`CounterAndProxy` on L1 calls a `Counter` contract on L2 and receives the new count
back. Here is what runs on each side.

**On L1:**

1. Off-chain, the outcome is pre-computed as a single deferred `ExecutionEntry`
   carrying `returnData = abi.encode(uint256(1))` and a `RollupUpdate` that advances
   L2's state root. `postAndVerifyBatch` verifies the proof and loads it into L2's
   queue.
2. A user calls `CounterAndProxy.incrementProxy()`.
3. That calls the `CrossChainProxy` standing in for `Counter` on L2.
4. The proxy forwards to `EEZ.executeCrossChainCall`. The registry computes the
   call's `crossChainCallHash` from its seven fields — `isStatic`, source address,
   source rollup, target address, target rollup, value, and calldata — matches it
   against `entry.proxyEntryHash`, checks each `RollupUpdate`'s `currentRoot`
   against the live root, verifies the rolling hash, applies the state delta, and
   returns `entry.returnData`.
5. `CounterAndProxy` receives `1`. The registry's stored root for L2 has advanced.

Because this entry makes no top-level calls on L1, its rolling hash is just the
entry-begin seed over the state deltas and `proxyEntryHash` — there is nothing to
fold.

**On L2**, in a coordinated but independent flow, `SYSTEM_ADDRESS` calls
`EEZL2.executeIncomingCrossChainCall`, which loads the mirroring L2 entry. The
inbound call is forwarded through a lazily-created source proxy — the L2-side proxy
standing in for `CounterAndProxy` on L1 — into `Counter.increment()`. The counter
advances to 1, and the L2 entry's rolling hash folds `CALL_BEGIN` with the call's
identity followed by `CALL_END(success = true, abi.encode(uint256(1)))`.

The two halves are tied together by **content, not coordination**: both sides build
the identical `crossChainCallHash` preimage, which is what binds the L1 side's cached
`returnData` to the execution that actually happened on L2. If the L2 call had
returned anything other than `1`, its rolling hash would differ and the entry would
fail.

Both sides happen in the same L1 block. The L2 state root committed in the L1 entry's `RollupUpdate` is the ground truth — the L2 execution is the deterministic consequence of the pre-committed state transition.
