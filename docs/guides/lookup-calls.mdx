A **static entry** is how EEZ resolves a **read-only query** across a rollup boundary. Instead of executing a state-changing cross-chain call, EEZ hands back pre-recorded return data for a `STATICCALL` that would otherwise have to reach across chains. The prover computes the correct return value off-chain, records it, and the on-chain machinery verifies it and returns it to the caller.

The same machinery also resolves a second pattern: a **pre-verified reverting reentrant call**. When a contract calls back through a proxy inside a `try/catch` and expects that call to revert, the reentrant table stores the revert data and the (optionally state-mutating) sub-execution that produced it.

There is no separate "lookup" struct and no separate lookup key space. Reentrant reads and reverted reentrant calls are ordinary rows of the **same unified reentrant table** used for successful reentrant calls — `ExpectedL1ToL2Call` on L1, `ExpectedOutgoingCrossChainCall` on L2 — content-addressed by the same position key as plain-success rows. Only top-level static reads (outside any execution) get a dedicated struct, `StaticExecutionEntry`. *(Source: `STATIC_ENTRY.md`, header table and lines 16-22.)*

## Two Homes, Split by Execution Context

| Situation | Mechanism | Lives in | Match key |
| --- | --- | --- | --- |
| Reentrant static read, fired `_insideExecution()` | STATIC-kind row (`isStatic` folded into the hash) in the entry's unified reentrant table | `ExecutionEntry.expectedL1ToL2Calls[]` (L1) / `expectedOutgoingCalls[]` (L2) | `expectedL1toL2Hash == keccak256(crossChainCallHash, expectedRollingHash)` |
| Reentrant call that reverts (`try/catch`) | REVERTED-kind row (`success == false`) in the same table | same table | same key formula, with `isStatic = false` folded into `crossChainCallHash` instead |
| Top-level static read (including one that reverts) | `StaticExecutionEntry` | L1: `_transientStaticEntries` while a batch is mid-flight, else per-rollup `staticEntryQueue`; L2: the `staticEntries` pool | L1: `proxyEntryHash` + `destinationRollupId` + every `expectedStateRoots` pin live; L2: `proxyEntryHash` alone, same-block only |

*(Source: `STATIC_ENTRY.md` §0 header table, lines 9-14.)*

There is no `failed` flag and no four-tuple context index. A single boolean, `success`, carries the same polarity on `ExecutionEntry`, `ExpectedL1ToL2Call`, and `StaticExecutionEntry`: `false` means "run/verify the sub-calls, then `revert(returnData)`"; `true` means "…then return `returnData`." What used to require a dedicated struct with its own match tuple is now just another row, distinguished purely by what's folded into its key.

:::info
STATIC vs CALL is decided by the *key*, not by a kind selector on the row: `crossChainCallHash` folds `isStatic`, so a static read can only ever match a row whose key was built from a static hash. SUCCESS vs REVERTED within the CALL kind is the row's own `success` flag. *(Source: `STATIC_ENTRY.md` lines 82-85.)*
:::

## Routing: How a Read Reaches `staticCrossChainCall`

A contract performs a cross-chain read by `STATICCALL`ing the counterparty's `CrossChainProxy`, exactly like a regular call — no separate proxy or entry point.

```solidity
// Regular cross-chain call (state-changing)
(bool ok, bytes memory ret) = crossChainProxy.call(calldata);

// Cross-chain view query (static read)
(bool ok, bytes memory ret) = crossChainProxy.staticcall(calldata);
// ↑ EEZ routes this to staticCrossChainCall automatically
```

**Detection mechanism:** `CrossChainProxy._fallback()` self-calls `staticCheck()`, which attempts a transient-storage write (`tstore`, EIP-1153). That write reverts inside a `STATICCALL` context but succeeds in a regular `CALL` context — so the self-call's success or failure alone tells the proxy which opcode it was invoked with. A failed self-call routes to `staticCrossChainCall` (view); a successful one routes to `executeCrossChainCall`.

```solidity
// src/base/CrossChainProxy.sol — _fallback()
(bool success,) = address(this).call{gas: STATIC_CHECK_GAS}(abi.encodeCall(this.staticCheck, ()));
if (!success) {
    // Static context — look up pre-computed result via view function
    (success, result) = EEZ.staticcall(abi.encodeCall(IEEZ.staticCrossChainCall, (msg.sender, msg.data)));
} else {
    // Normal context — execute cross-chain call
    (success, result) = EEZ.call{value: msg.value}(abi.encodeCall(IEEZ.executeCrossChainCall, (msg.sender, msg.data)));
}
```
*(Source: `src/base/CrossChainProxy.sol:69-102`, corroborated by `STATIC_ENTRY.md` §1.)*

`staticCrossChainCall` is `view`. It computes the call's identity with the same canonical `crossChainCallHash` formula used everywhere else (`CORE_PROTOCOL_SPEC.md` §C.3), but with `isStatic = true` — a read keys **distinctly** from an otherwise-identical state-changing call, so it can only ever match a row built from a static key. `value` is always `0` (a `STATICCALL` can't carry ETH) and `callGas` folds to `0` too — a read never keys on gas, even on an L2 with `USE_GAS_LEFT`. It then branches on `_insideExecution()`: inside, it scans the active entry's unified reentrant table; outside, the top-level `StaticExecutionEntry` pool. *(Source: `STATIC_ENTRY.md` §1, lines 38-46; confirmed in `src/EEZ.sol:1266-1278` and `src/L2/EEZL2.sol:594-609`.)*

## Field Reference

### `ExpectedL1ToL2Call` — the unified reentrant table (L1)

```solidity
// src/interfaces/IEEZ.sol
struct ExpectedL1ToL2Call {
    bytes32 expectedL1toL2Hash;          // position key: keccak256(crossChainCallHash, expectedRollingHash)
    L2ToL1Call[] l2ToL1Calls;            // this row's OWN sub-calls, run to completion
    bytes32 revertedOrStaticRollingHash; // expected sub-call hash, checked for STATIC / REVERTED
    bool success;                        // whether resolution returns or reverts
    bytes returnData;                    // returned on success / reverted-with when !success
}
```

| Field | Meaning |
| --- | --- |
| `expectedL1toL2Hash` | Content-addresses this row by `keccak256(crossChainCallHash, expectedRollingHash)`, where `expectedRollingHash` is the live `_rollingHash` at the instant the reentrant call (or read) fires. No cursor coordinates or context index are needed — the rolling hash alone uniquely pins the execution point. |
| `l2ToL1Calls` | This row's own sub-call array. A SUCCESS row folds it into the host's continuous hash between `NESTED_BEGIN`/`NESTED_END`; a STATIC row runs it flatly via `STATICCALL`; a REVERTED row runs it as a mini-entry under the tagged schema, then reverts. |
| `revertedOrStaticRollingHash` | Expected hash of the sub-call array — only checked for STATIC and REVERTED kinds (a plain SUCCESS row folds into the host hash instead). |
| `success` | For a CALL-kind row: `true` = plain successful reentrant call; `false` = REVERTED — a pre-verified reentrant call that reverts. Static reads always resolve through the same field's polarity on `StaticExecutionEntry` or this row. |
| `returnData` | Returned on success, or the revert payload when `!success`. |

*(Source: `src/interfaces/IEEZ.sol:83-120`, `STATIC_ENTRY.md` §2 lines 57-63.)*

There is **no kind selector** on the row itself. STATIC vs CALL is decided entirely by which key matched — `crossChainCallHash` folds `isStatic` — and SUCCESS vs REVERTED within the CALL kind is just the row's own `success` flag. *(Source: `STATIC_ENTRY.md` lines 82-85.)*

### `StaticExecutionEntry` — the top-level pool (L1)

```solidity
// src/interfaces/IEEZ.sol
struct StaticExecutionEntry {
    ExpectedStateRootPerRollup[] expectedStateRoots; // state-root pins — part of the MATCH
    bytes32 proxyEntryHash;      // the inbound call's crossChainCallHash (isStatic = true folded in)
    L2ToL1Call[] l2ToL1Calls;    // read-only sub-calls run via STATICCALL during resolution
    bytes32 rollingHash;         // expected untagged hash of the sub-calls
    uint64 destinationRollupId;  // routes the pool entry; must match the calling proxy's rollup
    bool success;                // whether resolution returns or reverts
    bytes returnData;            // returned on success / reverted-with when !success
}
```

| Field | Meaning |
| --- | --- |
| `expectedStateRoots` | State-root pins per rollup — part of the match predicate, not just a freshness check. See [State-Root Pins](#state-root-pins-top-level-l1-only) below. |
| `proxyEntryHash` | The inbound call's `crossChainCallHash`, computed with `isStatic = true` folded in — mirrors `ExecutionEntry.proxyEntryHash`. |
| `l2ToL1Calls` | Read-only sub-calls, run via `STATICCALL` at resolution. No reentrant frames — a reentrant read re-enters the pool as *another* `StaticExecutionEntry`. |
| `rollingHash` | Expected untagged hash of the sub-calls (`keccak256(prev, success, retData)` per sub-call). |
| `destinationRollupId` | Routes publishing into `verificationByRollup[rid].staticEntryQueue` and is re-checked at match time. Load-bearing for the transient pool (a single global table, not queue-routed). |
| `success` | `false` ⇒ resolution reverts with `returnData`; `true` ⇒ it returns `returnData`. |
| `returnData` | Returned on success, or the revert payload when `!success`. |

*(Source: `src/interfaces/IEEZ.sol:144-152`, `STATIC_ENTRY.md` §2 lines 65-74 and 86-90.)*

:::note
Field names above are L1's. L2's mirror struct is `ExpectedOutgoingCrossChainCall`, using self-relative names (`expectedOutgoingHash`, `incomingCalls`, cursor `_lastOutgoingCallConsumed`) and dropping the L1-only fields (`destinationRollupId`, `expectedStateRoots`). See [L1 / L2 Differences](#l1--l2-differences) below.
:::

## The Position Key (`expectedL1toL2Hash`)

Every reentrant-table row is content-addressed by one value:

```
expectedL1toL2Hash = keccak256(abi.encodePacked(crossChainCallHash, expectedRollingHash))
```

`expectedRollingHash` is the live `_rollingHash` at the instant the reentrant call or read fires. Because the rolling hash chains every prior call result and nesting boundary, it uniquely pins the execution point — no cursor coordinates or context index needed:

- Two textually identical calls at different points key differently (different `_rollingHash`).
- A read and a state-changing call with identical params key differently (`isStatic` folds into the call hash).
- A reverted sub-execution reuses the host table for its own reentrant calls; its rows can't collide with host-level rows because their keys embed the sub-execution's interior `_rollingHash` values.

Matching walks **strictly forward** from the reentrant cursor (`_lastL1ToL2CallConsumed` on L1, `_lastOutgoingCallConsumed` on L2); the first key match is the row. A resolved CALL advances the cursor past its row; a static read cannot (it's a `view` frame) — it is *position-pinned* rather than *consumed*, so the same STATIC row satisfies repeated identical reads fired at the same hash point, and it still only matches at or after the cursor.

*(Source: `STATIC_ENTRY.md` §3, lines 96-124; disambiguation of multiple same-hash reads: `CORE_PROTOCOL_SPEC.md` §E.4.)*

## Resolution Mechanics

### Reentrant static read (inside an execution)

`staticCrossChainCall`'s in-execution branch:

1. **(L1 only)** Proxy protection: the read's target rollup must be in the executing entry's allowed set (`_isRollupAllowed`, derived from its `stateUpdates`) — else `ReentrantDestinationNotVerified`.
2. Compute the key from the static-kind `crossChainCallHash` plus the live `_rollingHash`; scan the active table forward from the cursor.
3. On match → `_resolveStaticEntry(l2ToL1Calls, revertedOrStaticRollingHash, success, returnData)` (below). On no match → revert `ExecutionNotFound` directly — a `view` frame can't defer to a later rolling-hash check the way a reentrant CALL no-match can.

```solidity
// src/EEZ.sol — staticCrossChainCall, in-execution branch
if (_insideExecution()) {
    if (!_isRollupAllowed(destRid)) revert ReentrantDestinationNotVerified(destRid);
    bytes32 expectedL1toL2Hash = _computeExpectedL1toL2Hash(crossChainCallHash, _rollingHash);
    ExpectedL1ToL2Call[] memory expectedCalls = _getExpectedL1toL2Calls();
    for (uint256 i = _lastL1ToL2CallConsumed; i < expectedCalls.length; i++) {
        ExpectedL1ToL2Call memory expectedCall = expectedCalls[i];
        if (expectedCall.expectedL1toL2Hash == expectedL1toL2Hash) {
            return _resolveStaticEntry(
                expectedCall.l2ToL1Calls, expectedCall.revertedOrStaticRollingHash,
                expectedCall.success, expectedCall.returnData
            );
        }
    }
    revert ExecutionNotFound();
}
```
*(Source: `src/EEZ.sol:1284-1303`; spec: `STATIC_ENTRY.md` §4.1, lines 132-142.)*

### Top-level static read (outside any execution)

`staticCrossChainCall`'s pool branch selects one table on L1:

- While a batch is mid-flight (`_transientEntries.length != 0`): **only** `_transientStaticEntries` — the transient phase is self-contained.
- Otherwise: the calling proxy's own rollup queue, `verificationByRollup[destRid].staticEntryQueue`.

The match is a full scan (a non-matching candidate is skipped, never an error):

```
staticEntry.proxyEntryHash == crossChainCallHash
&& staticEntry.destinationRollupId == destRid
&& _stateRootsMatch(staticEntry)   // every pin equals the live root
```

There is **no block gate** on the top-level static path — a static entry does not go stale with the block; as long as its pins match the live roots, it resolves. Lifetime is bounded instead by the queue reset: every batch that verifies a rollup wipes that rollup's `staticEntryQueue` along with its entry queue.

On L2 the pool is the single `staticEntries` table, matched by `proxyEntryHash` alone — but gated on `lastLoadBlock == block.number` instead, since L2 has no pins to bound staleness.

*(Source: `STATIC_ENTRY.md` §4.2, lines 162-190; confirmed in `src/EEZ.sol:1305-1325`.)*

### `_resolveStaticEntry` / `_processNStaticCalls` — the shared resolution body

Both the reentrant STATIC branch and the top-level pool resolve through the same function:

```solidity
function _resolveStaticEntry(
    L2ToL1Call[] memory calls,
    bytes32 revertedOrStaticRollingHash,
    bool success,
    bytes memory returnData
) internal view returns (bytes memory) {
    if (_processNStaticCalls(calls) != revertedOrStaticRollingHash) revert RollingHashMismatch();
    if (!success) {
        assembly { revert(add(returnData, 0x20), mload(returnData)) }
    }
    return returnData;
}
```

`_processNStaticCalls` runs the sub-call array flatly, in **static context**:

- Each sub-call dispatches `sourceProxy.staticcall(executeOnBehalf(target, gas, data))` — read-only, no value, reverts on any state write in the target.
- Results fold into an **untagged** accumulator seeded at `bytes32(0)`: `hash = keccak256(prev, success, retData)` per sub-call. No `CALL_BEGIN`/`CALL_END`/`NESTED_BEGIN`/`NESTED_END` tags and no call-identity fold — the surrounding key already pins the context. The hash is **always** compared: an empty `calls[]` hashes to `0`, so a sub-call-less static row/entry must carry an expected hash of `0`.
- Every referenced source proxy **must already be deployed**: `CREATE2` is unavailable inside a `STATICCALL` frame, and a `STATICCALL` to a codeless address silently returns `(true, "")` — so a codeless proxy reverts `StaticCallProxyNotDeployed` rather than letting the prover pre-hash a no-op.
- Every sub-call must be marked `isStatic` with `value == 0` — dispatch is read-only whatever the fields say, so a mismatch reverts (`NonStaticSubCall` / `StaticCallWithValue`) instead of silently executing a proven state-changing call read-only.
- No force-revert handling (`revertNextNCalls`) — nothing mutates state, so there's nothing to roll back.

A naturally-reverting *sub-call* is not special: the `STATICCALL` simply returns `(false, retData)` and the untagged hash captures it. The row/entry-level `success == false` is for the *whole read* reverting toward its caller.

*(Source: `src/EEZ.sol:1332-1371`, `STATIC_ENTRY.md` §4.3, `CORE_PROTOCOL_SPEC.md` §E.2.)*

:::info
This is the same shared body for both contexts — there's no separate "reverted-lookup" execution path anymore. A REVERTED reentrant call (`success == false` CALL-kind row) is resolved by a *different* function, `_resolveNestedReentrant` inside `_consumeNestedCall`, which runs its sub-array as a real mini-entry under the **tagged** schema (may itself contain reentrant calls, resolved from the same host table) before reverting. See [Reverted reentrant calls](#reverted-reentrant-calls) below.
:::

### Reverted reentrant calls

A `try/catch`-wrapped reentrant call compiles to a normal `CALL`, not a `STATICCALL`, so it never reaches `staticCrossChainCall`. It's matched inside `_consumeNestedCall` against a CALL-kind row (built with `isStatic = false`) whose `success == false`:

```
advance the reentrant cursor past the matched row
_rollingHashNestedBegin(crossChainCallHash)          // open the frame
_processNCalls(row.l2ToL1Calls)                      // run the row's OWN sub-array, tagged schema
require _rollingHash == row.revertedOrStaticRollingHash   // else RollingHashMismatch
revert(row.returnData)                               // terminal revert
```

The terminal revert rolls back the sub-execution's state, the cursor advance, and the rolling-hash writes in one shot — the caller's `try`/`catch` observes exactly `returnData`. Because the sub-array runs through `_processNCalls` (real `CALL`/`STATICCALL` dispatch per sub-call), it **can mutate state** before the terminal revert unwinds it — unlike a STATIC row's sub-array, which never mutates because it's dispatched via `STATICCALL` throughout.

A `success == true` row takes the *other* branch of the same resolver: it closes the frame with `NESTED_END` into the host's continuous hash and returns `returnData` — that's a plain reentrant call, not a static/reverted resolution at all, and is specified in `EXECUTION_ENTRY_SPEC.md`.

*(Source: `STATIC_ENTRY.md` §4.1, lines 144-160.)*

## Per-Frame Sub-Arrays — No Shared Partition

Every reentrant-table row and every static entry carries its **own** sub-call array, run to completion by its resolver:

- STATIC rows / static entries: run flatly by `_processNStaticCalls` (untagged hash).
- REVERTED rows: run by `_processNCalls` as a mini-entry (tagged schema, may itself contain reentrant calls resolved from the host table).

There is no global flat-call cursor and no `callCount` partition to maintain: the entry's `l2ToL1Calls[]` holds only its top-level calls, and each frame's completeness is structural — the resolver processes the whole array it was handed. This replaces the old `callCount` bookkeeping that used to partition a shared flat-call array between the entry level and its nested lookups.

*(Source: `STATIC_ENTRY.md` §5.)*

## State-Root Pins (Top-Level, L1 Only)

`expectedStateRoots[]` is the key L1-only feature of `StaticExecutionEntry`. It content-addresses a top-level static entry to a point on each pinned rollup's state trajectory: a candidate only matches when every pin equals the live `rollups[rollupId].stateRoot` — a mismatching candidate is skipped and the scan continues, no dedicated error.

```solidity
// This static entry only matches when the pin is live:
StaticExecutionEntry memory entry = StaticExecutionEntry({
    expectedStateRoots: [
        ExpectedStateRootPerRollup({ rollupId: 1, stateRoot: keccak256("l2-state-after-step-3") })
    ],
    proxyEntryHash: ...,
    l2ToL1Calls: ...,
    rollingHash: ...,
    destinationRollupId: 1,
    success: true,
    returnData: abi.encode(remoteBalance)
});
```

The pins serve two roles:

- **The freshness predicate.** With no block gate on the static path, the pins are what invalidates a cached read once any pinned rollup's root moves on.
- **Transient-phase capable.** Roots advance entry-by-entry during a batch, so a pin can target an intermediate mid-batch state.

`_validateBatchStructure` enforces, per static entry, at **publish time** (unconditional on `success`):

| Rule | Error |
| --- | --- |
| Pins strictly increasing by `rollupId` (rejects duplicates and any mainnet pin) | `ExpectedStateRootsNotStrictlyIncreasing` |
| Every pinned rollup must be in the batch | `RollupNotInBatch` |
| `destinationRollupId` must itself be among the pins | `StaticEntryDestinationNotPinned` |
| Every sub-call's `sourceRollupId` must be among the pins | `CallSourceNotVerified` |

The one mandatory pin is the entry's own `destinationRollupId` — so `expectedStateRoots` can never be empty in practice; a pin-less static entry fails validation. The prover may pin *additional* rollups beyond that mandatory one, narrowing the entry to a specific cross-rollup interleaving.

Prover binding: each static entry is hashed whole (`keccak256(abi.encode(staticEntry))`) into the batch's `publicInputsHash`, so its content can't be swapped after proving. `immediateStaticEntryCount` — the leading prefix loaded into `_transientStaticEntries` for the meta-hook window — is an unproven dispatch parameter (like `immediateEntryCount`).

*(Source: `STATIC_ENTRY.md` §6, confirmed against `src/EEZ.sol` error declarations at lines 250, 265, 270, 293 and `_validateBatchStructure` at line 481.)*

## L1 / L2 Differences

| Feature | L1 (EEZ) | L2 (EEZL2) |
| --- | --- | --- |
| Reentrant table struct | `ExpectedL1ToL2Call` | `ExpectedOutgoingCrossChainCall` |
| Reentrant table field names | `expectedL1toL2Hash`, `l2ToL1Calls` | `expectedOutgoingHash`, `incomingCalls` (self-relative) |
| Top-level struct | `StaticExecutionEntry` (with `expectedStateRoots`, `destinationRollupId`) | `StaticExecutionEntry` (drops both — single rollup) |
| Top-level pool | `_transientStaticEntries` / per-rollup `staticEntryQueue` | single `staticEntries` table |
| Top-level match | `proxyEntryHash` + `destinationRollupId` + all `expectedStateRoots` pins live; no block gate | `proxyEntryHash` alone; gated on `lastLoadBlock == block.number` |
| Staleness bound | State-root pins | Same-block restriction |
| Call-hash source side | `sourceRollupId = MAINNET_ROLLUP_ID` | `sourceRollupId = ROLLUP_ID` (this L2) |
| Proxy protection (reentrant) | Checks `_isRollupAllowed(destRid)` against the entry's `stateUpdates` | No allowed-rollups set |

*(Source: `STATIC_ENTRY.md` §7.)*

## Invariants Summary

- `success == false` ⇒ resolution ends in `revert(returnData)`; `success == true` ⇒ it returns `returnData` — the same polarity on `ExecutionEntry`, `ExpectedL1ToL2Call`, and `StaticExecutionEntry`.
- A static read never mutates: `STATICCALL` dispatch, untagged hash, no cursor advance, no proxy auto-creation, no force-revert handling.
- STATIC and REVERTED sub-arrays are verified against `revertedOrStaticRollingHash` (rows) / `rollingHash` (static entries); the untagged accumulator seeds at `bytes32(0)`, so an empty sub-array requires an expected hash of `0`.
- STATIC and CALL kinds can never match each other's keys — `crossChainCallHash` folds `isStatic`.
- Matching is strictly forward from the reentrant cursor; a CALL consumes its row (cursor advances past it), a static read does not.
- A REVERTED resolution runs its own sub-array with the tagged schema inside `NESTED_BEGIN`, checks the sub-hash, then terminal-reverts — state, cursor, and hash all roll back with it.
- No-match asymmetry: a reentrant CALL no-match folds `CALL_NOT_FOUND` and returns `""` (the entry fails later at its rolling-hash check); a static no-match reverts `ExecutionNotFound` immediately, in both branches.
- L1 top-level match = `proxyEntryHash` + `destinationRollupId` + all pins live; full-scan skip semantics; no block gate — pins govern freshness, and every re-verify of the rollup wipes its `staticEntryQueue`.
- Validation (L1): pins strictly increasing and in-batch; `destinationRollupId` ∈ pins; every sub-call source ∈ pins; whole static entries folded into `publicInputsHash`; `immediateStaticEntryCount ≤ staticEntries.length`, and a non-zero count requires a non-zero `immediateEntryCount`.

*(Source: `STATIC_ENTRY.md` §8.)*
