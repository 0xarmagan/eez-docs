The EEZ `Bridge` contract is a periphery contract that enables trustless asset transfers between Ethereum L1 and any EEZ-registered rollup. It uses a **lock-and-mint model**: native tokens are locked in the Bridge on the source chain, and a corresponding `WrappedToken` ERC20 is minted on the destination. When you bridge back, the wrapped token is burned and the native tokens are released. The Bridge itself is designed to be deployed at the **same address on every chain** using CREATE2, so both sides of the bridge are always at a predictable, identical address.

:::note
`Bridge.sol` is also an **illustrative periphery example**, not a hardened reference implementation. Known simplifications: no fee-on-transfer token accounting, and no re-deployment authorization checks on `initialize()`.
:::

## The Lock-and-Mint Model

When you call `bridgeTokens` on the source chain:

- If the token is **native to the source chain**, the Bridge locks it in the contract via `safeTransferFrom`.
- If the token is **already a wrapped token** (bridged from another chain), the Bridge burns it instead, tracing back to the original.

On the destination chain, `receiveTokens` is called automatically through the EEZ cross-chain execution machinery:

- If the destination chain is the **original home chain** of the token, the locked native tokens are released via `safeTransfer`.
- Otherwise, a `WrappedToken` is minted (or deployed on first use) representing the foreign token.

This means the full round-trip for an L1 ERC20 → L2 is: **lock on L1 → mint wrapped on L2**. Bridging back is: **burn wrapped on L2 → release native on L1**.

## Deploying Bridge via CREATE2

The Bridge is deployed with no constructor arguments so it can be placed at the same address on every chain using CREATE2. Use your preferred CREATE2 factory (the canonical `0x4e59b44847b379578588920cA78FbF26c0B4956C` factory works on most networks) with a shared salt:

```bash
# Deploy Bridge on L1
forge script script/DeployBridge.s.sol:BridgeDeployL1 \
  --rpc-url $L1_RPC --broadcast --private-key $PK \
  --sig "run(address,bytes32)" $ROLLUPS $SALT
# Outputs: Deployed to: <BRIDGE_L1 address>

# Deploy Bridge on L2 (same salt → same address)
forge script script/DeployBridge.s.sol:BridgeDeployL2 \
  --rpc-url $L2_RPC --broadcast --private-key $PK \
  --sig "run(address,uint64,bytes32)" $MANAGER_L2 $L2_ROLLUP_ID $SALT
# Outputs: Deployed to: <BRIDGE_L2 address> (identical to BRIDGE_L1 with a shared factory + salt)
```

Choose your salt carefully — a deterministic, human-readable salt (e.g. `keccak256("eez-bridge-v1")`) works well for testnet. The CREATE2 address is a function of the factory address, salt, and init bytecode, so identical inputs produce the same address on every EVM chain.

## Initializing the Bridge

Because there is no constructor, you must call `initialize` once on each deployment to bind chain-specific configuration:

```solidity
function initialize(
    address _manager,   // EEZ (L1) or EEZL2 (L2) address
    uint64 _rollupId,   // 0 for L1 mainnet, chain-specific ID for L2s
    address _admin      // admin who can call setCanonicalBridgeAddress
) external
```

`initialize` reverts with `AlreadyInitialized` if called a second time. After initialization, the Bridge reads `manager` to compute `CrossChainProxy` addresses for outbound calls, and `rollupId` to identify which chain it is operating on during inbound receives.

### Setting the Canonical Bridge Address

When you deploy both sides of the bridge, each Bridge instance needs to know the address of its counterpart for proxy computations. Call `setCanonicalBridgeAddress` as the admin after deployment:

```solidity
// On L1 Bridge: tell it the L2 Bridge address
bridge_l1.setCanonicalBridgeAddress(address(bridge_l2));

// On L2 Bridge: tell it the L1 Bridge address
bridge_l2.setCanonicalBridgeAddress(address(bridge_l1));
```

This step is only needed when the two Bridge deployments land at different addresses (e.g. during testing without a shared CREATE2 factory). In a canonical cross-chain deploy with the same salt, both Bridges share the same address and this step can be skipped.

## Bridging ETH

Use `bridgeEther` to transfer native ETH from the current chain to a destination rollup:

```solidity
function bridgeEther(
    uint64 _rollupId,           // destination rollup ID
    address destinationAddress  // recipient on the destination
) external payable
```

Send ETH as `msg.value`. The Bridge creates (or reuses) a `CrossChainProxy` representing `destinationAddress` on the destination rollup and forwards the full `msg.value` through it. EEZ records the ETH delta in `StateUpdate.etherDelta` on the L1 execution entry, and the L2 sequencer forwards the same value through the source proxy to the recipient's `receive()`.

```solidity
// Bridge 1 ETH to an address on rollup 1
bridge.bridgeEther{value: 1 ether}(1, recipientOnL2);
```

## Bridging ERC20 Tokens

Use `bridgeTokens` to transfer any ERC20 token cross-chain:

```solidity
function bridgeTokens(
    address token,              // ERC20 token to bridge (native or wrapped)
    uint256 amount,             // amount to transfer
    uint64 _rollupId,           // destination rollup ID
    address destinationAddress  // recipient on the destination
) external
```

Before calling, approve the Bridge to pull the tokens:

```solidity
IERC20(token).approve(address(bridge), amount);
bridge.bridgeTokens(token, amount, destRollupId, recipient);
```

The Bridge inspects `wrappedTokenInfo[token]` to decide the path:

| Token type | Source action | Destination action |
|---|---|---|
| Native (originated on this chain) | Locked in Bridge via `safeTransferFrom` | Released via `safeTransfer`, or minted as `WrappedToken` |
| Wrapped (bridged from another chain) | Burned via `WrappedToken.burn` | Native released on origin chain, or re-minted as wrapped elsewhere |

The `bridgeTokens` function encodes a `receiveTokens` call and routes it through a `CrossChainProxy` targeted at the destination Bridge. EEZ's cross-chain execution machinery then delivers this call automatically on the destination chain during the same L1 block.

## Receiving Tokens (Automatic)

You do not call `receiveTokens` directly — EEZ calls it on the destination Bridge when it processes the outbound proxy call. It is shown here for reference:

```solidity
function receiveTokens(
    address originalToken,      // token address on the origin chain
    uint64 originalRollupId,    // rollup ID where the native token lives
    address to,                 // recipient on this chain
    uint256 amount,             // amount to deliver
    string calldata name,       // ERC20 name (for first-time WrappedToken deploy)
    string calldata symbol,     // ERC20 symbol
    uint8 tokenDecimals,        // ERC20 decimals
    uint64 sourceRollupId       // rollup the call originated from
) external onlyBridgeProxy(sourceRollupId)
```

The `onlyBridgeProxy` modifier verifies that `msg.sender` is exactly the `CrossChainProxy` computed from the Bridge address and `sourceRollupId`. This is the Bridge's primary security check — only the EEZ execution machinery can deliver calls through a valid `CrossChainProxy`.

## Looking Up Wrapped Token Addresses

After a token has been bridged at least once, its `WrappedToken` is deployed and registered. Look it up with:

```solidity
function getWrappedToken(
    address originalToken,
    uint64 originalRollupId
) external view returns (address)
```

Returns `address(0)` if the token has never been bridged to this chain. You can pre-compute the address deterministically before any bridge interaction using the same CREATE2 parameters the Bridge uses internally:

```solidity
bytes32 wrappedSalt = keccak256(abi.encodePacked(originalToken, originalRollupId));
bytes32 bytecodeHash = keccak256(abi.encodePacked(
    type(WrappedToken).creationCode,
    abi.encode(name, symbol, decimals, bridgeAddress)
));
address predicted = address(uint160(uint256(keccak256(
    abi.encodePacked(bytes1(0xff), bridgeAddress, wrappedSalt, bytecodeHash)
))));
```

There's no longer a standalone Forge script for this computation — `script/flash-loan-test/` (which used to host `ComputeWrappedTokenAddress`) is gone entirely. The same CREATE2 math is now inlined directly where it's needed: the `DeployL2` contract in `script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol` pre-computes a `WrappedToken` address this same way (mirroring `Bridge._getOrDeployWrapped`) before the token exists, so the token-gated NFT can reference it at deploy time.

## The WrappedToken Contract

Each `WrappedToken` is an ERC20 + ERC20Permit contract deployed by the Bridge via CREATE2. Key properties:

- **`BRIDGE`** — immutable, set to the deploying Bridge. Only the Bridge can call `mint` or `burn`.
- **`mint(address to, uint256 amount)`** — called by the Bridge on inbound receives. No external access.
- **`burn(address from, uint256 amount)`** — called by the Bridge when you bridge wrapped tokens back. Tokens are pulled from `from` directly; only the Bridge (`BRIDGE`) can invoke this function.
- **Decimals** — preserved exactly from the original token at deployment time.
- **ERC20Permit** — allows gasless approvals via `permit`.

```solidity
// WrappedToken is an ERC20 + ERC20Permit
// Only Bridge can mint and burn
function mint(address to, uint256 amount) external onlyBridge
function burn(address from, uint256 amount) external onlyBridge
```

Wrapped tokens are registered in two mappings on the Bridge:

- `wrappedTokens[salt] → address` — forward lookup from `(originalToken, originalRollupId)` to wrapped address.
- `wrappedTokenInfo[wrappedAddress] → TokenInfo` — reverse lookup so `bridgeTokens` knows a token is wrapped and can trace back to the origin chain.

## Full Example: Bridging an ERC20 from L1 to L2

### Step 1 — Approve the L1 Bridge

Grant the Bridge allowance to pull your tokens before bridging:

```solidity
IERC20(token).approve(address(bridge_l1), 1000e18);
```

### Step 2 — Call bridgeTokens on L1

Lock tokens on L1 and enqueue the cross-chain delivery:

```solidity
bridge_l1.bridgeTokens(
    token,       // native ERC20 on L1
    1000e18,     // amount
    1,           // destination: rollup ID 1 (L2)
    recipient    // address to receive wrapped tokens on L2
);
```

The Bridge locks `1000e18` tokens in its contract and emits `TokensBridged`.

### Step 3 — Wait for the EEZ batch to process

The cross-chain call to `receiveTokens` is delivered by EEZ when the L1 batch that includes this block is verified. During the same L1 block, the L2 Bridge's `receiveTokens` is called through the source proxy.

Confirm delivery by watching for the L2 Bridge's `receiveTokens` events, not `TokensBridged` — that event only fires on the *source* chain, inside `bridgeTokens()`. The L2 Bridge never calls `bridgeTokens()` in this flow; it only calls `receiveTokens()`, which emits `WrappedTokensMinted` (this case — the token is foreign to L2) or `TokensReleased` (if the destination happens to be the token's native chain). So watch for `WrappedTokensMinted` on the L2 Bridge here, or poll the recipient's wrapped-token balance (Step 4). If the L1 batch that posted this call is never verified in the same block, delivery never happens — the `lastVerifiedBlock` gate (see [Post Batch](/guides/post-verify-batch#same-block-execution-requirement)) prevents any later-block consumption, so a missed same-block verification means resubmitting the bridge call in a new batch.

### Step 4 — Recipient holds WrappedToken on L2

On L2, the Bridge calls `_getOrDeployWrapped`, which either deploys a new `WrappedToken` via CREATE2 (first bridge for this token) or reuses the existing one. The recipient's balance increases by `1000e18` wrapped tokens.

Check the balance:
```solidity
address wrapped = bridge_l2.getWrappedToken(token, 0); // 0 = L1 mainnet
IERC20(wrapped).balanceOf(recipient); // → 1000e18
```

### Step 5 — Bridge back: approve and bridgeTokens on L2

To return to L1, approve and bridge the wrapped token from L2:

```solidity
IERC20(wrapped).approve(address(bridge_l2), 1000e18);
bridge_l2.bridgeTokens(
    wrapped,     // WrappedToken on L2
    1000e18,
    0,           // destination: L1 mainnet (rollup ID 0)
    recipient    // address to release native tokens to on L1
);
```

The Bridge sees `wrappedTokenInfo[wrapped].originalToken != address(0)`, burns the wrapped tokens, and routes a `receiveTokens` call back to the L1 Bridge. On L1, the locked tokens are released to `recipient`.
