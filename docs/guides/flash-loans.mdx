EEZ's synchronous composability makes cross-rollup flash loans possible in a way that is fundamentally different from conventional bridge-and-wait patterns. Because EEZ batches state transitions for multiple rollups into a single L1 block and delivers cross-chain calls atomically, you can borrow tokens on L1, bridge them to L2 to perform some action (such as claiming a token-gated NFT), bring them back, and repay the flash loan — all within the same Ethereum block, as if the two chains were a single execution environment.

## The Core Concept

A conventional flash loan is atomic because the entire borrow-use-repay cycle happens within one EVM transaction. A cross-rollup flash loan requires the borrowed funds to travel to another chain and back. EEZ makes this atomic by:

1. **Pre-committing the full execution plan** — the prover computes all state transitions (L1 locks, L2 mints, L2 burns, L1 unlocks) off-chain before the L1 batch is submitted.
2. **Delivering cross-chain calls synchronously** — within `postAndVerifyBatch`, EEZ walks the execution entries and fires cross-chain calls in order. Each call resolves before the next one starts.
3. **Enforcing accounting at the batch level** — EEZ's `etherDelta` field on each `StateUpdate` ensures that ETH moved cross-chain is always accounted for. For ERC20s, the Bridge's lock-and-mint guarantees that tokens cannot be double-spent.

The result: a smart contract on L1 can borrow tokens, instruct the EEZ Bridge to send them to L2, wait for an L2 contract to act on them, and receive the tokens back — all before the L1 transaction finalizes.

## How EEZ Enables This

### The Reentrant Cross-Chain Call Pattern

Cross-chain calls in EEZ are **reentrant by design**. When an L1 contract calls a `CrossChainProxy` targeting an L2 contract, EEZ's `executeCrossChainCall` immediately invokes the destination (on L2 in the same block). If that L2 contract in turn calls back to L1 — for instance, to bridge tokens back — EEZ handles the inbound L1 call as part of the same top-level execution entry's nested frame (`ExpectedL1ToL2Call`).

This reentrant pattern is what the flash loan executor uses:

```text
L1: FlashLoanBridgeExecutor.onFlashLoan()
  → bridge_l1.bridgeTokens(...)              // L1→L2 call via CrossChainProxy
    └── L2: bridge_l2.receiveTokens(...)     // tokens arrive on L2 as WrappedToken
  → executorL2Proxy.claimAndBridgeBack(...)  // L1→L2 call: use the tokens
    └── L2: executorL2.claimAndBridgeBack()
          → FlashLoanersNFT.claim()          // token-gated action on L2
          → bridge_l2.bridgeTokens(...)      // L2→L1 call via CrossChainProxy
            └── L1: bridge_l1.receiveTokens() // tokens arrive back on L1
  → IERC20(token).transfer(flashLoanPool, amount)  // repay
```

This entire call tree executes within the scope of the `FlashLoan.flashLoan` call on L1, satisfying the flash loan's invariant check (`balanceAfter >= balanceBefore`) at the end.

### revertNextNCalls for Forced Rollbacks

Each `L2ToL1Call` carries a `revertNextNCalls` field (`uint16`; see [Build Entries](/guides/build-execution-entries#l2tol1call) for the full struct). Setting `revertNextNCalls = N` on a call causes EEZ to execute the next `N` calls, capture their results in the rolling hash, and then forcibly roll back all of their EVM state changes — even though the calls themselves succeeded. This is different from a naturally-reverting call: a `revertNextNCalls > 0` call succeeds at the EVM level but has its state effects undone afterward. This lets you run a call for its side effects on the destination chain (or to produce a result you need for the rolling hash) without letting those state changes persist. The flash loan flow itself doesn't use this — every call in the round trip is meant to persist — but it's available for scenarios that need a call's side effects folded into the hash without keeping its state changes.

### The ETH Accounting Invariant (etherDelta)

Every execution entry carries a `StateUpdate` array whose `etherDelta` field records the **net ETH change for each rollup** caused by the entry (see [Build Entries](/guides/build-execution-entries#stateupdate-l1-only) for the full struct). EEZ enforces accounting by checking that ETH flowing into and out of each rollup balances across all entries in a batch. For ERC20 flash loans, `etherDelta` is zero — only the bridge's lock-and-mint invariant applies.

## Worked Example: The Flash Loan Test

[`script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol`](https://github.com/eez-association/eez-core-protocol/blob/main/script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol) contains the full end-to-end demonstration. It's structured differently from a typical one-way scenario: five contracts (`Deploy`, `DeployL2`, `Deploy2`, `ExecuteL2`, `Execute`) plus a `ComputeExpected` verifier, every one of them reading its inputs from environment variables (`vm.envAddress(...)`) rather than positional CLI arguments. Here is how the round trip is orchestrated across **two** L1 entries and **two** L2 deliveries.

### Contracts Involved

| Contract | Chain | Role |
| --- | --- | --- |
| `FlashLoan` | L1 | Flash loan pool — holds the native ERC20 tokens |
| `FlashLoanBridgeExecutor` (L1) | L1 | Orchestrates the full flow; implements `IFlashLoanReceiver` |
| `Bridge` (L1) | L1 | Locks/releases ERC20 tokens on L1 |
| `FlashLoanBridgeExecutor` (L2) | L2 | Claims NFT and bridges tokens back |
| `Bridge` (L2) | L2 | Mints/burns `WrappedToken` on L2 |
| `FlashLoanersNFT` | L2 | Token-gated NFT — requires ≥10,000 tokens to claim |

The two `Bridge` deployments share a single CREATE2 salt (keyed off the freshly-deployed `TestToken` address), so they land at the **same address on both chains** — `_bridgeAddress()` proxy lookups line up without a `setCanonicalBridgeAddress` call.

### The L1 Entries

The L1 side has exactly two execution entries — not three, and there's no zero-hash entry that needs a separate system trigger:

```solidity
// Entry 0: forward bridge leg — bridge.bridgeTokens (L1) → bridge.receiveTokens (L2).
//          No L1-side calls; the rolling hash is seed-only.
// Entry 1: claim leg — executorL1 → executorL2.claimAndBridgeBack. Its one top-level
//          l2ToL1Call IS the return bridge leg (bridge.receiveTokens), which runs
//          directly on L1 and releases the escrowed tokens back to executorL1.
```

Both entries have a non-zero `proxyEntryHash` — each is consumed by a real proxy-routed call inside `onFlashLoan` (below), so `executeL2Txs` is never called anywhere in this flow.

### The L1 Trigger (same block)

`Execute.run()` posts the batch and fires the user trigger in the same transaction broadcast:

```solidity
EEZ(rollupsAddr).postAndVerifyBatch(
    immediateSingleRollupBatch(proofSystemAddr, L2_ROLLUP_ID, _l1Entries(a), noStaticEntries())
);
FlashLoanBridgeExecutor(a.executorL1).execute(); // triggers pool.flashLoan → onFlashLoan → ...
```

The `onFlashLoan` callback in `FlashLoanBridgeExecutor` performs three steps:

```solidity
function onFlashLoan(address _token, uint256 amount) external override {
    require(msg.sender == address(flashLoanPool), "Unauthorized");

    // 1. Bridge tokens to executor on L2
    IERC20(_token).approve(address(bridge), amount);
    bridge.bridgeTokens(_token, amount, l2RollupId, executorL2);

    // 2. Trigger executor(L2) to claim NFT and bridge tokens back
    (bool success,) = executorL2Proxy.call(
        abi.encodeCall(this.claimAndBridgeBack, (wrappedTokenL2, nftL2, bridgeL2, 0, address(this)))
    );
    require(success, "Cross-chain call failed");

    // 3. Repay (tokens are back from bridge release)
    IERC20(_token).safeTransfer(msg.sender, amount);
}
```

Step 1 calls `bridge.bridgeTokens`, which routes through a `CrossChainProxy` to `bridge.receiveTokens` on L2. EEZ consumes Entry 0 and mints 10,000 `WrappedToken` units to `executorL2` on L2.

Step 2 calls `executorL2Proxy`, which routes to `executorL2.claimAndBridgeBack`. EEZ consumes Entry 1. Inside that call, `executorL2` claims the NFT (it now holds ≥10,000 wrapped tokens) and calls `bridge.bridgeTokens` to send the tokens back. This fires the reentrant L2→L1 return call, which is folded as Entry 1's top-level `l2ToL1Call` — it releases the native tokens back to `executorL1` directly on L1, no nested `ExpectedL1ToL2Call` frame needed on the L1 side.

Step 3 finds the tokens back in the executor's balance and transfers them to the flash loan pool. The invariant `balanceAfter >= balanceBefore` is satisfied.

### The Claim Delivery's Rolling Hash (L2 Entry 1)

The nesting lives on the **L2 side**, not the L1 side: L2 entry 1 (the `claimAndBridgeBack` delivery) folds a `NESTED_BEGIN`/`NESTED_END` pair around the reentrant return call that fires mid-execution, using `RollingHashBuilder` from `script/e2e/shared/E2EHelpers.sol`:

```solidity
bytes32 claimRh = RollingHashBuilder.entryBeginL2(claimHash);       // seed
claimRh = RollingHashBuilder.appendCallBegin(claimRh, claimHash);   // top-level call begins
bytes32 rhAtFire = claimRh;                                         // return leg fires right here
claimRh = RollingHashBuilder.appendNestedBegin(claimRh, retHashL2Out); // nested frame opens
claimRh = RollingHashBuilder.appendNestedEnd(claimRh);                 // nested frame closes — no second argument
claimRh = RollingHashBuilder.appendCallEnd(claimRh, true, "");      // top-level call ends (void return)
```

`appendNestedEnd` takes only the running hash — there's no `nestedNumber` counter to fold in. The reentrant call's identity is bound in separately: `rhAtFire` (the rolling hash at the moment the nested frame opens) and the return call's own hash are combined into `expectedL1toL2Hash(retHashL2Out, rhAtFire)`, which is what `ExpectedOutgoingCrossChainCall.expectedOutgoingHash` gets matched against when the return leg actually fires. On the **L1 side**, by contrast, entry 1's rolling hash is a flat `appendCallBegin`/`appendCallEnd` pair around the same return call — no nesting — because there the return leg is a direct top-level `l2ToL1Call`, not a reentrant call happening inside another call's execution.

The rolling hash captures the exact sequence of cross-chain call events, making the execution entry tamper-evident. Any deviation from the pre-committed plan (wrong call order, unexpected reentrant calls) causes the batch to revert.

### Running the E2E Test Locally

The generic local runner handles the whole cycle in one command, from the project root:

```bash
bash script/e2e/run/local.sh script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol
```

This starts two Anvil nodes (L1 on 8545, L2 on 8546), deploys shared infra (`EEZ`, `EEZL2`, a proof system), then auto-discovers and runs every `Deploy*` contract in the file **in file order**: `Deploy` (L1 — `TestToken` + `Bridge` via CREATE2), `DeployL2` (L2 — the `Bridge` twin at the same address, a placeholder `FlashLoanBridgeExecutor`, the pre-computed `WrappedToken` address, `FlashLoanersNFT`), `Deploy2` (L1 — the funded `FlashLoan` pool, the `executorL2` proxy, the real `FlashLoanBridgeExecutor`). It then runs `ExecuteL2` before `Execute` (matching the presence of both contracts in the file), decodes both blocks' events, and — since the script also ships `ComputeExpected` — cross-checks every on-chain hash against the locally recomputed expectation.

Every phase is env-var driven; the runner exports each phase's `console.log("KEY=value")` output as the next phase's input automatically, so nothing is typed by hand in local mode. Run manually (e.g. against a persistent network) with the same contracts, no `--sig`/positional args needed:

```bash
# Deploy (L1) — env: ROLLUPS · outputs: TOKEN, BRIDGE, BRIDGE_SALT
forge script script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol:Deploy \
  --rpc-url $L1_RPC --broadcast --private-key $PK

# DeployL2 (L2) — env: MANAGER_L2, TOKEN, BRIDGE, BRIDGE_SALT · outputs: EXECUTOR_L2, WRAPPED_TOKEN_L2, FLASH_LOANERS_NFT
forge script script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol:DeployL2 \
  --rpc-url $L2_RPC --broadcast --private-key $PK

# Deploy2 (L1) — env: ROLLUPS, TOKEN, BRIDGE, EXECUTOR_L2, WRAPPED_TOKEN_L2, FLASH_LOANERS_NFT · outputs: FLASH_LOAN_POOL, EXECUTOR_L1
forge script script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol:Deploy2 \
  --rpc-url $L1_RPC --broadcast --private-key $PK

# ExecuteL2 (L2) — env: MANAGER_L2 + BRIDGE, TOKEN, EXECUTOR_L1, EXECUTOR_L2, WRAPPED_TOKEN_L2, FLASH_LOANERS_NFT
forge script script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol:ExecuteL2 \
  --rpc-url $L2_RPC --broadcast --private-key $PK

# Execute (L1, same block as the batch post) — env: ROLLUPS, PROOF_SYSTEM, FLASH_LOAN_POOL + scenario addresses
forge script script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol:Execute \
  --rpc-url $L1_RPC --broadcast --private-key $PK
```

The scenario also ships an `ExecuteNetwork` contract, so the same file works unmodified with the generic network runner (`script/e2e/run/network.sh`) against a live devnet — see [`script/e2e/README.md`](https://github.com/eez-association/eez-core-protocol/blob/main/script/e2e/README.md) for that flow.

:::note Real L2 execution, not a table load
`ExecuteL2.run()` doesn't just pre-load the L2 execution table — it calls `EEZL2(managerAddr).executeIncomingCrossChainCall(...)` directly, once per delivery. This is the entry point that atomically loads a one-entry table *and* drives that entry through the destination contract (see `EEZL2.executeIncomingCrossChainCall` in `src/L2/EEZL2.sol`). Running the steps above genuinely mints `WrappedToken` to `executorL2`, claims the NFT, burns the wrapped tokens on the return leg, and fires the reentrant L2→L1 call that `postAndVerifyBatch` / `executor.execute()` then consume for real on L1 — the pool balance, NFT claim, and atomic repayment all actually happen, matching the console output the script prints (`nft claimed by executorL2=true`, `pool balance=10000000000000000000000 (expected 10000000000000000000000)`).
:::

## Key Takeaways

- **Reentrant L2→L1 calls close the loop** — `ExpectedL1ToL2Call` is what brings the tokens back to L1 before the flash loan callback returns, inside the same top-level entry's nested frame.
- **No trusted intermediary** — the ZK proof in `postAndVerifyBatch` attests to the validity of the L2 state transitions; the L1 execution machinery enforces correctness of the on-chain call sequence via the rolling hash.
