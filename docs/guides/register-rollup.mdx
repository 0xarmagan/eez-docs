Registering is a one-time bootstrap step for rollup operators. If you run a based rollup and want its state to be visible to — and callable from — other rollups in the EEZ network, you need to register once on L1 so the central `EEZ` registry can track your state root, own your deferred execution queue, and route cross-chain calls to your rollup. DApp developers and end users do **not** register; they interact with rollups that are already registered. Plan for the registration transaction to be issued by the same party that will operate your proof-system configuration long-term, since the manager you register controls thresholds and verification keys forever after.

Before your rollup can participate in EEZ's cross-chain execution model, you must register it with the central `EEZ` registry contract on L1. Registration is permissionless — anyone can deploy a manager and register it — but you need to wire together three components: a `Rollup.sol` manager contract that holds your proof system configuration, a call to `EEZ.registerRollup` that records your manager in the central registry, and a one-shot callback that writes your assigned `rollupId` back to your manager. Once registered, the registry tracks your rollup's state root and deferred execution queue under that `rollupId`.

## Prerequisites

- An Ethereum L1 node or testnet RPC endpoint
- At least one deployed `IProofSystem`-conforming verifier contract address
- A verification key (`bytes32`) for each proof system you plan to allow
- The address of the deployed `EEZ` registry contract

---

## Steps

### 1. Deploy your `Rollup.sol` manager

Deploy the per-rollup manager with your initial proof system(s), their verification keys, and the batch threshold. The manager holds your proof-system configuration and, after registration, owns the callback that records your assigned `rollupId`.

```solidity
constructor(
    address rollupsRegistry,   // the central EEZ registry on L1
    address _owner,            // owner: can add/remove proof systems, set threshold, set state root
    uint256 _threshold,        // minimum proof systems that must verify each batch (M-of-N)
    address[] memory proofSystems,  // IProofSystem-conforming verifier addresses
    bytes32[] memory vkeys          // verification keys, parallel to proofSystems (non-zero, no duplicates)
)
```

The constructor reverts `InvalidConfig` if `rollupsRegistry` is `address(0)`, if `proofSystems.length != vkeys.length`, or if any `vkey` is zero; it reverts `ProofSystemAlreadyAllowed` on a duplicate proof system. There is no central registry of proof systems — you are responsible for vetting each verifier before adding it.

Deploy it directly with `forge create` (no dedicated deploy script ships in `eez-core-protocol` for a standalone manager — the repo's own scripted deploys, like `DeployEEZL1` in `script/e2e/shared/DeployInfra.s.sol`, are wired for local e2e devnets, not a generic external rollup):

```bash
forge create src/rollupContract/Rollup.sol:Rollup \
  --rpc-url $L1_RPC --private-key $PK --broadcast \
  --constructor-args $EEZ $OWNER $THRESHOLD "[$PROOF_SYSTEM]" "[$VKEY]"
# Outputs: Deployed to: <ROLLUP_CONTRACT address>
```

### 2. Register the manager with the `EEZ` registry

Call `registerRollup` on the central registry, passing your deployed manager and your rollup's genesis state root. The registry assigns the next sequential ID (`++rollupCounter`, starting at `1`; `MAINNET_ROLLUP_ID = 0` is reserved for L1), stores the initial state root, and emits `RollupCreated(rollupId, rollupContract, initialState)`.

```solidity
function registerRollup(address rollupContract, bytes32 initialState)
    external
    returns (uint64 rollupId)
```

Reverts `InvalidRollupContract` if `rollupContract` is `address(0)` or the registry itself.

```bash
cast send $EEZ "registerRollup(address,bytes32)" $ROLLUP_CONTRACT $INITIAL_STATE \
  --rpc-url $L1_RPC --private-key $PK

# Confirm the assigned rollupId and stored state root on-chain:
cast call $EEZ "rollups(uint64)(address,bytes32,uint256)" 1 --rpc-url $L1_RPC
# Returns: (rollupContract, initialState, etherBalance)
```

### 3. The one-shot registration callback (automatic)

As part of the same transaction, `registerRollup` calls back into your manager:

```solidity
function rollupContractRegistered(uint64 _rollupId) external {
    if (msg.sender != ROLLUPS) revert NotEEZRegistry();  // registry-only
    if (rollupId != 0) revert AlreadyRegistered();        // one-shot
    rollupId = _rollupId;
}
```

This writes the assigned `rollupId` into your manager's storage, replacing the `0` "not yet registered" sentinel. It accepts the call only from the registry and only once, so a manager can never be silently re-registered under a different ID. After this fires, the registry tracks your rollup's state root and deferred execution queue under that `rollupId`, and the `rollupContract` pointer is immutable.

## Managing your rollup after registration

### Updating the threshold

Change the minimum required proof systems per batch at any time:

```solidity
function setThreshold(uint256 newThreshold) external onlyOwner
```

```solidity
rollup.setThreshold(2); // now require 2-of-N proof systems per batch
```

Setting the threshold above your current proof system count locks the rollup — no batch can satisfy `checkProofSystemsAndGetVkeys` until you either add more proof systems or lower the threshold. This is intentional: you can use it as an emergency brake.

### Emergency state root override

If you need to set the state root outside of a normal batch cycle, use the owner escape hatch:

```solidity
function setStateRoot(bytes32 newStateRoot) external onlyOwner
```

```solidity
rollup.setStateRoot(newStateRoot);
// internally calls: IEEZRegistry(ROLLUPS).setStateRoot(rollupId, newStateRoot)
```

The registry gates this call three ways: it reverts `NotRollupContract` if the caller isn't the registered manager (`msg.sender == rollups[rollupId].rollupContract`), then applies two temporal lockouts — `SetStateRootNotAllowedDuringExecution` if called while `_insideExecution()` is true (blocks a malicious manager from rewriting state mid-execution via a reentrant proxy path), and `RollupBatchActiveThisBlock` if `lastVerifiedBlock(rollupId) == block.number` (a verified batch already touched this rollup this block). You can only use the escape hatch in blocks where no verified batch has touched your rollup, and never from inside an active execution.

### Ownership transfer

Transfer control of the manager to a new address using the standard OpenZeppelin `Ownable` interface:

```solidity
rollup.transferOwnership(newOwner);
```

The `rollupContract` pointer in the EEZ registry is immutable after registration. Transferring ownership of your `Rollup.sol` does not change what the registry stores — the new owner simply gains control of `addProofSystem`, `removeProofSystem`, `updateVerificationKey`, `setThreshold`, and `setStateRoot` on that same contract.

## Key addresses and IDs

See [`rollupId`](/reference/glossary#rollupid) in the glossary for the full definition, including the `MAINNET_ROLLUP_ID = 0` sentinel and immutability rules.

Your `rollupId` is the single identifier you pass everywhere: `destinationRollupId` in execution entries, the rollup ID argument to `executeL2TX`, and the ID forwarded in cross-chain call hashes. Keep it accessible — your builder node needs it at batch construction time. In your manager's storage, a `rollupId` of `0` doubles as the "not yet registered" sentinel — never use it as a live rollup identifier before the registration callback fires.
