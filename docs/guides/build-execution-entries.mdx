Every cross-chain interaction in EEZ is described by an `ExecutionEntry` struct that you — or your builder node — construct off-chain before posting a batch. An entry is a pre-simulated, proof-bound record of a cross-chain call: it declares what calls will execute, in what order, with what return data, and produces a single `rollingHash` that the on-chain protocol verifies after execution completes. Building entries correctly means simulating the full execution graph in advance, recording every call result and every nesting boundary, and encoding that simulation as the arrays and hash the contract expects.

Reentrant reads and reentrant calls that revert are **not** a separate struct anymore — they're rows of the same unified reentrant table described below, distinguished only by which key they were built from and their own `success` flag. See [Reading Cross-Chain State with Static Entries](/guides/lookup-calls) for the full resolution mechanics of the STATIC and REVERTED kinds; this guide focuses on building entries and their plain-success reentrant calls.

## The `ExecutionEntry` struct

The L1 and L2 execution structs share the same conceptual shape but have different field sets. On L1, entries carry state-root updates and routing information that L2 entries omit.

### L1 entry (`IEEZ.sol`)

```solidity
struct ExecutionEntry {
    // Per-rollup state updates — the entry's full state transition (≥1, enforced on-chain).
    // The prover asserts stateUpdates.length >= 1 — an empty array leaves the entry unpinned
    // from any rollup trajectory (no StateRootMismatch backstop). Strictly increasing by rollupId.
    StateUpdate[] stateUpdates;

    // bytes32(0) = L2Tx (immediate entry, drained inline by postAndVerifyBatch, or consumed
    // by executeL2Txs). Non-zero = deferred entry, consumed by executeCrossChainCall when the
    // live cross-chain call hash matches this value.
    bytes32 proxyEntryHash;

    // The entry's TOP-LEVEL calls only — reentrant frames carry their OWN sub-array inside
    // expectedL1ToL2Calls[i].l2ToL1Calls. No shared partition, no callCount.
    L2ToL1Call[] l2ToL1Calls;

    // Unified reentrant table: every kind of reentrant frame — plain SUCCESS, read-only
    // STATIC, and try/catch'd REVERTED — content-addressed by expectedL1toL2Hash.
    ExpectedL1ToL2Call[] expectedL1ToL2Calls;

    // Expected rolling hash after all calls and nestings complete.
    // On-chain checked: if (_rollingHash != entry.rollingHash) revert RollingHashMismatch()
    bytes32 rollingHash;

    // Which rollup's queue this entry routes to; must be ∈ stateUpdates (EntryDestinationNotInStateUpdates).
    uint64 destinationRollupId;

    // false = the entry runs, is verified, then reverts with returnData (all effects roll back).
    // true = executeCrossChainCall returns returnData regardless of inner-call outcomes.
    bool success;

    // Pre-computed top-level return value (or the revert payload when !success).
    bytes returnData;
}
```

### L2 entry (`IEEZL2.sol`)

The L2 struct is deliberately leaner. It has no `stateUpdates` (L2 has no state-root tracking), no `destinationRollupId` (a single rollup), and uses self-relative directional names because the counterparty can be L1 or another L2:

```solidity
struct ExecutionEntry {
    // Hash of the inbound call — never bytes32(0) on L2 (executeL2Txs is L1-only).
    bytes32 proxyEntryHash;

    // All calls this entry executes on this L2, flat, top-level only.
    CrossChainCall[] incomingCalls;

    // Unified reentrant (outgoing) table — same three kinds as L1's expectedL1ToL2Calls.
    ExpectedOutgoingCrossChainCall[] expectedOutgoingCalls;

    bytes32 rollingHash;
    bool success;
    bytes returnData;
}
```

`CrossChainCall` (`IEEZL2.sol`) is field-for-field identical to L1's `L2ToL1Call` — only the type name differs.

## What an entry represents

An entry is the complete pre-simulated record of one top-level cross-chain interaction. Before you can build an entry, you must simulate the full execution graph:

- Run the destination call and record its return data
- Detect any reentrant cross-chain calls the destination makes and recurse
- Record every call's success/failure flag and return data in execution order
- Record every nesting boundary (when control enters and exits a reentrant frame)

The `rollingHash` you compute from this simulation is what binds the proof to the actual on-chain execution. If a single call returns different data than you recorded, or a nesting boundary is folded with the wrong identity hash, the `rollingHash` check reverts the entry.

## Supporting structs

### `StateUpdate` (L1 only)

Each `StateUpdate` in `stateUpdates[]` represents one rollup's state transition caused by this entry. The `currentState` field is checked against `rollups[rollupId].stateRoot` at consumption time — a mismatch reverts `StateRootMismatch(rollupId)`.

```solidity
struct StateUpdate {
    uint64  rollupId;      // which rollup's state changes
    bytes32 currentState;  // expected pre-state root: must match rollups[rollupId].stateRoot at consumption
    bytes32 newState;      // post-execution state root applied after the entry completes
    int256  etherDelta;    // signed ETH balance change for this rollup (positive = deposit, negative = withdrawal)
}
```

Every L1 entry must include **at least one** `StateUpdate` — enforced on-chain (`EntryHasNoStateUpdates`), not left to prover convention. `stateUpdates` must be strictly increasing by `rollupId`, starting above `MAINNET_ROLLUP_ID` (`StateUpdatesNotStrictlyIncreasing`) — this rejects duplicates and a mainnet delta in the same motion. `stateUpdates` also doubles as the entry's proxy-protection set: every call source and every reentrant/static-read target must be one of these rollups (`CallSourceNotVerified` / `ReentrantDestinationNotVerified`).

### `L2ToL1Call`

Each element of `l2ToL1Calls[]` is one top-level call. Every reentrant frame carries its **own** sub-array of the same type — there is no shared flat array or `callCount` partition to maintain; each frame's array is run to completion by its own resolver.

```solidity
struct L2ToL1Call {
    uint16  revertNextNCalls; // 0 = normal; N > 0 = force-revert the next N calls' state effects (this one included)
    bool    isStatic;         // if true, dispatched via STATICCALL — no state writes, zero value
    uint64  gas;              // gas limit for the target call; 0 = forward all remaining gas
    address sourceAddress;    // identity of the caller on the source rollup
    uint64  sourceRollupId;   // which rollup the caller originates from
    address targetAddress;    // contract called on the target rollup
    uint256 value;            // ETH sent with the call
    bytes   data;             // calldata (selector + encoded arguments)
}
```

The L2 mirror, `CrossChainCall`, is field-for-field identical — only the struct name differs. Every executed call's `sourceRollupId` must be in the entry's `stateUpdates` — enforced at batch validation (`CallSourceNotVerified`), not at runtime.

### `revertNextNCalls`: forced-revert context

`revertNextNCalls > 0` on a call marks a **forced revert**: the next `revertNextNCalls` calls — this one included — execute and succeed normally, but their EVM state effects are rolled back at the protocol layer. The rolling hash still commits to what actually happened (typically `success=true` with the real return data); only the destination state disappears.

`revertNextNCalls` covers a **contiguous** run of calls within one call array (the entry's top-level array, or one reentrant frame's own sub-array), and only the *first* call in that run carries the nonzero value. Nesting one span inside another is a prover-convention violation, not an on-chain check — the processor would mechanically recurse, but the outer span's rollback already discards whatever the inner span would have rolled back, so a well-formed prover never emits one.

`revertNextNCalls` is used whenever the prover determines a call is reverted in the destination chain's view, even though the destination call itself succeeds. The canonical case is a cross-chain call from rollup A to rollup B where B's destination call **succeeds**, but the prover's view of A shows the higher-level transaction containing the call was rolled back on A. B must not retain state that A no longer commits to, so the entry wraps the call in `revertNextNCalls = 1`.

The processor (`_processNCalls`):

1. Checks `i + revertNextNCalls <= calls.length` — else `RevertSpanOutOfBounds(start, span, length)`.
2. Zeroes `calls[i].revertNextNCalls` in its throwaway memory copy (the flat-call array is `memory`-only throughout — entries are never SSTOREd for this walk), so the isolated re-run sees the call as normal.
3. Slices the span into a fresh memory array (`_sliceL2ToL1Calls`) and self-calls `executeInContextAndRevert(span)`, which processes the span through the same call processor and then **always** reverts with `error ContextResult(bytes32 rollingHash, uint256 reentrantConsumed, uint256 callsProcessed)`.
4. The EVM revert rolls back every state effect and transient write inside the self-call — including the rolling hash and the reentrant cursor.
5. The caller decodes `ContextResult` and re-applies the rolling hash and cursor exactly as they stood at the end of the reverted span; a `CALL_NOT_FOUND` divergence observed inside the span rides out the same way, so it still fails the entry at its boundary.
6. Emits `CallsReverted(entryIndex, startIndex, span)` and skips past the span.

> **For builders:** the self-call target is `executeInContextAndRevert(L2ToL1Call[] memory calls)` (L2: `executeInContextAndRevert(CrossChainCall[] memory calls)`), guarded by `if (msg.sender != address(this)) revert NotSelf();` — it takes the sliced span itself, not a call count. `ContextResult` is declared once on the shared `src/base/EEZBase.sol` with three fields (`rollingHash`, `reentrantConsumed`, `callsProcessed`); both L1 (`src/EEZ.sol`) and L2 (`src/L2/EEZL2.sol`) always pass `callsProcessed = 0` — the field exists only so the decoder is shared between the two identically-shaped reverts.

#### When `revertNextNCalls` is the right tool

Use `revertNextNCalls > 0` only when a call **would succeed** but its state must not survive. For a destination that naturally reverts, `revertNextNCalls = 0` is correct and simpler: the proxy `.call` already returns `(success=false, retData)`, `CALL_END` hashes that outcome, and the destination's own revert rolls back its own state. Wrapping a single naturally-reverting call in `revertNextNCalls = 1` produces the same rolling hash and the same on-chain state as `revertNextNCalls = 0` — it just adds an extra self-call frame for nothing.

Reentrant calls that revert (a destination that `try/catch`es a reentrant cross-chain call) take a third, distinct path — a `success = false` row in the unified reentrant table — never `revertNextNCalls`, never a plain-success `ExpectedL1ToL2Call`. Four situations, four tools:

| Situation | Tool |
| --- | --- |
| Top-level call that naturally reverts, or a natural inner revert of a non-reentrant call | Plain call with `revertNextNCalls = 0`; `CALL_END(false, retData)` captures it (or, at the top level, `ExecutionEntry` with `success = false`) |
| Reentrant call that succeeds | `success = true` row in the unified reentrant table |
| Reentrant call that reverts (caller wraps it in `try/catch`) | `success = false` row in the unified reentrant table |
| Reentrant `STATICCALL` (read-only), or a top-level static read | STATIC-kind row / `StaticExecutionEntry` — see [Static Entries](/guides/lookup-calls) |
| Successful call(s) whose state must be force-reverted | `revertNextNCalls > 0` on the first call of the span |

### `ExpectedL1ToL2Call` — the unified reentrant table

Each element of `expectedL1ToL2Calls[]` is a row of **one** table that serves three kinds: plain SUCCESS, read-only STATIC, and try/catch'd REVERTED. `_consumeNestedCall` and `staticCrossChainCall` both match sequentially against this array when the destination contract calls back through a proxy during entry execution.

```solidity
struct ExpectedL1ToL2Call {
    bytes32 expectedL1toL2Hash;          // position key: keccak256(crossChainCallHash, expectedRollingHash)
    L2ToL1Call[] l2ToL1Calls;            // this row's OWN sub-calls, run to completion
    bytes32 revertedOrStaticRollingHash; // expected sub-call hash — checked only for STATIC / REVERTED kinds
    bool success;                        // whether resolution returns or reverts
    bytes returnData;                    // returned on success / reverted-with when !success
}
```

There is **no kind selector** on the row. STATIC vs CALL is decided entirely by which key matched (`crossChainCallHash` folds `isStatic`), and SUCCESS vs REVERTED within the CALL kind is just the row's own `success` flag. For a plain SUCCESS row, `revertedOrStaticRollingHash` is unused — set it to `bytes32(0)`.

**This guide covers building SUCCESS rows.** For a SUCCESS row, `_resolveNestedReentrant` runs the row's own `l2ToL1Calls[]` between `NESTED_BEGIN`/`NESTED_END`, folding into the host's continuous `rollingHash`, then returns `returnData`. A reentrant call that must revert, or a reentrant read, is a different kind of row entirely — see [Reading Cross-Chain State with Static Entries](/guides/lookup-calls) for their full match keys and resolution mechanics.

## Computing the `crossChainCallHash`

Every cross-chain call is identified by a deterministic hash of eight fields. Both on-chain contracts and off-chain tooling compute the same value from the same preimage.

```solidity
// src/base/EEZBase.sol — computeCrossChainCallHash
crossChainCallHash = keccak256(abi.encode(
    bool    isStatic,        // true = read-only STATICCALL key; false = state-changing call key
    address sourceAddress,   // the caller's identity on the source rollup
    uint64  sourceRollupId,  // the rollup the caller originates from
    address targetAddress,   // the contract being called on the target rollup
    uint64  targetRollupId,  // the rollup where the call executes
    uint256 value,           // ETH value sent (0 for static calls)
    uint64  callGas,         // 0 everywhere except calls LEAVING an L2 under USE_GAS_LEFT
    bytes   data              // calldata: selector + ABI-encoded arguments
))
```

The on-chain `EEZ`/`EEZL2` contracts expose this as `computeCrossChainCallHash(...)` — a `public pure` function (defined once on the shared `EEZBase`) you can call off-chain for verification. `callGas` is `0` at every keying site except a call leaving an L2 under `USE_GAS_LEFT` (a production-mode toggle); every fixture and current deployment runs `useGasLeft = false`, so build every key with `callGas = 0`.

The `E2EHelpers.sol` script library provides a free function that bakes `callGas = 0`:

```solidity
// From script/e2e/shared/E2EHelpers.sol
function crossChainCallHash(
    bool isStatic,
    address sourceAddress,
    uint256 sourceRollupId,
    address targetAddress,
    uint256 targetRollupId,
    uint256 value,
    bytes memory data
) pure returns (bytes32) {
    return keccak256(
        abi.encode(isStatic, sourceAddress, sourceRollupId, targetAddress, targetRollupId, value, uint256(0), data)
    );
}
```

### Hash semantics by entry point

| Entry point | `isStatic` | `sourceAddress` | `sourceRollupId` | `targetAddress` | `targetRollupId` | `value` | `callGas` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `executeCrossChainCall` (L1 proxy) | `false` | proxy's caller | `MAINNET_ROLLUP_ID` (0) | proxy's `originalAddress` | proxy's `originalRollupId` | `msg.value` | `0` |
| `executeCrossChainCall` (L2 proxy) | `false` | proxy's caller | this L2's `ROLLUP_ID` | proxy's `originalAddress` | proxy's `originalRollupId` | `msg.value` | `gasleft()` if `USE_GAS_LEFT`, else `0` |
| Reentrant call (matches a row in the unified table) | same as the `executeCrossChainCall` row for the chain making the call | same | same | same | same | same | same |
| `executeL2Txs` | n/a — entry has `proxyEntryHash == bytes32(0)` | — | — | — | — | — | — |
| `staticCrossChainCall` (both chains) | `true` | proxy's caller | this chain's rollup ID | proxy's `originalAddress` | proxy's `originalRollupId` | `0` | `0` |
| Flat-call `CALL_BEGIN` fold (both chains) | `call.isStatic` | `call.sourceAddress` | `call.sourceRollupId` | `call.targetAddress` | executing chain's own ID | `call.value` | `0` |

Nothing else (caller depth, parent frame, position in the entry) feeds into the hash — position is pinned separately, by the rolling hash folded into the reentrant table's key (below).

For the counter example from the e2e scripts, the L1-to-L2 cross-chain call hash is:

```solidity
bytes32 hash = crossChainCallHash(
    false,                    // state-changing call
    counterAndProxy,          // caller on L1
    MAINNET_ROLLUP_ID,        // caller originates from L1 (0)
    counterL2,                // Counter contract on L2
    L2_ROLLUP_ID,              // call executes on L2
    0,                         // no ETH
    abi.encodeWithSelector(Counter.increment.selector)
);
```

This same hash is used as `proxyEntryHash` in the L1 entry, as `proxyEntryHash` in the L2 mirror entry, and as the call hash the L1 proxy presents to `executeCrossChainCall` at runtime. Both sides always compute the same value because the eight inputs are identical.

## Computing the `rollingHash`

The `rollingHash` is a single `bytes32` accumulator that commits to every call result and every nesting boundary in the entry's execution. It is **seeded** with the entry's starting state + identity, then updated at five tagged events. To build the correct `rollingHash` for any entry, simulate the execution graph and apply each event in the order the on-chain protocol produces them.

### The entry-begin seed

```text
seed (L1)  statesHash   = fold over stateUpdates: keccak256(prev, rollupId_i, currentState_i), from bytes32(0)
           _rollingHash = keccak256(statesHash, proxyEntryHash)
seed (L2)  _rollingHash = keccak256(bytes32(0), proxyEntryHash)   // no state deltas on L2
```

This is a mandatory first step (`_rollingHashEntryBegin` on L1, the equivalent `entryBeginL2` seed on L2) — it reverts `RollingHashNotCleared` if the accumulator isn't already zero, so every entry starts from a clean slate that binds its starting state and identity, not just its call results.

### The five tagged events

```text
CALL_BEGIN     = 1   keccak256(prev, uint8(1), crossChainCallHash)
CALL_END       = 2   keccak256(prev, uint8(2), success, returnData)
NESTED_BEGIN   = 3   keccak256(prev, uint8(3), crossChainCallHash)
NESTED_END     = 4   keccak256(prev, uint8(4))
CALL_NOT_FOUND = 5   keccak256(prev, uint8(5), crossChainCallHash)
```

- **`CALL_BEGIN`**: emitted when the processor starts a call, folding the call's **identity hash** (its `crossChainCallHash`) — not a call number. This binds *which* call ran, not just its result.
- **`CALL_END`**: emitted when the call completes. `success` is the `bool` from the proxy's `.call`/`.staticcall`, and `returnData` is the full ABI-encoded return payload.
- **`NESTED_BEGIN`**: emitted when a reentrant frame starts, folding the reentrant call's identity hash.
- **`NESTED_END`**: emitted when a SUCCESS reentrant frame closes into the host's continuous hash (a REVERTED frame never reaches `NESTED_END` — its terminal revert rolls the frame back before it gets there).
- **`CALL_NOT_FOUND`**: emitted when a reentrant call finds no matching row in the table. This diverges the hash from what the entry's proof committed to, so the entry later fails `RollingHashMismatch` — it survives any intermediate `try/catch`.

No call/frame index is folded in anywhere: `_rollingHash` is a chain, so order, count, and nesting are already bound by the chain itself plus the tags — an explicit index would be redundant, and omitting it is what lets a `revertNextNCalls` span be processed as a self-contained sub-slice without diverging the hash from a continuous run.

### Walk-through: simple entry with no reentry

Use `RollingHashBuilder` to build the hash in the same order the on-chain processor produces events. This matches the counter e2e script's L2 entry exactly — one call that returns `abi.encode(uint256(1))`:

```solidity
bytes32 proxyEntryHash = crossChainCallHash(false, counterAndProxy, MAINNET_ROLLUP_ID, counterL2, L2_ROLLUP_ID, 0, incrementCallData);

bytes32 rh = RollingHashBuilder.entryBeginL2(proxyEntryHash);        // seed
rh = RollingHashBuilder.appendCallBegin(rh, proxyEntryHash);          // same call, so same hash
rh = RollingHashBuilder.appendCallEnd(rh, true, abi.encode(uint256(1)));
// rh is now entries[0].rollingHash
```

Adapting the "L2→L1→L2" pattern from `EXECUTION_ENTRY_SPEC.md`: Alice on L2 calls A's proxy on L2 (A lives on L1). While A executes on L1, it calls B's proxy on L1 (B lives on L2) — a reentrant call that succeeds with an empty sub-array:

```text
CALL_BEGIN(ccHash of Alice → A)
  NESTED_BEGIN(ccHash of A → B)
  NESTED_END
CALL_END(true, <A's return>)
```

For this example, on the L1 side (an immediate L2Tx entry):

- `l2ToL1Calls = [{ src: Alice, srcRollup: L2, dest: A, value: 0, data: callBProxy }]` — the entry's one top-level call.
- `expectedL1ToL2Calls = [{ expectedL1toL2Hash: keccak256(hash(A → B) ‖ fireHash), l2ToL1Calls: [], revertedOrStaticRollingHash: 0, success: true, returnData: abi.encode(1) }]`, where `fireHash` is the live `_rollingHash` right after `CALL_BEGIN` of the Alice → A call — the exact point A's reentrant call to B fires.
- Because A's reentrant call succeeds with no sub-calls of its own, `NESTED_BEGIN` is immediately followed by `NESTED_END` — there's nothing to fold in between.

There is no `callCount` partition to check anymore — each frame's array (the entry's own `l2ToL1Calls[]`, and the reentrant row's own `l2ToL1Calls[]`) is run to completion structurally. Completeness of SUCCESS rows rests entirely on the rolling hash: a skipped SUCCESS row omits its `NESTED_BEGIN`/`NESTED_END` fold and diverges the hash from what the proof committed to.

## The `E2EHelpers` utility library

The `script/e2e/shared/E2EHelpers.sol` file provides utilities that eliminate manual hash construction errors.

### `crossChainCallHash` free function

Computes the canonical call hash from individual fields (shown above). A `crossChainCallHashStatic(...)` convenience wrapper folds `isStatic = true` for read-only keys.

### `RollingHashBuilder` library

Reproduces the exact tagged-hash sequence `EEZBase`'s fold helpers produce on-chain:

```solidity
library RollingHashBuilder {
    function entryBegin(StateUpdate[] memory deltas, bytes32 proxyEntryHash) internal pure returns (bytes32);
    function entryBeginL2(bytes32 proxyEntryHash) internal pure returns (bytes32);

    function appendCallBegin(bytes32 prev, bytes32 ccHash) internal pure returns (bytes32);
    function appendCallEnd(bytes32 prev, bool success, bytes memory retData) internal pure returns (bytes32);
    function appendNestedBegin(bytes32 prev, bytes32 ccHash) internal pure returns (bytes32);
    function appendNestedEnd(bytes32 prev) internal pure returns (bytes32);
    function appendCallNotFound(bytes32 prev, bytes32 ccHash) internal pure returns (bytes32);

    function appendStatic(bytes32 prev, bool success, bytes memory retData) internal pure returns (bytes32);
}
```

Every `append*` helper takes the call's `crossChainCallHash`, not a call number — matching the on-chain fold exactly. `appendCallNotFound` reproduces the divergent `CALL_NOT_FOUND` tag for testing no-match scenarios; `appendStatic` reproduces the untagged static-call accumulator (see [Static Entries](/guides/lookup-calls)).

### Empty-array helpers

`E2EHelpers.sol` also exports free functions that return typed empty arrays, saving boilerplate in entry construction:

```solidity
noStaticEntries()     // → StaticExecutionEntry[]              (L1, empty)
noNestedActions()     // → ExpectedL1ToL2Call[]                (L1, empty)
noCalls()             // → L2ToL1Call[]                        (empty)

noL2StaticEntries()   // → L2 StaticExecutionEntry[]           (IEEZL2, empty)
noL2OutgoingCalls()   // → ExpectedOutgoingCrossChainCall[]     (IEEZL2, empty)
noL2Calls()           // → CrossChainCall[]                    (IEEZL2, empty)
```

Solidity can't overload free functions by return type alone, so the `IEEZL2`-typed empties get an `L2` infix.

## Full example: the counter scenario

The counter e2e script (`script/e2e/one_way/L1_to_L2/counter/E2ECounter.s.sol`) builds both sides of an L1→L2 cross-chain `Counter.increment()` call — the current canonical simple example. The L1 entry carries the state update and cached return data; the L2 mirror entry carries the actual call that drives `Counter.increment()` on the L2 instance.

### L1 entry

```solidity
function _l1Entries(address counterL2, address counterAndProxy)
    internal
    pure
    returns (ExecutionEntry[] memory entries)
{
    StateUpdate[] memory deltas = new StateUpdate[](1);
    deltas[0] = StateUpdate({
        rollupId: L2_ROLLUP_ID,
        currentState: keccak256("l2-initial-state"),
        newState: keccak256("l2-state-after-counter"),
        etherDelta: 0
    });

    bytes32 proxyEntryHash = _callHash(counterL2, counterAndProxy);
    bytes32 rh = RollingHashBuilder.entryBegin(deltas, proxyEntryHash);

    entries = new ExecutionEntry[](1);
    entries[0] = ExecutionEntry({
        stateUpdates:         deltas,
        proxyEntryHash:       proxyEntryHash,
        destinationRollupId:  L2_ROLLUP_ID,
        l2ToL1Calls:          noCalls(),          // no calls execute on L1 side
        expectedL1ToL2Calls:  noNestedActions(),  // no reentrant calls
        rollingHash:          rh,                 // no calls → the hash is just the entry-begin seed
        success:              true,
        returnData:           abi.encode(uint256(1)) // cached result of increment()
    });
}
```

The L1 entry has an empty `l2ToL1Calls[]` because no calls execute on L1 — the entry is purely a state-update carrier and cached-return-data store, so its `rollingHash` is just the entry-begin seed with no folds. `proxyEntryHash` is the call hash the L1 proxy will present to `executeCrossChainCall` at runtime.

### L2 entry (mirror)

```solidity
function _l2Entries(address counterL2, address counterAndProxy)
    internal
    pure
    returns (L2ExecutionEntry[] memory entries)
{
    CrossChainCall[] memory calls = new CrossChainCall[](1);
    calls[0] = CrossChainCall({
        gas:            0,
        revertNextNCalls: 0,
        isStatic:       false,
        sourceAddress:  counterAndProxy,   // the L1 caller's identity
        sourceRollupId: MAINNET_ROLLUP_ID,
        targetAddress:  counterL2,
        value:          0,
        data:           abi.encodeWithSelector(Counter.increment.selector)
    });

    bytes32 proxyEntryHash = _callHash(counterL2, counterAndProxy);
    bytes32 ccHash = _callHash(counterL2, counterAndProxy); // same call — same hash on both sides
    bytes32 rh = RollingHashBuilder.entryBeginL2(proxyEntryHash);
    rh = RollingHashBuilder.appendCallBegin(rh, ccHash);
    rh = RollingHashBuilder.appendCallEnd(rh, true, abi.encode(uint256(1)));

    entries = new L2ExecutionEntry[](1);
    entries[0] = L2ExecutionEntry({
        proxyEntryHash:        proxyEntryHash,
        incomingCalls:         calls,
        expectedOutgoingCalls: new ExpectedOutgoingCrossChainCall[](0),
        rollingHash:           rh,
        success:               true,
        returnData:            abi.encode(uint256(1))
    });
}
```

`proxyEntryHash` is **identical** on both sides — the same eight hash inputs produce the same `bytes32`. This is the link that lets the L1 registry verify the entry matches the incoming proxy call, while the L2 system delivers the real execution. `Execute` posts the L1 entry via `postAndVerifyBatch` and calls `CounterAndProxy.incrementProxy()` in the same block; `ExecuteL2` loads the L2 entry via `executeIncomingCrossChainCall`. See [Post and Verify a Batch](/guides/post-verify-batch) for how the L1 side reaches the chain.

## Common errors and how to avoid them

| Error | Cause | Fix |
| --- | --- | --- |
| `RollingHashMismatch` | Wrong call order, wrong return data, a missing/misplaced `NESTED_BEGIN`/`NESTED_END`, or a `CALL_NOT_FOUND` divergence from a reentrant call your simulation didn't account for | Re-simulate the execution graph and rebuild the rolling hash step by step with `RollingHashBuilder` |
| `RevertSpanOutOfBounds(start, span, length)` | A `revertNextNCalls` span extends past the end of its call array | Ensure `i + revertNextNCalls <= calls.length` for every span |
| `EntryHasNoStateUpdates` | `entry.stateUpdates` is empty | Every L1 entry needs at least one `StateUpdate` |
| `StateUpdatesNotStrictlyIncreasing(rollupId)` / `EntryDestinationNotInStateUpdates(rollupId)` | `stateUpdates` isn't strictly ascending, or `destinationRollupId` isn't among the entry's own updates | Sort `stateUpdates` by `rollupId`; route `destinationRollupId` to a rollup the entry actually proved |
| `StateRootMismatch(rollupId)` | A `StateUpdate.currentState` doesn't match the live state root at consumption | Rebuild the entry with the correct pre-state root for each rollup |
| `ExecutionNotFound` | `proxyEntryHash` doesn't match the live call hash, or a reentrant/static call found no matching row in the table | Verify all eight `crossChainCallHash` inputs — `isStatic`, addresses, rollup IDs, `value`, `callGas`, `data` |
| `CallSourceNotVerified(rollupId)` / `ReentrantDestinationNotVerified(rollupId)` | A call's source, or a reentrant/static-read target, isn't one of the entry's `stateUpdates` rollups | Add a `StateUpdate` for every rollup the entry drives proxies against |

There is no completeness check on `l2ToL1Calls[]` or `expectedL1ToL2Calls[]` length anymore — each frame's array is run to completion structurally, and the unified reentrant table may legitimately contain unused STATIC/REVERTED rows. Completeness of SUCCESS rows is enforced purely by the rolling hash, not by a length comparison.
