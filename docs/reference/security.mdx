This page explains the mechanisms EEZ relies on to keep a cross-chain call trustworthy, and states plainly what has and hasn't been independently verified. For the itemized list of known edge cases and limitations, see [Caveats](/reference/caveats) — this page covers the security *architecture*, not the full limitations list.

## Audit status

**EEZ has not undergone a third-party security audit.** There is no bug bounty program at this time. The protocol is early-stage: interfaces, storage layout, and execution semantics are still in flux (see the warning above, shown on every page that describes contract behavior). Do not deploy EEZ contracts with real funds, and do not use the [`AcceptAllProofSystem`](/reference/glossary#acceptallproofsystem) mock outside local test networks — it accepts every proof unconditionally and provides no verification guarantee whatsoever. The proof system EEZ deployments actually run today, `ECDSAProofSystem`, is itself a placeholder — it recovers a single trusted signer's address from an ECDSA signature over the batch's public inputs hash, in place of a ZK verifier. See [`IProofSystem`](/contracts/interfaces/iproofsystem) for the interface every proof system implements, and [Multi-Prover Model](/concepts/multi-prover) for how it plugs into the M-of-N threshold model.

This page will be updated once an audit is scheduled or completed. Until then, treat every claim below as "this is how the code is designed to behave," not "this has been independently verified."

## Multi-prover verification model

EEZ does not trust a single proof system. A batch carries a globally sorted list of proof system addresses and one proof per proof system; each participating rollup independently selects the subset of proof systems it accepts via an M-of-N threshold configured on its own [`Rollup.sol`](/contracts/rollup) manager. This means:

- Different rollups can use entirely different proof systems (ZK-SNARKs, ZK-STARKs, optimistic fraud proofs, or even a trusted multi-sig) while sharing the same batch and overhead.
- A rollup operator controls their own trust assumptions — raising the threshold or requiring specific proof systems is a local decision, not a protocol-wide one.
- The public inputs hash each proof system verifies is constructed so that proof systems with disjoint rollup memberships produce different public inputs — a proof cannot be replayed against a proof system it wasn't generated for.

See [Multi-Prover Model](/concepts/multi-prover) for the full accumulator construction and [IProofSystem](/contracts/interfaces/iproofsystem) for the interface every proof system must implement.

## Rolling hash integrity

Every execution entry and lookup call carries a `rollingHash` — a cumulative Keccak fold over every call event in execution order. Execution replays every call and checks the accumulated hash against the pre-committed value; any divergence (wrong return data, an extra call, a missing nesting boundary, reordered operations) reverts the entire entry with `RollingHashMismatch`. There is no path through which execution can silently diverge from what the proof committed to.

See [Rolling Hash](/concepts/rolling-hash) for the exact tagged-event formulas.

## State-root content addressing

Every entry's [`StateDelta`](/reference/glossary#statedelta) is checked against the target rollup's current on-chain state root before it's allowed to apply, and reverts `StateRootMismatch` on any mismatch. This prevents a stale or reordered entry — one computed against state that no longer matches the chain — from silently applying against the wrong state.

## What this model does not cover

The mechanisms above guarantee that *if* a proof verifies, the execution it attests to is applied exactly as committed. They do not, on their own, guarantee that:

- Any individual proof system is itself sound (that's the proof system's responsibility, not the registry's — see [Multi-Prover Model](/concepts/multi-prover)).
- The off-chain sequencer that pre-computes execution traces is honest or live (see [Caveats](/reference/caveats) for queue-blocking and liveness edge cases).
- The contracts are free of implementation bugs — which is precisely what an audit exists to check, and which hasn't happened yet.

If you find a security issue, treat it with the same caution you would for any pre-audit, unaudited contract system, and avoid disclosing exploit details in public channels (e.g. GitHub issues) until the team has a chance to respond.
