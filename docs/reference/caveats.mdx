EEZ is a synchronous cross-rollup protocol with a number of edge cases that you must understand before building on it. Some of these are fundamental constraints of the execution model; others are deliberate simplifications that will be addressed as the protocol matures. Read this page carefully before deploying any production-facing code.

:::warning
EEZ is an **early-stage, unaudited implementation**. Interfaces, storage layout, and execution semantics are still in flux. Do not use EEZ contracts with real funds until a full security audit has been completed and the protocol is declared stable.
:::

## Queue Blocking on Revert

:::note
Match-time failures are skipped; only an already-matched entry that reverts mid-execution blocks the queue.
:::

Consumption forward-scans the queue (`_findMatchingEntry`) for the first entry matching identity (`proxyEntryHash`), routing (`destinationRollupId`), **and** state preconditions (every [`StateUpdate`](/reference/glossary#stateupdate)`.currentState` equal to the live root). A non-matching candidate is skipped cleanly — the cursor moves past it and it never executes. This means **you CAN stack multiple candidate entries** in a persistent queue, each gated by a different `currentState`: only the one matching the live state root is consumed, and the others are skipped without any transaction reverting. If none of the candidates match, the call reverts `ExecutionNotFound`.

The blocking behavior applies only to an entry that has **already matched** identity, routing, and state — and then reverts mid-execution (for example, `RollingHashMismatch` or `EtherDeltaMismatch`). That case reverts the whole consuming transaction **without** advancing the queue cursor: the entry remains at the front of the queue, and a retry re-matches the same entry.

**The `IMMEDIATE` prefix is more forgiving still** — see [Immediate entry skip](/reference/glossary#immediate-entry-skip). `_attemptExecuteImmediateL2Txs` wraps each leading immediate entry in a `try/catch`, so a reverting immediate entry emits `L2TxSkipped` and the cursor advances (though if the immediate run is non-empty and every entry in it reverts, the whole post is unwound with `AllImmediateL2TxsFailed`).

Build your persistent execution entries so their `StateUpdate.currentState` gates correctly reflect the state root(s) you expect at consumption time, and design intentionally if you want to stack alternatives gated on different roots.

## Transient-Phase Isolation

:::note
Cross-rollup interactions inside the [meta hook](/reference/glossary#meta-hook) are only supported between rollups verified **together in the same batch**. Interactions with any other rollup must wait for persistent consumption.
:::

While a `postAndVerifyBatch` is mid-flight (during the immediate-entry drain and the meta-hook window), EEZ routes **all** resolution exclusively from that batch's own transient tables:

- Execution entries are consumed from the batch's own transient cursor.
- Top-level lookups never fall through to the persistent queues.

A rollup that was verified by an earlier batch in the same block passes the block gate, but any call to it during the hook will miss with `ExecutionNotFound`. Consequence:

- **Do** batch all rollups you need to interact with synchronously into the same `postAndVerifyBatch` call.
- **Do not** expect to reach rollups verified in separate earlier transactions during the meta hook.
- Cross-rollup interactions that span separate batches must use the persistent queue path (enqueue entries, consume in a later transaction).

## Indistinguishable Revert Reasons from a Proxy

When you call a `CrossChainProxy` and the call reverts, you cannot distinguish between these two causes:

1. The execution table did not contain a matching entry for this call.
2. The underlying destination contract call itself reverted.

Both cases surface as a revert from the proxy with no additional context distinguishing the source. If your code needs to handle these differently, you must design around this limitation — for example, by pre-checking that an entry exists before making the call, or by using a lookup call to probe the remote state first.

## Opcode Differences When Using Proxies

When a call is routed through a `CrossChainProxy`, certain EVM opcodes return information about the **proxy** itself rather than the proxied contract:

- `DELEGATECALL` — executes in the proxy's context.
- `BALANCE` — returns the proxy's ETH balance, not the proxied contract's.
- `EXTCODESIZE` — returns the proxy's code size.
- `EXTCODECOPY` — copies the proxy's bytecode.

:::warning
Do not rely on any of these opcodes to inspect the remote contract from the caller's side. If you need the remote contract's code or balance, use a dedicated cross-chain view call or lookup.
:::

Block-state opcodes also reflect the chain where the call is currently executing, not the chain the call originated from:

- `BLOCKNUMBER`, `BLOCKHASH`, `BLOCKGASLIMIT`, `CHAINID`, `COINBASE`, and similar block context opcodes reflect the **destination chain's** values.

This means that the same logical action observed on L1 vs. L2 will see different values for these opcodes. Do not use block-context opcodes to infer cross-chain ordering or to derive timestamps that must be consistent across chains.

## Block Gating: Entries Are Valid for One Block Only

Execution entries posted in a `postAndVerifyBatch` are **only consumable within the same L1 block** they were posted. The `RollupVerification.lastVerifiedBlock` field doubles as a read gate: `executeCrossChainCall` and `executeL2Txs` both check `lastVerifiedBlock(rollupId) == block.number` and revert if the check fails.

`staticCrossChainCall` does **not** enforce this gate for its top-level pool path. It is a `view` function that scans the active/persistent static-entry tables for a matching entry and returns it regardless of which block that entry was posted in — static reads deliberately skip the block-freshness check that state-mutating consumption enforces.

Practical consequences:

- Any contract that consumes a cross-chain entry must do so in the same block as the `postAndVerifyBatch` that posted it.
- Entries from a previous block are not skipped — they are simply never readable again (the next `postAndVerifyBatch` for that rollup overwrites the queue).
- Same-block re-verification (posting a second batch for the same rollup in the same block) **replaces** the prior queue entirely; it does not append.

Design your execution flow so that `postAndVerifyBatch` and all consuming calls happen atomically within a single block. The `Batcher` and `FlashLoanBatcher` helper contracts demonstrate this pattern by combining batch posting and trigger calls in a single transaction.

## State Root Staleness

:::note
Top-level [`StaticExecutionEntry`](/reference/glossary#staticexecutionentry) entries on L1 use `expectedStateRoots` to pin a cached read to a specific point in each referenced rollup's state trajectory. Pinning is mandatory, not optional: the entry's own `destinationRollupId` must appear in `expectedStateRoots`, or the batch reverts `StaticEntryDestinationNotPinned` at publish time — likewise, every rollup any of the entry's read-only sub-calls sources from must also be pinned, or the batch reverts `CallSourceNotVerified`. An unconditional, unpinned match is not possible.
:::

Mandatory pinning closes the specific bug where an entry with no pins at all could resolve against whatever state root happened to be live at read time. What remains your responsibility is pinning the **correct** root:

- If you publish a `StaticExecutionEntry` that records the return value of a remote read, pin `expectedStateRoots` to the exact state root(s) your off-chain prover observed when computing `returnData` — not a later or earlier one.
- If the pinned root no longer matches the live root by the time someone resolves the entry (because the remote state advanced), resolution simply misses that candidate rather than returning stale data — see the match predicate in [`staticCrossChainCall`](/guides/lookup-calls#routing-how-a-read-reaches-staticcrosschaincall).

State-root pinning is split-independent (does not depend on the transient/persistent split), transient-phase capable (roots advance entry-by-entry during a batch), and robust across same-block re-verifications (the root trajectory continues coherently).

## Match-Time Skip vs. Execution-Time Block — Summary Table

| Execution mode | Non-matching candidate | Matched, then reverts mid-execution |
|---|---|---|
| Persistent queue entry | Skipped cleanly, cursor moves past it | Reverts consuming tx, queue cursor does NOT advance (queue blocked) |
| Immediate entry (`_attemptExecuteImmediateL2Txs`) | — (leading prefix, always attempted) | `L2TxSkipped` event, cursor advances |
| Transient entry (within `postAndVerifyBatch`) | Skipped cleanly, cursor moves past it | Reverts the entire batch tx |
| STATIC-kind row of `ExpectedL1ToL2Call` / `ExpectedOutgoingCrossChainCall` (reentrant, inside execution) | Reverts `ExecutionNotFound` directly (no fallback) | — (resolves per its own `success` flag, by design; never a mid-execution revert) |
| Top-level `StaticExecutionEntry` (outside execution) | Miss → scan continues to next candidate | — (`view` function; resolves per its own `success` flag) |

## Early-Stage Status: What This Means for You

The EEZ implementation is explicitly labeled as early-stage with several known, intentional simplifications:

- **No fee-on-transfer token accounting** in `Bridge.sol`. Tokens with transfer fees will not bridge correctly.
- **`Bridge.initialize()` has no chain-context binding**. Nothing prevents calling it with the wrong `rollupId` or `manager` address — the wrong configuration silently produces an unusable bridge.
- **No re-deployment authorization**. There is no mechanism to update or replace a Bridge once deployed, beyond calling `setCanonicalBridgeAddress`.
- **Single admin key**. `Bridge.setCanonicalBridgeAddress` is gated on a single EOA admin address set at initialization. There is no multisig or timelock.
- **Interfaces are not stable**. `IEEZ.sol`, `IEEZL2.sol`, and the execution struct layouts may change between versions. Do not rely on ABI compatibility across protocol upgrades.

Before building production applications on EEZ, wait for a published audit and a stability declaration. Until then, use it for exploration, prototyping, and contributing to the protocol's development.
