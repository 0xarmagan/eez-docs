EEZ is a novel synchronous cross-rollup protocol with a number of edge cases that you must understand before building on it. Some of these are fundamental constraints of the execution model; others are deliberate simplifications that will be addressed as the protocol matures. Read this page carefully before deploying any production-facing code.

:::warning
EEZ is an **early-stage, unaudited implementation**. Interfaces, storage layout, and execution semantics are still in flux. Do not use EEZ contracts with real funds until a full security audit has been completed and the protocol is declared stable.
:::

## Queue Blocking on Revert

:::warning
A reverting entry in a persistent execution queue **blocks the entire queue** — it does not get skipped.
:::

Each rollup's execution queue encodes exactly one valid consumption order. When `executeCrossChainCall` attempts to consume a persistent entry and that entry reverts mid-execution — for example, because of a `StateRootMismatch` or `RollingHashMismatch` — the consuming transaction reverts without advancing the queue cursor. The entry remains at the front of the queue.

This means **you cannot stack multiple candidate entries** and rely on the first one that matches to apply. The queue is not a competing-candidates pool; it is a strict ordered sequence.

**The one exception** is the `IMMEDIATE` prefix. `attemptApplyImmediate` wraps each immediate entry in a `try/catch`, so a reverting immediate entry emits `ImmediateEntrySkipped` and the cursor advances. You can use immediate entries with a `StateDelta.currentState` gate to create alternatives — only the entry whose `currentState` matches the live state root will succeed, and the others are skipped cleanly.

For persistent (non-immediate) entries, there is no such tolerance. Build your execution entries carefully and verify them against the exact state root trajectory before posting.

## Transient-Phase Isolation

:::note
Cross-rollup interactions inside the meta hook are only supported between rollups verified **together in the same batch**. Interactions with any other rollup must wait for persistent consumption.
:::

While a `postAndVerifyBatch` is mid-flight (during the immediate-entry drain and the meta-hook window), EEZ routes **all** resolution exclusively from that batch's own transient tables:

- Execution entries are consumed from the batch's own transient cursor.
- Top-level lookups never fall through to the persistent queues.

A rollup that was verified by an earlier batch in the same block passes the block gate, but any call to it during the hook will miss with `ExecutionNotFound`. Consequence:

- **Do** batch all rollups you need to interact with synchronously into the same `postAndVerifyBatch` call.
- **Do not** expect to reach rollups verified in separate earlier transactions during the meta hook.
- Cross-rollup interactions that span separate batches must use the persistent queue path (enqueue entries, consume in a later transaction).

## Indistinguishable Revert Reasons from a Proxy

When you call a `CrossChainProxy` and the call reverts, you cannot distinguish between these two causes:

1. The execution table did not contain a matching entry for this call.
2. The underlying destination contract call itself reverted.

Both cases surface as a revert from the proxy with no additional context distinguishing the source. If your code needs to handle these differently, you must design around this limitation — for example, by pre-checking that an entry exists before making the call, or by using a lookup call to probe the remote state first.

## Opcode Differences When Using Proxies

When a call is routed through a `CrossChainProxy`, certain EVM opcodes return information about the **proxy** itself rather than the proxied contract:

- `DELEGATECALL` — executes in the proxy's context.
- `BALANCE` — returns the proxy's ETH balance, not the proxied contract's.
- `EXTCODESIZE` — returns the proxy's code size.
- `EXTCODECOPY` — copies the proxy's bytecode.

:::warning
Do not rely on any of these opcodes to inspect the remote contract from the caller's side. If you need the remote contract's code or balance, use a dedicated cross-chain view call or lookup.
:::

Block-state opcodes also reflect the chain where the call is currently executing, not the chain the call originated from:

- `BLOCKNUMBER`, `BLOCKHASH`, `BLOCKGASLIMIT`, `CHAINID`, `COINBASE`, and similar block context opcodes reflect the **destination chain's** values.

This means that the same logical action observed on L1 vs. L2 will see different values for these opcodes. Do not use block-context opcodes to infer cross-chain ordering or to derive timestamps that must be consistent across chains.

## Block Gating: Entries Are Valid for One Block Only

Execution entries posted in a `postAndVerifyBatch` are **only consumable within the same L1 block** they were posted. The `RollupVerification.lastVerifiedBlock` field doubles as a read gate: `executeCrossChainCall`, `executeL2TX`, and `staticCallLookup` all check `lastVerifiedBlock(rollupId) == block.number` and revert if the check fails.

Practical consequences:

- Any contract that consumes a cross-chain entry must do so in the same block as the `postAndVerifyBatch` that posted it.
- Entries from a previous block are not skipped — they are simply never readable again (the next `postAndVerifyBatch` for that rollup overwrites the queue).
- Same-block re-verification (posting a second batch for the same rollup in the same block) **replaces** the prior queue entirely; it does not append.

Design your execution flow so that `postAndVerifyBatch` and all consuming calls happen atomically within a single block. The `Batcher` and `FlashLoanBatcher` helper contracts demonstrate this pattern by combining batch posting and trigger calls in a single transaction.

## State Root Staleness

:::note
Top-level `LookupCall` entries on L1 use `expectedStateRoots` to pin a cached read to a specific point in the rollup's state trajectory. An empty `expectedStateRoots` array matches unconditionally.
:::

When a top-level `LookupCall` is published without any `expectedStateRoots` pins, it can match against any state root. This is intentional for state-independent reads but can lead to stale data being returned if you are not careful:

- If you publish a lookup that records the return value of a remote read, and the remote state has since advanced, the lookup still matches and returns the old value.
- For correctness, always pin `expectedStateRoots` to the specific state root(s) your off-chain prover observed when computing `returnData`.

State-root pinning is split-independent (does not depend on the transient/persistent split), transient-phase capable (roots advance entry-by-entry during a batch), and robust across same-block re-verifications (the root trajectory continues coherently).

## No Skipping on Persistent Revert — Summary Table

| Execution mode | Revert behavior |
|---|---|
| Persistent queue entry | Reverts consuming tx, queue cursor does NOT advance (queue blocked) |
| Immediate entry (`attemptApplyImmediate`) | `ImmediateEntrySkipped` event, cursor advances |
| Transient entry (within `postAndVerifyBatch`) | Reverts the entire batch tx |
| `LookupCall` outside execution | Miss → scan continues to next candidate |
| `ExpectedLookup` nested (inside execution) | Must match exactly; miss reverts |

## Early-Stage Status: What This Means for You

The EEZ implementation is explicitly labeled as early-stage with several known, intentional simplifications:

- **No fee-on-transfer token accounting** in `Bridge.sol`. Tokens with transfer fees will not bridge correctly.
- **`Bridge.initialize()` has no chain-context binding**. Nothing prevents calling it with the wrong `rollupId` or `manager` address — the wrong configuration silently produces an unusable bridge.
- **No re-deployment authorization**. There is no mechanism to update or replace a Bridge once deployed, beyond calling `setCanonicalBridgeAddress`.
- **Single admin key**. `Bridge.setCanonicalBridgeAddress` is gated on a single EOA admin address set at initialization. There is no multisig or timelock.
- **Interfaces are not stable**. `IEEZ.sol`, `IEEZL2.sol`, and the execution struct layouts may change between versions. Do not rely on ABI compatibility across protocol upgrades.

Before building production applications on EEZ, wait for a published audit and a stability declaration. Until then, use it for exploration, prototyping, and contributing to the protocol's development.
