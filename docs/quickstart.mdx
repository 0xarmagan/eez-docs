Run a real cross-rollup call — an L1 contract calling an L2 contract and getting the
return value back — against two local chains. No devnet access and no configuration
required.

<AuditStatus />

## Prerequisites

- [Foundry](https://book.getfoundry.sh/getting-started/installation) (`forge`, `cast`)
- `bash`
- `git`

## 1. Clone and build

```bash
git clone https://github.com/eez-association/eez-core-protocol.git
cd eez-core-protocol
forge build
```

`forge build` must complete cleanly before the scenario runners will work.

## 2. Run the test suite

```bash
forge test
```

This exercises the protocol in-process: entry construction, rolling-hash folding,
revert spans, static resolution, and the blob codec.

## 3. Run a cross-rollup scenario

This is the interesting part. The repository ships end-to-end scenarios that stand up
two local chains, deploy the contracts on both sides, post a proved batch to L1, and
drive the call through to completion — then verify the result.

Local mode needs no setup at all:

```bash
bash script/e2e/run/local-parallel.sh counter
```

`counter` is the simplest scenario: an L1 contract calls a `Counter` contract on L2
through a cross-chain proxy, and the increment lands. To run everything instead, pass
no arguments:

```bash
bash script/e2e/run/local-parallel.sh
```

Each argument may be a **scenario name** (`counter`), a **category** (`one_way`,
`multi_call`, `multi_tx`, `nested`, `reentrant`, `revert`), or a
**category/direction** (`one_way/L2_to_L1`). Categories expand to every scenario
beneath them, and scenarios run in parallel:

```bash
bash script/e2e/run/local-parallel.sh one_way          # one category
bash script/e2e/run/local-parallel.sh counter bridge   # two scenarios
```

## 4. What the run actually checks

A passing scenario is a much stronger signal than "no revert." The runner verifies
the same properties the specification defines:

- **L1 settlement** — the batch consumed the expected entries, checked via
  `ExecutionConsumed` routing and `EntryExecuted` rolling hash plus call and nested
  counts.
- **Posted batch contents** — the `postAndVerifyBatch` calldata is decoded and every
  expected entry is field-matched against its posted twin: calls, reentrant frames,
  `returnData`, `success` flags, and state updates.
- **Rolling-hash replay** — each posted entry's rolling hash is reproduced by
  replaying the scenario's recorded fold steps over a seed rebuilt from the posted
  state roots. This is exact per-call verification, return data included.
- **L2 table and calls** — every expected entry must have a byte-identical loaded
  twin on L2, and each `IncomingCrossChainCallExecuted` must re-hash to the emitted
  call hash.

Note that the two chains are never correlated by block number. The link is
**content**: identical `crossChainCallHash` preimages on both sides, and an entry
identity of `keccak256(proxyEntryHash, rollingHash)`. Because the rolling hash folds
every call result, the source side's cached return values are cryptographically bound
to what actually executed on the destination — any divergence changes the hash and
fails the run.

That is [the rolling hash](/spec/core-protocol/e-rolling-hash) doing its job, observable
end to end.

## 5. Pick a scenario that matches your use case

Each scenario is a worked instance of a flow pattern from the
[Execution Entry specification](/spec/execution-entries):

| Scenario | What it exercises |
|---|---|
| `counter` | L1→L2, the simplest one-way call |
| `counterL2` | L2→L1, the same shape in reverse |
| `bridge` | ether movement via `etherDelta` |
| `nestedCounter` / `nestedCounterL2` | reentrant call inside a cross-chain call |
| `deepNested` | multiple levels of reentrancy |
| `reentrant` | the reentrant expected-call table |
| `flash-loan` | borrow, use, and repay across chains in one block |
| `multi-call-twice` / `multi-call-two-diff` | several top-level calls in one entry |
| `counter-multi-tx` | multiple transactions in one block |
| `revertCounter` / `revertContinue` | forced reverts via `revertNextNCalls` |
| `nestedCallRevert` | a reverting reentrant frame (`success = false`) |

`L2` and `L2`-suffixed variants run the mirrored direction. Read a scenario's
`.s.sol` source alongside its spec section — together they show both the structure a
prover must build and the on-chain behaviour it produces.

## Running against a devnet

Local mode uses throwaway chains. To run the same scenarios against a real devnet you
need endpoints and a funded test key in a `chain.env` file at the repo root, then the
network runners take over. Full setup — endpoint routing, key hygiene, timeouts, and
the parallel orchestrator — is documented in `script/e2e/README.md`.

Use a fresh throwaway key (`cast wallet new`). Well-known Anvil keys may be shared
with devnet actors, and the resulting nonce races surface as triggers that never land.
