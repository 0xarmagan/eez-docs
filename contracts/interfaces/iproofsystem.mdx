`IProofSystem` is the single-function interface that any proof verifier must implement to participate in EEZ batch verification. A proof system is any contract capable of checking whether a given proof is valid for a particular set of public inputs. EEZ intentionally places no restrictions on what cryptographic scheme you use: ZK-SNARK/STARK verifiers, ECDSA multisig contracts, BLS aggregation schemes, and trivially-accepting mock contracts for testing all satisfy the interface equally. There is no central registry of proof systems — each rollup's `IRollupContract` manager maintains its own allowed set.

## Interface Definition

```solidity
interface IProofSystem {
    function verify(
        bytes calldata proof,
        bytes32 publicInputsHash
    ) external view returns (bool valid);
}
```

---

## `verify`

```solidity
function verify(
    bytes calldata proof,
    bytes32 publicInputsHash
) external view returns (bool valid)
```

Checks whether `proof` is a valid proof for the public input identified by `publicInputsHash`. The EEZ registry calls this function once per proof system per batch inside `_verifyProofSystemBatch`. All proofs in a batch must verify atomically — if any `verify` call returns `false`, the entire `postAndVerifyBatch` call reverts with `InvalidProof`.

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `proof` | `bytes` | The raw proof bytes. The encoding and structure are entirely specific to this proof system. For a ZK-SNARK verifier these might be elliptic curve points; for an ECDSA multisig contract they might be packed signature bytes; for a mock test verifier they might be empty. |
| `publicInputsHash` | `bytes32` | A single `keccak256` hash that binds together all public inputs for this proof. EEZ constructs this hash inside `_verifyProofSystemBatch` according to the formula described below. Your proof circuit (or signing logic) must commit to the same hash value. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `valid` | `bool` | Return `true` if the proof is valid for the given `publicInputsHash`. Return `false` (do not revert) if the proof is invalid. The EEZ registry treats a `false` return as a failed verification and reverts the whole `postAndVerifyBatch` call. |

---

## How `publicInputsHash` Is Constructed

The EEZ registry builds `publicInputsHash` in two stages before calling `verify`. Understanding this construction is essential when implementing a proof circuit or a signing scheme.

**Stage 1 — Shared public input across all proof systems in the batch:**

```
customDataAcc = bytes32(0)
for each rollup r in the batch (rollupId-ascending):
    customData_r = IRollupContract(rollupContract_r).getCustomData(batch.blockNumber)
    customDataAcc = keccak256(abi.encode(customDataAcc, rollupId_r, customData_r))

sharedPublicInput = keccak256(abi.encodePacked(
    abi.encode(entryHashes),          // keccak256(abi.encode(entry)) per entry
    abi.encode(lookupCallHashes),     // keccak256(abi.encode(lookupCall)) per lookup
    abi.encode(blobHashes),           // EIP-4844 blob hashes selected by blobIndices[]
    keccak256(callData),              // batch-scoped calldata hash
    customDataAcc                     // folded per-rollup custom data
))
```

`entryHashes` and `lookupCallHashes` cover the full serialised structs including all state deltas, call arrays, expected reentrant tables, rolling hashes, and return data — any tampering with any entry changes the hash.

**Stage 2 — Per-proof-system accumulator mixing in vkeys:**

```
acc_k = bytes32(0)
for each rollup r that selected proof system k in the batch:
    acc_k = keccak256(abi.encode(acc_k, rollupId_r, vkMatrix[r][j]))

publicInputsHash[k] = keccak256(abi.encodePacked(sharedPublicInput, acc_k))
```

`vkMatrix[r][j]` is the verification key returned by `IRollupContract.checkProofSystemsAndGetVkeys` for rollup `r`'s participation in proof system `k`. Note that `j` is not simply `k`: `vkMatrix` is a JAGGED matrix — each rollup only receives vkeys for the proof systems it actually selected — so `j = _findIndexPosition(proofSystemIndex[r], k)` is a per-rollup lookup that maps the global proof system index `k` to its position within rollup `r`'s own `proofSystemIndex[]`/`vkMatrix[r]` row. This means each proof system's `publicInputsHash` is unique: two proof systems in the same batch see different hashes even though they share the same `sharedPublicInput`.

## Implementing a Custom Proof System

Any contract that implements the `verify` function satisfies the interface. The following examples illustrate common patterns.

### ZK Proof Verifier

A production ZK proof system wraps an on-chain circuit verifier (e.g., a Groth16 or PLONK verifier generated by a ZK toolchain). The `proof` bytes encode one or more elliptic curve points and scalar values, and `publicInputsHash` is passed directly as the single public input:

```solidity
contract ZKProofSystem is IProofSystem {
    IGroth16Verifier public immutable verifier;

    constructor(IGroth16Verifier _verifier) {
        verifier = _verifier;
    }

    function verify(
        bytes calldata proof,
        bytes32 publicInputsHash
    ) external view returns (bool valid) {
        (uint256[2] memory a, uint256[2][2] memory b, uint256[2] memory c)
            = abi.decode(proof, (uint256[2], uint256[2][2], uint256[2]));
        uint256[1] memory input = [uint256(publicInputsHash)];
        return verifier.verifyProof(a, b, c, input);
    }
}
```

### ECDSA Multisig Verifier

For development networks or rollups that prefer social consensus, you can implement a proof system as a multisig over `publicInputsHash`. Each signer calls `verify` indirectly by producing a signature off-chain; the proof bytes are packed signatures:

```solidity
contract ECDSAProofSystem is IProofSystem {
    address[] public signers;
    uint256 public threshold;

    function verify(
        bytes calldata proof,
        bytes32 publicInputsHash
    ) external view returns (bool valid) {
        bytes32 messageHash = keccak256(
            abi.encodePacked("\x19Ethereum Signed Message:\n32", publicInputsHash)
        );
        uint256 count = proof.length / 65;
        uint256 valid_sigs = 0;
        for (uint256 i = 0; i < count; i++) {
            bytes memory sig = proof[i * 65:(i + 1) * 65];
            address recovered = ECDSA.recover(messageHash, sig);
            if (_isSigner(recovered)) valid_sigs++;
        }
        return valid_sigs >= threshold;
    }
}
```

The reference `ECDSAProofSystem.sol` in the EEZ repository (`src/proofSystems/ECDSAProofSystem.sol`) is intentionally **simpler** than the multisig example above — treat that example as an illustrative pattern for when you actually need threshold signatures, not a description of the reference. The reference is a **single-signer** verifier (one `address signer`, no `threshold` and no signature loop) that recovers directly against the **raw `bytes32 publicInputsHash`** with **no** EIP-191 `"\x19Ethereum Signed Message"` prefix:

```solidity
contract ECDSAProofSystem is IProofSystem {
    address public immutable signer;

    constructor(address _signer) {
        signer = _signer;
    }

    function verify(
        bytes calldata proof,
        bytes32 publicInputsHash
    ) external view returns (bool) {
        // proof is a single 65-byte abi.encodePacked(r, s, v) signature (v = 27 or 28)
        address recovered = ECDSA.recover(publicInputsHash, proof);
        return recovered == signer;
    }
}
```

If you follow the multisig example instead, remember its EIP-191-prefixed digest is **incompatible** with the reference: a signature made over the prefixed hash will not recover against the raw `publicInputsHash`.

### Mock Verifier for Testing

During testing you often want to bypass proof verification entirely. A trivially-accepting mock is a valid `IProofSystem`:

```solidity
contract MockProofSystem is IProofSystem {
    function verify(
        bytes calldata,
        bytes32
    ) external pure returns (bool) {
        return true;
    }
}
```

You can also build a mock that accepts only specific `publicInputsHash` values, which lets you test rejection paths without a real proof circuit.

## Registering a Proof System

You do not register proof systems with the EEZ central registry. Instead, each rollup's `IRollupContract` manager controls its own allowed proof system set. To add a proof system to a rollup, the rollup owner calls `addProofSystem(address proofSystem, bytes32 vkey)` on their `IRollupContract`. The `vkey` is the verification key your circuit is compiled against — it becomes part of the `publicInputsHash` for every batch that proof system attests to, binding the proof to a specific circuit version.

When the EEZ registry calls `checkProofSystemsAndGetVkeys` during `postAndVerifyBatch`, it receives back the vkeys for the subset of proof systems the batch selected. Any proof system address that returns a zero vkey for a rollup is treated as not allowed, and the batch reverts.
