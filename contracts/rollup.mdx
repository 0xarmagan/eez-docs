<UnauditedWarning />

The `Rollup` contract is the reference implementation of an `IRollupContract`-conforming manager for a single rollup. It separates per-rollup governance (which proof systems are trusted, what verification keys they use, and how many must attest per batch) from the central `EEZ` registry, which only tracks state roots and ether balances. You deploy `Rollup`, configure it with your proof systems and threshold, and then register it via `EEZ.registerRollup`. From that point the `EEZ` registry calls back into your `Rollup` during every batch submission to fetch verification keys and enforce your threshold.

:::info
You do not have to use this reference implementation. Any contract that satisfies the `IRollupContract` interface can be registered with `EEZ`. The reference `Rollup` uses OpenZeppelin `Ownable` for access control; a production rollup might use a timelock, multisig, or DAO governance contract instead.
:::

---

## Public State

| Variable | Type | Description |
| --- | --- | --- |
| `ROLLUPS` | `address` (immutable) | The central `EEZ` registry this rollup is registered with. Set in the constructor; never changes. |
| `rollupId` | `uint256` | The ID assigned to this rollup by the registry. Written exactly once via the `rollupContractRegistered` callback; `0` means not yet registered. |
| `threshold` | `uint256` | Minimum number of proof systems that must attest per batch. Enforced inside `checkProofSystemsAndGetVkeys`. |
| `verificationKey(address)` | `mapping(address => bytes32)` | Per-proof-system verification key. A value of `bytes32(0)` means the proof system is not allowed for this rollup. |

---

## Constructor

The constructor initialises the contract with the central registry address, the initial owner, a starting threshold, and an initial set of proof systems and their verification keys. You must deploy and configure this contract before registering it via `EEZ.registerRollup` — the registry never deploys it for you.

```solidity
constructor(
    address rollupsRegistry,
    address _owner,
    uint256 _threshold,
    address[] memory proofSystems,
    bytes32[] memory vkeys
)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupsRegistry` | `address` | Address of the deployed `EEZ` contract. Stored as the immutable `ROLLUPS` and used to validate that only the registry can fire the `rollupContractRegistered` callback. Must not be `address(0)`. |
| `_owner` | `address` | The initial owner, passed to OpenZeppelin `Ownable`. The owner can add/remove proof systems, rotate verification keys, change the threshold, and invoke the escape-hatch state root override. |
| `_threshold` | `uint256` | The initial minimum number of proof systems that must attest per batch. You can set this to any value, including zero (any subset passes) or a value above the initial proof-system count (which locks the rollup until more proof systems are added). You are responsible for choosing a secure value. |
| `proofSystems` | `address[]` | Initial proof system contract addresses. Each must conform to `IProofSystem`. There is no central registry — you are responsible for vetting each proof system before adding it. Must have the same length as `vkeys`. |
| `vkeys` | `bytes32[]` | Verification keys parallel to `proofSystems`. Each entry must be non-zero and each proof system address must appear at most once. If any `vkey` is `bytes32(0)`, or if the arrays differ in length, construction reverts. |

#### Errors (constructor)

| Error | Condition |
| --- | --- |
| `InvalidConfig` | `rollupsRegistry` is `address(0)`, `proofSystems.length != vkeys.length`, or any `vkey` is `bytes32(0)`. |
| `ProofSystemAlreadyAllowed(address)` | A proof system address appears more than once in the initial `proofSystems` array. |

## Functions

<details>
<summary>rollupContractRegistered — One-shot registration callback from EEZ</summary>

`rollupContractRegistered` is called by the `EEZ` registry exactly once, immediately after `EEZ.registerRollup` assigns a rollup ID. It stores the assigned `rollupId` so that this contract can later pass it back to the registry when calling [`EEZ.setStateRoot`](/contracts/eez). You should never call this function yourself — only the `ROLLUPS` registry is permitted to call it, and it can only be called once.

**Who can call it:** Only `ROLLUPS` (the `EEZ` registry). Calling from any other address reverts.

```solidity
function rollupContractRegistered(uint256 _rollupId) external
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupId` | `uint256` | The rollup ID assigned by the registry. IDs start at `1` (`0` is reserved for mainnet). This value is stored in the public `rollupId` state variable and must be passed back to `EEZ.setStateRoot` in any future escape-hatch calls. |

#### Errors

| Error | Condition |
| --- | --- |
| `NotEEZRegistry` | `msg.sender` is not the immutable `ROLLUPS` address. |
| `AlreadyRegistered` | `rollupId` is already non-zero — the contract has already been registered. Prevents an existing rollup's manager from being silently hijacked by re-registering. |

</details>

<details>
<summary>checkProofSystemsAndGetVkeys — Bulk vkey lookup for batch verification</summary>

Reference implementation of the `IRollupContract.checkProofSystemsAndGetVkeys` interface method — see [IProofSystem](/contracts/interfaces/iproofsystem) for its role in batch verification. Enforces this rollup's `threshold` and rejects any address whose `verificationKey` is zero, then returns the vkey list parallel to the input.

**Who can call it:** Anyone, but in practice only `EEZ` during [`postAndVerifyBatch`](/contracts/eez). Called via STATICCALL so no state mutation is possible.

```solidity
function checkProofSystemsAndGetVkeys(address[] calldata proofSystems)
    external
    view
    returns (bytes32[] memory vkeys)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `proofSystems` | `address[]` | The proof-system addresses chosen for this rollup in the current batch, in strictly-ascending order. The `EEZ` registry derives this list by resolving `RollupIdWithProofSystems.proofSystemIndex` entries from the batch's global `proofSystems` array. The strictly-ascending invariant is enforced both by the registry (at `_validateStructure`) and re-checked here to reject duplicates and `address(0)` from any caller. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `vkeys` | `bytes32[]` | Verification keys parallel to the input `proofSystems` array. Every entry is guaranteed non-zero on successful return. The `EEZ` registry uses these to construct the per-rollup vkey accumulator folded into each proof system's public-inputs hash. |

#### Errors

| Error | Condition |
| --- | --- |
| `ThresholdNotMet(uint256 submitted, uint256 required)` | `proofSystems.length < threshold`. The batch is trying to use fewer proof systems than this rollup requires. |
| `ProofSystemNotAllowed(address)` | An address in the input is `address(0)`, is not strictly greater than the previous address (duplicate or out-of-order), or has a zero verification key (not added to this rollup). |

</details>

<details>
<summary>getCustomData — Provide L1 block context for batch binding</summary>

`getCustomData` returns an opaque blob that this rollup binds into its per-rollup verification commit for the L1 `blockNumber` the batch is targeting. The `EEZ` registry folds the result — keyed by `rollupId`, in rollup-ID-ascending order — into the batch's shared public inputs hash (`customDataAcc`), so the ZK proof attests against this exact L1 view. The reference implementation returns `abi.encode(timestamp, blockHash)` where `timestamp` is `0` (recoverable off-chain from the block header) and `blockHash` is fetched via `blockhash()`.

**Who can call it:** Anyone, but called by `EEZ` during `postAndVerifyBatch` as a STATICCALL.

```solidity
function getCustomData(uint64 blockNumber) external view returns (bytes memory customData)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `blockNumber` | `uint64` | The L1 block number this batch is bound to, as specified in `ProofSystemBatchPerVerificationEntries.blockNumber`. Special values: `0` — No block context. Returns an empty bytes blob. `type(uint64).max` — Latest context. Returns `abi.encode(block.timestamp, blockhash(block.number - 1))`. Any other value — Returns `abi.encode(0, blockhash(blockNumber))`. Reverts if the block hash is unavailable (block is in the future or older than 256 blocks). |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `customData` | `bytes` | The ABI-encoded `(timestamp, blockHash)` pair, or an empty blob for `blockNumber == 0`. The exact encoding is rollup-defined — you can override this function to return any blob your circuit expects, as long as you keep it consistent with your prover. |

#### Errors

| Error | Condition |
| --- | --- |
| `BlockHashUnavailable(uint64 blockNumber)` | `blockhash(blockNumber)` returned `bytes32(0)` — the block is in the future, is the current block, or is more than 256 blocks in the past. The reference implementation rejects this rather than silently binding a zero hash. |

</details>

<details>
<summary>setStateRoot — Owner escape hatch for manual state root override</summary>

`setStateRoot` is an emergency back-door that lets the owner directly set the rollup's state root via the `EEZ` registry without submitting a ZK proof. This is the only call this contract makes back into `EEZ`. The registry independently validates that `msg.sender` (this contract) is the registered manager for `rollupId`, and blocks the call if a `postAndVerifyBatch` has already touched this rollup in the current block. Use this only for emergencies — for example, to correct a state root if the proving infrastructure fails.

**Who can call it:** Owner only (`onlyOwner`).

**Emits:** `StateRootEscape(newStateRoot)`

```solidity
function setStateRoot(bytes32 newStateRoot) external onlyOwner
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `newStateRoot` | `bytes32` | The new state root to commit directly to the `EEZ` registry for this rollup. No pre-state validation is performed — you must ensure the value is correct. Subsequent batch submissions will use this as their expected `currentState`. |

#### Errors

| Error | Condition |
| --- | --- |
| `OwnableUnauthorizedAccount` | `msg.sender` is not the current owner. |
| `NotRollupContract` (from EEZ) | This contract is no longer the registered manager for its `rollupId` — should not happen in normal operation. |
| `RollupBatchActiveThisBlock(uint256)` (from EEZ) | A `postAndVerifyBatch` has already verified this rollup in the current block. Wait until the next block. |
| `SetStateRootNotAllowedDuringExecution` (from EEZ) | A cross-chain execution is currently active. |

</details>

<details>
<summary>addProofSystem — Add a proof system to the allowed set</summary>

`addProofSystem` registers a new proof system and its verification key for this rollup. After calling this, the proof system's address can appear in future batches' `proofSystems` arrays, and its verification key will be returned by `checkProofSystemsAndGetVkeys`. You are responsible for ensuring that `proofSystem` is a genuine `IProofSystem`-conforming contract — the `Rollup` contract performs no on-chain vetting.

**Who can call it:** Owner only (`onlyOwner`).

**Emits:** `ProofSystemAdded(proofSystem, verificationKey)`

```solidity
function addProofSystem(address proofSystem, bytes32 vkey) external onlyOwner
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `proofSystem` | `address` | The address of the proof system contract to allow. Must not already be in the allowed set (non-zero `verificationKey` for this address). Should conform to `IProofSystem` (`verify(bytes, bytes32) → bool`). |
| `vkey` | `bytes32` | The verification key for this proof system. Must be non-zero. The exact format is defined by the proof system's circuit — consult the prover documentation. |

#### Errors

| Error | Condition |
| --- | --- |
| `OwnableUnauthorizedAccount` | `msg.sender` is not the owner. |
| `InvalidConfig` | `vkey` is `bytes32(0)`. |
| `ProofSystemAlreadyAllowed(address)` | The proof system already has a non-zero verification key for this rollup. Use `updateVerificationKey` instead. |

</details>

<details>
<summary>removeProofSystem — Remove a proof system from the allowed set</summary>

`removeProofSystem` de-lists a proof system by zeroing its verification key. After this call, any batch that includes this proof system in this rollup's subset will revert with `ProofSystemNotAllowed` during `checkProofSystemsAndGetVkeys`. Take care: removing a proof system may drop the number of allowed systems below `threshold`, effectively locking the rollup until you add more systems or lower the threshold. The function does not check whether the removal would violate the threshold.

**Who can call it:** Owner only (`onlyOwner`).

**Emits:** `ProofSystemRemoved(proofSystem)`

```solidity
function removeProofSystem(address proofSystem) external onlyOwner
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `proofSystem` | `address` | The address of the proof system to remove. Must currently be in the allowed set (non-zero verification key). Attempting to remove a proof system that was never added reverts. |

#### Errors

| Error | Condition |
| --- | --- |
| `OwnableUnauthorizedAccount` | `msg.sender` is not the owner. |
| `ProofSystemNotAdded(address)` | The proof system has a zero verification key — it was never added (or was already removed). |

</details>

<details>
<summary>updateVerificationKey — Rotate a proof system's verification key</summary>

`updateVerificationKey` replaces the verification key for a proof system that is already in the allowed set. Use this when the proving circuit is upgraded but the same proof system contract continues to handle verification. The key takes effect immediately — the next batch posted after this call will use the new key. Ensure your proving infrastructure is producing proofs under the new key before calling this.

**Who can call it:** Owner only (`onlyOwner`).

**Emits:** `VerificationKeyUpdated(proofSystem, newVkey)`

```solidity
function updateVerificationKey(address proofSystem, bytes32 newVkey) external onlyOwner
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `proofSystem` | `address` | The address of the proof system whose key you want to rotate. Must currently be in the allowed set. |
| `newVkey` | `bytes32` | The replacement verification key. Must be non-zero. |

#### Errors

| Error | Condition |
| --- | --- |
| `OwnableUnauthorizedAccount` | `msg.sender` is not the owner. |
| `InvalidConfig` | `newVkey` is `bytes32(0)`. |
| `ProofSystemNotAdded(address)` | The proof system has a zero verification key — it is not currently in the allowed set. Use `addProofSystem` first. |

</details>

<details>
<summary>setThreshold — Update the minimum proof-system attestation count</summary>

`setThreshold` updates the minimum number of proof systems that must attest to any given batch for this rollup. The threshold is enforced at batch time inside `checkProofSystemsAndGetVkeys`. Any value is accepted, including `0` (any subset passes) or a value exceeding the current number of allowed proof systems (which will lock the rollup until more are added or the threshold is lowered). You are responsible for picking a value that reflects your rollup's security requirements.

**Who can call it:** Owner only (`onlyOwner`).

**Emits:** `ThresholdChanged(newThreshold)`

```solidity
function setThreshold(uint256 newThreshold) external onlyOwner
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `newThreshold` | `uint256` | The new minimum attestation count. A value of `1` means any single proof system suffices; a value of `n` requires `n` out of however many are in the allowed set. Setting this above the allowed set size prevents new batches from being accepted until more proof systems are added. |

#### Errors

| Error | Condition |
| --- | --- |
| `OwnableUnauthorizedAccount` | `msg.sender` is not the owner. |

</details>

## Events

| Event | Description |
| --- | --- |
| `ProofSystemAdded(proofSystem, verificationKey)` | Emitted when a proof system is added via `addProofSystem`. |
| `ProofSystemRemoved(proofSystem)` | Emitted when a proof system is removed via `removeProofSystem`. |
| `VerificationKeyUpdated(proofSystem, newVerificationKey)` | Emitted when a verification key is rotated via `updateVerificationKey`. |
| `ThresholdChanged(newThreshold)` | Emitted when the attestation threshold changes via `setThreshold`. |
| `StateRootEscape(newStateRoot)` | Emitted when the owner escape hatch is exercised via `setStateRoot`. |

## `IRollupContract` Interface

`Rollup.sol` is one implementation of the [`IRollupContract`](/contracts/interfaces/irollupcontract) interface. Any contract that implements `rollupContractRegistered`, `checkProofSystemsAndGetVkeys`, and `getCustomData` can be registered with the `EEZ` central registry — see the interface reference for the required semantics and invariants.
