The `EEZ` contract is the heart of the EEZ protocol on Ethereum mainnet. It serves as a permissionless registry for rollups, accepts multi-prover batch submissions that advance state roots, and provides the execution surface through which cross-chain proxy calls are routed and fulfilled. Every rollup's state root, ether balance, and deferred execution queue live here; per-rollup configuration (proof systems, verification keys, ownership, and threshold) live on a separate `IRollupContract`-conforming manager that `EEZ` calls into during verification.

---

## Constants

| Name | Value | Description |
| --- | --- | --- |
| `MAINNET_ROLLUP_ID` | `0` | Reserved rollup ID for Ethereum mainnet (L1). You cannot register a rollup with this ID, and no cross-chain proxy may target it. |

---

## Public State

| Variable | Type | Description |
| --- | --- | --- |
| `rollupCounter` | `uint256` (public) | Counter used to assign sequential rollup IDs. Incremented in `registerRollup`; the next registered rollup receives `rollupCounter + 1`. |
| `rollups` | `mapping(uint256 => RollupConfig)` (public) | Maps a rollup ID to its `RollupConfig` (manager address, state root, ether balance). A zero `rollupContract` means the ID is unregistered. |
| `authorizedProxies` | `mapping(address => ProxyInfo)` (public, inherited from `EEZBase`) | Maps a deployed `CrossChainProxy` address to the `(originalAddress, originalRollupId)` pair it represents. A zero `originalAddress` means the address is not a registered proxy. |
| `_transientExecutions` | `ExecutionEntry[]` (public) | Backing storage for the batch's leading prefix of execution entries (per `transientExecutionEntryCount`). Populated by `postAndVerifyBatch` step 4 and `delete`d at the end of every call, success or failure — semantically transient even though it's declared as regular storage (Solidity doesn't yet support `transient` for reference types with nested dynamic arrays). |
| `_transientLookupCalls` | `LookupCall[]` (public) | Backing storage for the batch's leading prefix of top-level lookup calls (per `transientLookupCallCount`). Same lifecycle as `_transientExecutions` — populated then `delete`d within a single `postAndVerifyBatch` call. |

## Functions

<details>
<summary>registerRollup — Register a new rollup</summary>

`registerRollup` is the permissionless entry point for onboarding a new rollup. You first deploy your `IRollupContract`-conforming manager (see [`Rollup.sol`](/contracts/rollup)) with the desired proof systems, verification keys, threshold, and ownership baked in, then call this function to register it. The registry assigns a fresh `rollupId`, stores your initial state root, and fires a one-shot `rollupContractRegistered(rollupId)` callback on your manager so it learns its assigned ID.

**Who can call it:** Anyone.

**Emits:** `RollupCreated(rollupId, rollupContract, initialState)`

```solidity
function registerRollup(address rollupContract, bytes32 initialState)
    external
    returns (uint256 rollupId)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupContract` | `address` | Address of your pre-deployed `IRollupContract`-conforming manager. Must not be `address(0)` or the `EEZ` registry itself. The registry stores this as the authoritative source for proof-system membership, verification keys, and threshold for the new rollup. |
| `initialState` | `bytes32` | The genesis state root for this rollup. Stored as `rollups[rollupId].stateRoot` and used as the starting point for all subsequent state-delta checks. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `rollupId` | `uint256` | The newly assigned rollup ID. IDs are assigned sequentially starting at `1` (`MAINNET_ROLLUP_ID = 0` is reserved). Your manager contract receives this same value via the `rollupContractRegistered` callback. |

#### Errors

| Error | Condition |
| --- | --- |
| `InvalidRollupContract` | `rollupContract` is `address(0)` or equals `address(this)`. |

</details>

<details>
<summary>postAndVerifyBatch — Post and atomically verify a proof batch</summary>

`postAndVerifyBatch` is the central ingest function for the protocol. You submit a single `ProofSystemBatchPerVerificationEntries` struct that bundles execution entries, top-level lookup calls, proof-system addresses, per-rollup proof-system subsets, ZK proofs, optional EIP-4844 blob indices, and a target L1 block number. The function validates and verifies the entire batch atomically — if any proof fails, the whole call reverts. On success it advances the state roots of all touched rollups, loads a transient execution stream, gives the caller's contract a meta-hook to consume entries inline, and finally publishes any remaining entries into per-rollup deferred queues.

**Who can call it:** Anyone. Correctness is enforced by the ZK proofs.

**Processing:** validates structure, fetches vkeys via `checkProofSystemsAndGetVkeys` (STATICCALL), verifies every proof atomically, marks each rollup as verified for the current block, drains leading transient entries inline (with a meta-hook on `msg.sender`), and publishes the remainder into per-rollup queues. See [Post Batch](/guides/post-verify-batch) for the full 8-step pipeline.

**Emits:** `BatchPosted(rollupCount)`, `ImmediateEntrySkipped` (per skipped entry), `L2ExecutionPerformed`, `ExecutionConsumed`, `EntryExecuted`, and (conditionally, from the immediate-entry drain's `_processNCalls`/`_consumeNestedAction` path) `CallResult`, `RevertSpanExecuted`, `L1ToL2CallConsumed`, `L1ToL2CallNotFound`

```solidity
function postAndVerifyBatch(
    ProofSystemBatchPerVerificationEntries calldata batch
) external
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `batch` | `ProofSystemBatchPerVerificationEntries` | The full batch descriptor. Key fields: **`entries`** (`ExecutionEntry[]`) — Ordered list of all execution entries. Each entry carries `stateDeltas`, a flat call array (`l2ToL1Calls`), reentrant call table (`expectedL1ToL2Calls`), nested lookups, a rolling hash, and the pre-computed `returnData`. **`l1ToL2lookupCalls`** (`LookupCall[]`) — Top-level lookup calls (static reads and reverting calls available outside an execution). Nested lookups travel inside their entries. **`transientExecutionEntryCount`** (`uint256`) — How many leading entries to place in the transient stream (available for meta-hook consumption). Must be `≤ entries.length`. **`transientLookupCallCount`** (`uint256`) — How many leading lookup calls to place in the transient stream. Must be `≤ l1ToL2lookupCalls.length`. **`proofSystems`** (`address[]`) — The batch-global list of proof system contract addresses, sorted strictly ascending. No duplicates, no `address(0)`. **`rollupIdsWithProofSystems`** (`RollupIdWithProofSystems[]`) — Per-rollup participation rows, sorted strictly ascending by `rollupId`. Each row pairs a `rollupId` with a `proofSystemIndex[]` (strictly-ascending indices into `proofSystems`) selecting the subset of proof systems that attest to that rollup. **`blobIndices`** (`uint256[]`) — Indices of the EIP-4844 blob commitments this batch consumes. May be empty. **`callData`** (`bytes`) — Batch-scoped calldata folded into the public inputs hash. **`proofs`** (`bytes[]`) — One proof per proof system in `proofSystems` (same length). Each proof covers the shared public inputs hash combined with that proof system's per-rollup vkey accumulator. **`blockNumber`** (`uint64`) — The L1 block this batch binds to. Forwarded to every rollup's `getCustomData(blockNumber)`. Use `0` for no block context, or `type(uint64).max` for the latest context. |

#### Errors

| Error | Condition |
| --- | --- |
| `PostBatchReentry` | `postAndVerifyBatch` was called while a batch is already mid-flight (e.g., from the meta hook). |
| `InvalidProofSystemConfig` | The batch is structurally malformed — empty `proofSystems`, length mismatch between `proofSystems` and `proofs`, empty `rollupIdsWithProofSystems`, `rollupIdsWithProofSystems` not strictly increasing by `rollupId`, an unregistered rollup, an empty `proofSystemIndex` for a rollup, an out-of-range proof-system index, or `proofSystemIndex` not strictly increasing within a rollup. |
| `DuplicateProofSystem(address)` | The `proofSystems` array is not strictly ascending (duplicates or address(0) detected). |
| `StateDeltasNotStrictlyIncreasing(uint256)` | An entry's `stateDeltas` are not strictly increasing by `rollupId` — rejects duplicate rollups within one entry and (bounding above `MAINNET_ROLLUP_ID`) a mainnet (L1) delta. |
| `RollupNotInBatch(uint256)` | A `StateDelta.rollupId` (within an entry) or an `ExpectedStateRootPerRollup.rollupId` (within a top-level lookup call's pins) is not in the batch's `rollupIdsWithProofSystems`. |
| `EntryDestinationNotInStateDeltas(uint256)` | An entry's `destinationRollupId` is not in **that entry's own** `stateDeltas` — a narrower check than batch membership. This error is entry-only; a top-level lookup call's destination is validated separately by `LookupDestinationNotPinned`. |
| `CallSourceNotVerified(uint256)` | An `l2ToL1Calls` entry's `sourceRollupId` is not in the host's verified rollup set (the entry's `stateDeltas`, or a top-level lookup's `expectedStateRoots` pins). MAINNET (L1) is never verified, so an L1-sourced call is always rejected here. |
| `ReentrantDestinationNotVerified(uint256)` | A reentrant `expectedL1ToL2Calls` entry's (or nested lookup's) `destinationRollupId` is not in the host's verified rollup set. MAINNET (L1) is never a valid cross-chain destination. |
| `ExpectedStateRootsNotStrictlyIncreasing(uint256)` | A top-level lookup call's `expectedStateRoots` pins are not strictly increasing by `rollupId` — same rationale as `StateDeltasNotStrictlyIncreasing`. |
| `LookupDestinationNotPinned(uint256)` | A top-level lookup call's `destinationRollupId` is not among its own `expectedStateRoots` pins. |
| `TransientCountExceedsEntries` | `transientExecutionEntryCount > entries.length`. |
| `TransientLookupCallCountExceedsLookupCalls` | `transientLookupCallCount > l1ToL2lookupCalls.length`. |
| `TransientLookupCallsWithoutTransientEntries` | `transientLookupCallCount != 0` while `transientExecutionEntryCount == 0` — transient lookups are only reachable while transient entries are mid-flight, so this shape is rejected outright. |
| `InvalidProof` | At least one proof system's `verify(proof, publicInputsHash)` returned false. |
| `ThresholdNotMet(uint256 submitted, uint256 required)` (from `Rollup`) | A rollup's manager rejected the proof-system subset because `submitted` (the subset length) is below `required` (the rollup's configured threshold). |
| `StateRootMismatch(uint256)`, `RollingHashMismatch`, `UnconsumedL2ToL1Calls`, `UnconsumedL1ToL2Calls`, `EtherDeltaMismatch`, `InsufficientRollupBalance`, `ExecutionNotFound` | **Not** raised by the immediate-entry drain (`attemptApplyImmediate`) — those failures are caught internally and surface as `ImmediateEntrySkipped` instead, never reverting the batch. These can only revert `postAndVerifyBatch` itself if the meta hook drives a queued entry via a nested `executeCrossChainCall` / `executeL2TX` call that fails and the caller's own `executeMetaCrossChainTransactions()` doesn't catch it — see those functions' error tables for exactly when each condition fires. |

</details>

<summary>attemptApplyImmediate — Self-call wrapper for one immediate entry</summary>

`attemptApplyImmediate` runs `_applyAndExecute` for a single transient entry in an isolated, revertible frame. `postAndVerifyBatch` step 5 dispatches each leading immediate entry (`proxyEntryHash == bytes32(0)`) through this self-call inside a `try`/`catch`: if the inner `_applyAndExecute` reverts, only that entry's state mutations roll back and the batch continues with the next entry (emitting `ImmediateEntrySkipped`). You should never call this directly — it is only reachable from `postAndVerifyBatch`'s own internal loop.

**Who can call it:** Only the `EEZ` contract itself (`msg.sender == address(this)`), via the self-call in `postAndVerifyBatch` step 5.

**Emits:** `L2ExecutionPerformed`, `EntryExecuted`, and (conditionally, via the shared `_processNCalls`/`_consumeNestedAction` path) `CallResult`, `RevertSpanExecuted`, `L1ToL2CallConsumed`, `L1ToL2CallNotFound`. On revert, none of these persist — the caller's `try`/`catch` in `postAndVerifyBatch` rolls back the frame and emits `ImmediateEntrySkipped` instead.

```solidity
function attemptApplyImmediate(uint256 transientIdx) public
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `transientIdx` | `uint256` | Index into `_transientExecutions` of the immediate entry to apply. |

#### Errors

| Error | Condition |
| --- | --- |
| `NotSelf` | `msg.sender` is not the `EEZ` contract itself. |
| `ResidualEntryEtherIn` | `_entryEtherDelta` is non-zero on entry — immediate entries carry no inbound value, so a non-zero accumulator signals a corrupted execution context. |
| `StateRootMismatch(uint256)`, `RollingHashMismatch`, `UnconsumedL2ToL1Calls`, `UnconsumedL1ToL2Calls`, `EtherDeltaMismatch`, `InsufficientRollupBalance`, `StaticCallWithValue`, `ExecutionNotFound` | Propagated from the inner `_applyAndExecute` call (via `_applyStateDeltas` and `_processNCalls`) — see `executeCrossChainCall`'s error table above for exactly when each condition fires. Caught by `postAndVerifyBatch`'s `try`/`catch`, so these never revert the batch itself — they only trigger `ImmediateEntrySkipped`. |

</details>

<details>
<summary>executeCrossChainCall — Execute a queued cross-chain call via proxy</summary>

`executeCrossChainCall` is the runtime entry point that `CrossChainProxy` contracts call into on behalf of a remote caller. When an external account calls a proxy on L1, the proxy determines whether it is in a static or non-static context, then delegates here. The function resolves the matching `ExecutionEntry` from the active execution stream (transient or persistent), processes the flat call array, applies state deltas, and returns the entry's pre-computed `returnData`. You should never call this function directly — always interact through a `CrossChainProxy`.

**Who can call it:** Registered `CrossChainProxy` contracts only (`authorizedProxies[msg.sender].originalAddress != address(0)`).

**Value:** Payable. The `msg.value` is tracked against the entry's `etherDelta` invariant.

**Emits:** `CrossChainCallExecuted`, `ExecutionConsumed`, `EntryExecuted`, `L2ExecutionPerformed`, and (conditionally, from the shared `_applyAndExecute`/`_processNCalls`/`_consumeNestedAction` path) `CallResult`, `RevertSpanExecuted`, `L1ToL2CallConsumed`, `L1ToL2CallNotFound`

```solidity
function executeCrossChainCall(address sourceAddress, bytes calldata callData)
    external
    payable
    returns (bytes memory result)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `sourceAddress` | `address` | The original `msg.sender` as observed by the calling proxy — i.e., the address that initiated the cross-chain call from the remote rollup. This value is part of the `crossChainCallHash` used to look up the matching execution entry. |
| `callData` | `bytes` | The calldata originally sent to the proxy. Combined with `sourceAddress` and the proxy's registered `(originalAddress, originalRollupId)` pair to derive the `crossChainCallHash` for entry lookup. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `result` | `bytes` | The pre-computed `returnData` from the matched `ExecutionEntry`. This is the value the ZK proof committed to as the canonical return for this cross-chain call. |

#### Errors

| Error | Condition |
| --- | --- |
| `UnauthorizedProxy` | `msg.sender` is not a registered `CrossChainProxy`. |
| `ExecutionNotInCurrentBlock(uint256)` | `lastVerifiedBlock` for the proxy's rollup is not the current block. The queued entries have expired. |
| `ExecutionNotFound` | No matching entry exists for the computed `crossChainCallHash` in the active stream, and no matching reverted lookup call exists either. |
| `ReentrantDestinationMismatch(uint256, uint256)` | Called reentrantly (`_insideExecution()` is true) and the matched `ExpectedL1ToL2Call`'s declared `destinationRollupId` differs from this call's rollup. |
| `StateRootMismatch(uint256)` | An entry's `StateDelta.currentState` doesn't match the current on-chain state root for the affected rollup. |
| `RollingHashMismatch` | The computed rolling hash after processing all calls doesn't match the entry's committed `rollingHash`. |
| `EtherDeltaMismatch` | Net ETH flow across the entry doesn't match the declared `etherDelta`. |
| `InsufficientRollupBalance` | Applying a negative `etherDelta` would drive a rollup's ether balance below zero. |
| `UnconsumedL2ToL1Calls` | Not all calls in the flat `l2ToL1Calls` array were consumed by the end of the entry. |
| `UnconsumedL1ToL2Calls` | Not all reentrant calls in `expectedL1ToL2Calls` were consumed. |
| `StaticCallWithValue` | A flat call flagged `isStatic` in the entry's `l2ToL1Calls` carries a non-zero `value`. A `STATICCALL` cannot transfer ETH, so this is rejected rather than silently dropped. |

</details>

<details>
<summary>executeL2TX — Execute a pure L2 transaction from the deferred queue</summary>

`executeL2TX` consumes the next pure-L2 entry (one with no L1-originated trigger, i.e., `proxyEntryHash == bytes32(0)`) from the active execution stream. While a `postAndVerifyBatch` batch is mid-flight (inside the meta-hook window, when the transient table is non-empty), consumption comes from the shared transient execution table via the global transient cursor; outside a batch it consumes from the rollup's persistent per-rollup deferred queue at `executionQueueIndex`. These are transactions the rollup executed internally — no cross-chain proxy call drove them. You can call this to finalize state-root updates and any outgoing L1 calls attached to such transactions. You cannot call this while a cross-chain execution is in progress.

**Who can call it:** Anyone, as long as no execution is currently active.

**Emits:** `L2TXExecuted(rollupId, executionQueueIndex)`, `ExecutionConsumed(crossChainCallHash, rollupId, executionQueueIndex)`, `L2ExecutionPerformed`, `EntryExecuted`, and (conditionally, from the shared `_applyAndExecute`/`_processNCalls`/`_consumeNestedAction` path) `CallResult`, `RevertSpanExecuted`, `L1ToL2CallConsumed`, `L1ToL2CallNotFound`

```solidity
function executeL2TX(uint256 rollupId) external returns (bytes memory result)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupId` | `uint256` | The rollup whose deferred queue you want to advance. The queue must have been populated in the current block by a `postAndVerifyBatch` call, and `lastVerifiedBlock[rollupId]` must equal `block.number`. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `result` | `bytes` | The pre-computed `returnData` from the consumed `ExecutionEntry` (the value the proof committed to for this transaction). |

#### Errors

| Error | Condition |
| --- | --- |
| `ExecutionNotInCurrentBlock(uint256)` | `lastVerifiedBlock` for the rollup is not the current block — either no batch was posted this block, or entries have already expired. |
| `L2TXNotAllowedDuringExecution` | Called while a cross-chain execution is already in progress (`_insideExecution()` is true). |
| `ResidualEntryEtherIn` | The ether accumulator is non-zero entering this call — indicates a protocol bug. |
| `ExecutionNotFound` | No matching pure-L2 entry (`proxyEntryHash == bytes32(0)`) exists in the active stream at the rollup's current cursor position. |
| `StateRootMismatch(uint256)` | The entry's `StateDelta.currentState` doesn't match the current on-chain state root. |
| `InsufficientRollupBalance` | Applying a negative `etherDelta` would drive the rollup's ether balance below zero. |
| `RollingHashMismatch` | The rolling hash after processing doesn't match the entry's committed value. |
| `UnconsumedL2ToL1Calls` | Not all calls in the flat `l2ToL1Calls` array were consumed by the end of the entry. |
| `UnconsumedL1ToL2Calls` | Not all reentrant calls in `expectedL1ToL2Calls` were consumed. |
| `EtherDeltaMismatch` | The net ETH flow doesn't match the declared `etherDelta`. |
| `StaticCallWithValue` | A flat call flagged `isStatic` in the entry's `l2ToL1Calls` carries a non-zero `value`. A `STATICCALL` cannot transfer ETH, so this is rejected rather than silently dropped. |

</details>

<summary>executeInContextAndRevert — Self-call wrapper for a revert span</summary>

`executeInContextAndRevert` runs a `revertSpan` sub-run of calls (a group of calls the prover marked to always revert together, e.g. a failed `try`/`catch` branch on L2) in an isolated frame that itself always reverts. `_processNCalls` dispatches into it via a self-call whenever it hits a call flagged with a non-zero `revertSpan`, decodes the reverted `ContextResult` payload to recover the post-span rolling hash and cursor state, and folds that state back into the outer entry — `RevertSpanExecuted` is then emitted by `_processNCalls` in the caller's own frame, not by this function. You should never call this directly.

**Who can call it:** Only the `EEZ` contract itself (`msg.sender == address(this)`), via the self-call in `_processNCalls`.

```solidity
function executeInContextAndRevert(uint256 callCount) external
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `callCount` | `uint256` | Number of calls (the `revertSpan`) to process from the active flat `l2ToL1Calls` array before the forced revert. |

#### Errors

| Error | Condition |
| --- | --- |
| `NotSelf` | `msg.sender` is not the `EEZ` contract itself. |
| `StaticCallWithValue` | A flat call within the span (`_processNCalls(callCount)`) is flagged `isStatic` and carries a non-zero `value`. A `STATICCALL` cannot transfer ETH, so this reverts the frame with `StaticCallWithValue` before ever reaching the deliberate `ContextResult` revert below. |
| `ContextResult(bytes32 rollingHash, uint256 reentrantConsumed, uint256 callsProcessed, bool callNotFound)` | Always reverted on the success path too — this is the function's only exit, not a failure signal. It carries the post-span rolling hash, reentrant-call cursor, flat-call cursor, and deferred no-match flag back to `_processNCalls`, which decodes it via `_decodeContextResult`. |

</details>

<details>
<summary>staticCallLookup — Resolve a static cross-chain read</summary>

`staticCallLookup` is the view-function counterpart to `executeCrossChainCall`. When a `CrossChainProxy` detects that it is being called in a static context (via `tstore`-based detection), it routes here instead. The function scans the active lookup table — either the transient pool during a batch or the rollup's persistent `lookupQueue` — for a `LookupCall` whose `crossChainCallHash` matches and whose state-root pins are all live. It then resolves and returns the pre-computed result. You should never call this directly; it is invoked by the proxy's `_fallback` via `STATICCALL`.

**Who can call it:** Registered `CrossChainProxy` contracts only, via STATICCALL.

```solidity
function staticCallLookup(address sourceAddress, bytes calldata callData)
    external
    view
    returns (bytes memory)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `sourceAddress` | `address` | The original `msg.sender` observed by the proxy — the address that issued the static cross-chain call from the remote chain. Used together with `callData` and the proxy's identity to compute the `crossChainCallHash`. |
| `callData` | `bytes` | The calldata forwarded by the proxy. Combined with `sourceAddress` and the proxy's `(originalAddress, originalRollupId)` to derive the lookup key. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `result` | `bytes` | The pre-computed return data from the matching `LookupCall`. If the lookup has `failed == true`, the call reverts with the stored `returnData` instead of returning it. |

#### Errors

| Error | Condition |
| --- | --- |
| `UnauthorizedProxy` | `msg.sender` is not a registered `CrossChainProxy`. |
| `ExecutionNotFound` | No matching `LookupCall` was found — the hash doesn't match, or the state-root pins are stale. |
| `ReentrantDestinationMismatch(uint256, uint256)` | Inside an execution, the matched `ExpectedLookup` declared a `destinationRollupId` that differs from the calling proxy's rollup. |
| `RollingHashMismatch` | The rolling hash recomputed from the matched lookup's `l2ToL1Calls` doesn't match its committed `rollingHash`. |
| `LookupCallProxyNotDeployed(address)` | A sub-call's derived source `CrossChainProxy` address has no deployed code — a `STATICCALL` to a codeless address would silently succeed as a no-op, so the prover can't pre-hash a false result. |

</details>

<details>
<summary>setStateRoot — Owner escape hatch for manual state root updates</summary>

`setStateRoot` is a governance-controlled escape hatch that lets the registered rollup manager contract directly override the on-chain state root for its rollup without going through the proof-submission path. Access is gated by the manager itself: only the address stored in `rollups[rollupId].rollupContract` can invoke it, so the effective policy — whether that manager exposes the call as owner-only, behind a multisig, or behind a timelock — is defined by each rollup's own manager implementation (the reference `Rollup.sol` uses OpenZeppelin `Ownable`). It exists for documented recovery scenarios such as a prover being offline or a rollup-software bug that needs to be corrected. The registry blocks this call for the rest of a block once `postAndVerifyBatch` has touched the rollup in that block, preventing races with the multi-prover verification flow.

**Who can call it:** Only `rollups[rollupId].rollupContract` (the rollup's registered manager).

**Emits:** `StateUpdated(rollupId, newStateRoot)`

```solidity
function setStateRoot(uint256 rollupId, bytes32 newStateRoot) external
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupId` | `uint256` | The ID of the rollup whose state root you want to override. The caller must be the `rollupContract` registered for this ID. |
| `newStateRoot` | `bytes32` | The new state root to commit. There is no pre-state check — this is an unconditional write, so you are responsible for correctness. |

#### Errors

| Error | Condition |
| --- | --- |
| `NotRollupContract` | `msg.sender` is not the registered `rollupContract` for `rollupId`. |
| `SetStateRootNotAllowedDuringExecution` | A cross-chain execution is currently in progress. |
| `RollupBatchActiveThisBlock(uint256)` | A `postAndVerifyBatch` has already touched this rollup in the current block. You must wait until the next block. |

</details>

<details>
<summary>createCrossChainProxy — Deploy a cross-chain proxy for a remote address</summary>

`createCrossChainProxy` deploys a `CrossChainProxy` contract via CREATE2 and registers it in the `authorizedProxies` registry. The proxy stands in for a specific `(originalAddress, originalRollupId)` pair on L1, allowing contracts on L1 to receive cross-chain calls from that remote address. The resulting proxy address is deterministic and can be pre-computed with `computeCrossChainProxyAddress` before deployment. You cannot create a proxy for an address on L1 itself (`MAINNET_ROLLUP_ID = 0`).

**Who can call it:** Anyone.

**Emits:** `CrossChainProxyCreated(proxy, originalAddress, originalRollupId)`

```solidity
function createCrossChainProxy(address originalAddress, uint256 originalRollupId)
    external
    returns (address proxy)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `originalAddress` | `address` | The remote address this proxy will represent. When the proxy is called on L1, it forwards the call as if `originalAddress` on `originalRollupId` is the caller. |
| `originalRollupId` | `uint256` | The rollup ID of the chain where `originalAddress` lives. Must not be `MAINNET_ROLLUP_ID` (0) — cross-chain proxies are for remote addresses only. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| `proxy` | `address` | The address of the newly deployed `CrossChainProxy` contract. |

#### Errors

| Error | Condition |
| --- | --- |
| `SameNetworkProxy(uint256)` | `originalRollupId` equals `MAINNET_ROLLUP_ID` (0) — you cannot proxy an L1 address on L1. |

</details>

<details id="computecrosschainproxyaddress">
<summary>computeCrossChainProxyAddress — Predict proxy address before deployment</summary>

`computeCrossChainProxyAddress` is a view function that lets you predict the deterministic CREATE2 address of a `CrossChainProxy` before deploying it. The address depends on the `EEZ` contract address, the `originalAddress`, the `originalRollupId`, and the `CrossChainProxy` bytecode. You can call this to check whether a proxy already exists at the computed address (non-zero `code.length`) or to pre-configure contracts that will receive cross-chain calls before the proxy is deployed.

**Who can call it:** Anyone.

```solidity
function computeCrossChainProxyAddress(address originalAddress, uint256 originalRollupId)
    public
    view
    returns (address)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `originalAddress` | `address` | The remote address the proxy would represent. |
| `originalRollupId` | `uint256` | The rollup ID of the chain where `originalAddress` lives. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| — | `address` | The deterministic CREATE2 address where the proxy would be (or already is) deployed. Check `address.code.length` to determine whether deployment has occurred. |

</details>

<details>
<summary>computeCrossChainCallHash — Compute the canonical call hash</summary>

`computeCrossChainCallHash` is a `pure` helper that computes the six-field `crossChainCallHash` used throughout the protocol as the canonical identifier for a cross-chain call. The same formula is used on L1 and L2, so off-chain tooling, provers, and contracts can all derive the same value. The hash is `keccak256(abi.encode(targetRollupId, targetAddress, value, data, sourceAddress, sourceRollupId))` and the field order must not be changed.

**Who can call it:** Anyone.

```solidity
function computeCrossChainCallHash(
    uint256 targetRollupId,
    address targetAddress,
    uint256 value,
    bytes memory data,
    address sourceAddress,
    uint256 sourceRollupId
) public pure returns (bytes32)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `targetRollupId` | `uint256` | The rollup ID of the chain being called (the destination). |
| `targetAddress` | `address` | The address being called on the destination chain. |
| `value` | `uint256` | The ETH value attached to the call (in wei). Use `0` for static calls. |
| `data` | `bytes` | The calldata for the call. |
| `sourceAddress` | `address` | The originating address on the source chain. |
| `sourceRollupId` | `uint256` | The rollup ID of the chain where the call originates. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| — | `bytes32` | The canonical cross-chain call hash used to match `ExecutionEntry.proxyEntryHash` and `ExpectedL1ToL2Call.crossChainCallHash` fields during execution. |

</details>

<details>
<summary>lastVerifiedBlock — Query the block of the last batch for a rollup</summary>

`lastVerifiedBlock` returns the block number at which a rollup was most recently touched by a successful `postAndVerifyBatch`. This value is used as a read gate: execution functions (`executeCrossChainCall`, `executeL2TX`) revert with `ExecutionNotInCurrentBlock` unless the return value equals `block.number`. It is also the lockout signal for `setStateRoot` — the escape hatch is blocked whenever this equals `block.number`.

**Who can call it:** Anyone.

```solidity
function lastVerifiedBlock(uint256 _rollupId) external view returns (uint256)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupId` | `uint256` | The rollup ID to query. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| — | `uint256` | The block number of the last successful `postAndVerifyBatch` that touched this rollup. Returns `0` if the rollup has never been verified. Only entries posted in the same block are consumable — entries from prior blocks are unreachable. |

</details>

<details>
<summary>queueLength — Query the deferred execution queue size</summary>

`queueLength` returns the total number of `ExecutionEntry` items in a rollup's deferred queue as populated by the most recent `postAndVerifyBatch` in the current block. This count includes already-consumed entries (the queue is not compacted). Compare against `executionQueueIndex` to determine how many entries remain to be consumed.

**Who can call it:** Anyone.

```solidity
function queueLength(uint256 _rollupId) external view returns (uint256)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupId` | `uint256` | The rollup ID whose queue length you want to check. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| — | `uint256` | Total number of entries in the rollup's `executionQueue`. The number of unconsumed entries is `queueLength(rollupId) - executionQueueIndex(rollupId)`. |

</details>

<details>
<summary>executionQueueIndex — Query the consumption cursor position</summary>

`executionQueueIndex` returns the next-to-consume cursor for a rollup's deferred execution queue. Each successful call to `executeCrossChainCall` or `executeL2TX` advances this cursor by one. The cursor is reset to `0` every time `postAndVerifyBatch` verifies a rollup (including same-block re-verifies, which replace the queue entirely).

**Who can call it:** Anyone.

```solidity
function executionQueueIndex(uint256 _rollupId) external view returns (uint256)
```

#### Parameters

| Name | Type | Description |
| --- | --- | --- |
| `rollupId` | `uint256` | The rollup ID whose cursor you want to read. |

#### Returns

| Name | Type | Description |
| --- | --- | --- |
| — | `uint256` | The index of the next entry to be consumed from the rollup's deferred queue. Entries at indices `[0, executionQueueIndex)` have already been consumed in the current block. |

</details>

## Key Structs

### [`ProofSystemBatchPerVerificationEntries`](/contracts/data-types#proofsystembatchperverificationentries)

The top-level batch struct you pass to `postAndVerifyBatch`. It bundles the execution entries, top-level lookup calls, proof systems, per-rollup PS subsets, ZK proofs, blob indices, calldata, and block context.

### [`ExecutionEntry`](/contracts/data-types#executionentry-l1)

Represents one unit of cross-chain execution. Contains `stateDeltas` (pre/post state roots and ether deltas per rollup), `proxyEntryHash` (the `crossChainCallHash` a proxy must present to consume this entry via `executeCrossChainCall` — `bytes32(0)` for a pure L2 transaction consumed via `executeL2TX`), `destinationRollupId` (which rollup's queue this entry is published under), a flat `l2ToL1Calls` array of all calls in execution order, a `expectedL1ToL2Calls` table for reentrant call pre-computation, `expectedLookups` for nested static/reverted reads, `callCount` for the top-level call partition, pre-computed `returnData`, and the expected `rollingHash`.

### [`StateDelta`](/contracts/data-types#statedelta)

Describes one rollup's state transition within an entry: `rollupId`, `currentState` (pre-state checked on-chain against `rollups[rollupId].stateRoot`), `newState`, and signed `etherDelta`.

### [`LookupCall`](/contracts/data-types#lookupcall-l1)

A top-level pre-computed result for a cross-chain call that should be looked up rather than executed. Lives in the transient pool or the rollup's persistent `lookupQueue`. Matched by `crossChainCallHash` \+ state-root pins \+ `destinationRollupId`.

### [`RollupConfig`](/contracts/data-types#rollupconfig)

The per-rollup record held by the central registry: `rollupContract` (the manager), `stateRoot`, and `etherBalance`.
